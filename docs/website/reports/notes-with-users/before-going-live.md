## 1. Before the first deploy, at your host

What the live copy of the app is given where it runs: its settings, its keys, and its files.

- [ ] Turn on HTTPS at your host, with a certificate browsers trust, send visitors who come over plain HTTP to HTTPS, and turn off the old versions of TLS (1.0 and 1.1). Most hosts have these on one settings page. (V12.2.1, V12.2.2, V12.1.1)
- [ ] Put a real address in SECURITY.md where people can tell you about a security problem they find. At `SECURITY.md:1`.

## 2. After the first deploy, at the live address

What only the app's own live site can answer. `sv probe` makes a handful of read-only requests to the address you give it and nothing else; it prints its answers and adds nothing to the report.

- [ ] The site answers over HTTPS, and plain HTTP is no way in. Run `sv probe https://your-address`. (V12.2.1)
- [ ] Its certificate is one browsers trust. Run `sv probe https://your-address`. (V12.2.2)
- [ ] Old versions of TLS (1.0 and 1.1) are refused. Run `sv probe https://your-address`. (V12.1.1)
- [ ] Browsers are told to use HTTPS only (HSTS). Run `sv probe https://your-address`. (V3.4.1)
- [ ] The session cookie's name carries the `__Host-` prefix. Run `sv probe https://your-address`. (V3.3.3)
- [ ] A program calling the API over plain HTTP is refused rather than redirected. Run `sv probe https://your-address --api /a/path/of/your/api`. (V4.1.2)
- [ ] Only strong encryption settings (cipher suites) are offered. Not sv probe: check it with a scanner made for it, such as testssl.sh or SSL Labs' online test (see "What only you can check"). (V12.1.2)
- [ ] If the app has accounts: on the live site, sign up, sign in, sign out, and change a password the way a person would, and see each works. The checks before going live tried them on a copy on this computer, not on your host.
