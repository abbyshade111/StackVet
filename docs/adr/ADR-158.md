# ADR-158: Sessions open pull requests as a GitHub App of the owner's, so the owner's code-owner review holds for their changes

**Status:** proposed, 21 November 2026, in the claim of backlog 0692. Chosen by the owner the same day, asked with a
recommendation: a separate identity for sessions rather than correcting ADR-051, and a GitHub App rather than a second
account. It becomes accepted in the pull request that builds it.

**Governs:** `.github/CODEOWNERS`, `.github/rulesets.json`. A pull request that changes them changes this record too, or
says in its description why it does not (`docs/adr/README.md`).

## Context

ADR-051's Later entry of 14 October 2026 (backlog 0290) made the "Main - ADR Check" ruleset ask for a code owner's
review of the files that judge the required checks (`.github/workflows/`, `tools/ci_scope.py`, `tools/adr_check.py`,
`tools/record_numbers.py`, and `action.yml`), so that a pull request could not edit its own judge and report green
unseen. It says such a change, "by a session or by the owner's own tooling", waits for the owner's review.

It does not, for a session. Sessions run `gh` and `git push` signed in as the owner, so the owner is the pull request's
author, and GitHub lets no author approve their own pull request. Pull requests opened that way that changed those
files merged with no review (#2352, #2354); only Dependabot's waited (backlog 0692). The owner found it on 21 November
2026, when GitHub offered no way to approve #2446.

## Decision

1. **The identity.** The owner creates a GitHub App on their own account, private to it, with no webhook, installed on
   `abbyshade111/StackVet`, `abbyshade111/homebrew-stackvet`, and `abbyshade111/scoop-stack-vet` only. Its permissions are
   the least a session needs: contents, pull requests, and workflows, read and write (workflows, because a session's
   change to a file under `.github/workflows/` is refused without it), and metadata, read, which GitHub always
   grants. No administration, so it cannot change a ruleset, a setting, or who may bypass a rule; it is never a bypass
   actor in `.github/rulesets.json`.
2. **The key and the token.** The App's private key stays on the owner's Mac, outside every repository and session
   folder, where the owner puts it (the macOS keychain is the plan). A script in `tools/` makes an installation token
   from it when a session needs one: signed with the `openssl` macOS has, valid for an hour, and handed to `gh` and
   `git` through the environment of the one command that uses it. It never prints, logs, or writes the key or the
   token (CLAUDE.md), and a session that cannot get a token says so and stops, rather than falling back to the owner's
   sign-in.
3. **What changes for a pull request.** A session's pull request is the App's. One that changes a code-owned file waits
   for the owner's approving review before auto-merge takes it, as ADR-051 said; every other one still merges on its
   checks alone (the ruleset asks for no approvals otherwise). The owner's own `gh` sign-in is unchanged and is how they
   approve. Commits keep their `Co-Authored-By:` lines, which ADR-092 reads.
4. **The witness.** A session's pull request that changes a file under `.github/workflows/` is seen waiting for the
   owner's review, and merges once they approve.

## Alternatives considered

- **Correct ADR-051 instead,** to say the rule holds back pull requests from anyone but the owner's account. The owner
  chose against leaving a session's change to its own judge unreviewed.
- **A second GitHub account (a machine user)** with a personal access token. Less to build, but the token lasts up to a
  year and the account is one more password and second factor to guard; an App's token lasts an hour, reaches only the
  repositories it is installed on, and cannot be signed into on the web.

## Consequences

- The owner reviews every session pull request that changes the workflows or the three judging scripts. That is the
  point, and also a wait: such a pull request no longer merges while the owner is away.
- A key on the owner's Mac becomes something to look after. Losing it means making a new one in the App's settings;
  a leaked token stops working within the hour, and the key can be revoked there.
- Cloud sessions, which do not run on the owner's Mac, are not covered by this record; the build says what they use.
- Until it is built, ADR-051's 14 October entry stays wrong for sessions; backlog 0692 says so.
