# ADR-086: The observability dashboard adds five things to `sv dashboard`, as the owner chose on 11 October 2026

**Status:** proposed, 11 October 2026, with the design of backlog 0227. Accepted in the pull request that builds each
part, which says where the build differs from this plan.

**Governs:** `crates/sv-report/src/dashboard.rs`, `crates/sv-cli/src/history.rs`, `crates/sv-report/src/dashboard/*.rs`, `crates/sv-cli/src/board_link.rs`, `crates/sv-cli/src/crash.rs`, `tools/backlog.py`. The dashboard is one page written from
the tool's own records; a change to what it reads, or to what it keeps, changes this record or says in its pull request
why it does not.

## Context

Backlog 0227 asks for an observability page once the observability review's findings are built, showing what `sv` did
and why, across runs and apps, from `sv`'s own records only. ADR-057 already decided the dashboard: one page, written to
the owner's computer, optional, with history kept outside every app's folder. Most of what 0227 lists is already in
`sv dashboard`: the per-app views, the "Over time" section read from the history, and the requirement changes between
runs. The owner was shown a mock-up on 11 October 2026 and answered the five questions it asked.

## Decision

1. **One page, not two.** The additions extend `sv dashboard`, which the owner chose over a page of its own.
2. **Every run kept on this computer.** The history under `~/.local/share/stackvet/history/` (ADR-057) keeps every run,
   not a selection. Nothing here changes what a run records.
3. **Requirement changes since the last run, with a drill-down.** The requirement view shows only those whose status
   changed since the run before. Each one links to its full row across every run, so nothing is hidden, only sorted.
4. **The build loop: names and sizes.** The build loop's section lists the prompts and report files it was given, by name
   and size, and the findings fixed, set aside, and new. It does not show their contents, since they can hold code.
5. **The backlog overview is its own page.** It reads the items' own status lines and parts, as backlog 0228 records them,
   and is linked from the dashboard. It is read-only and changes no item.

## Considered

- **Showing the contents of the build loop's prompts and reports.** Declined by the owner for item 4: they can hold code,
  and the page is written to a computer that may be shared.
- **Hiding the unchanged requirements altogether.** Declined for item 3: the drill-down keeps them one click away.

## Consequences

- No new record is kept. Only what the dashboard shows changes; what `sv` writes into a folder does not.
- The sv health section in 0227's first list is not among the five answers. It stays open in 0227 for the owner to decide.
- Each part is a separate pull request, with its own test that fails when the part is broken.

## Later, 11 October 2026: the owner's answers on the three open points

The owner answered the three points the first version left open, on 11 October 2026:

- **Sizes.** Yes: the build loop's record holds the size of each prompt and report file it was given, as ADR-084 records.
- **The backlog board.** A board file is written beside the repository (not inside it), by `tools/backlog.py board --html`,
  and the dashboard links to it when that file exists. The dashboard keeps no copy of the backlog.
- **A health section.** Yes. It shows `sv`'s own health in three parts: crashes (the crash files written under the history
  folder, backlog 0237), runs in the history that could not be read, and data files that did not load in a run, each
  named in the run's record. The third part is a change to what a run records, so it is written into the run record's
  own entry (ADR-057) by its own pull request.

Each of these is built in its own pull request, which accepts the decision it builds.

## Built, 11 October 2026: the names and sizes section (backlog 0227, part 1, second half)

Accepted in this pull request, for the first of the answers the dashboard shows: the build loop's section, "What the AI
coding tool was given", lists each report file and prompt by name, with its size where the record kept one (ADR-084,
decided the same day). A line written before sizes were kept shows the name only, and the section says so. The report
keeps the same map as the record (`handed_sizes`, left out when empty), so a report from before this reads and seals the
same. Not built yet: the board link (answer 2), the health section (answer 3), and the drill-down check (answer 4), each
in its own pull request.

## Built, 11 October 2026: the board link (backlog 0227, part 2)

The owner chose a board file beside the repository, and the dashboard linking to it. How that is done is this build's
choice, and the owner should confirm it:

- `tools/backlog.py board --html`, with no path, writes `stackvet-backlog.html` in the folder beside the repository, not
  inside it, so the board is never committed with the code. A path given still wins.
- The dashboard links the board only when the owner's file `backlog-board`, in the `stackvet` config folder, names a file
  that exists. Its first line is the path. `sv` only reads that file; it never writes to the config folder, and the owner
  writes the line.
- The link sits at the top of the dashboard, under the heading, and opens the file in the browser.

## Built, 11 October 2026: the health section, in part (backlog 0227, part 3, first two of its three kinds)

The dashboard's section "sv's own health on this computer" is built for two of the three kinds the owner chose:
- **Crashes.** Each crash file `sv` keeps under the history folder (backlog 0237) is listed by its time, the version, the
  command, and where in `sv` it stopped. Never the panic's message. A file missing any of its three lines is counted as
  unreadable, not guessed at.
- **Kept runs that could not be read.** The total across the apps, as each app's view already counts them.

The section always appears, and says so when nothing was kept.

## Built, 11 October 2026: the third kind of health, data files that did not load (backlog 0227, part 3)

Each kept run now names the data files `sv` ships that did not load in it, by file name and never by path (ADR-057, Later,
the same day). The health section counts them over the kept runs that record this, and says so when none does. A run kept
before the record named them says nothing either way: it is not counted as "none", and the section does not say that it
was. The drill-down check (answer 4) is the only part of 0227 still to build.

## Built, 11 October 2026: the drill-down on requirement changes (backlog 0227, part 4, answer 3)

The last part of 0227 is built, and this decision is accepted. Each run's comparison with the run before lists every
requirement whose status moved, not the first twelve with "and N more" as before. Each one is a line that opens, in
place, onto that requirement's status in every kept run of the app, oldest first, so nothing is hidden, only sorted.
Where the build differs from the plan: the plan said each line links to its full row, but a `#` link would change which
view the page shows (each app's view is shown by its address), so the row opens in place (`<details>`) instead. The
sentence about the changes is kept as it was, and the old `changes_since` text is unchanged for the tests that read it.
A run that kept no statuses, or did not finish, is said in the row rather than left out. Held by
`crates/sv-report/src/dashboard/drill_tests.rs`: a moved requirement opens onto its status in each run; every moved
requirement is listed, fifteen of fifteen, not twelve; a run without statuses or one that did not finish is said. Break
tests: with the list disabled, two of the three tests fail; with the unfinished-run row disabled, its test fails.
With this part, 0227's four parts are built.
