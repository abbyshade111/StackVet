# ADR-106: The suite runs as three jobs side by side, and the required check waits for them all

**Status:** accepted, 12 October 2026, in the pull request that builds it; proposed the same day with the backlog claim
(0192 part 1). The owner's decision the same day, after backlog 0270 measured cargo-nextest: "I don't want to move
forward with nextest, so if splitting into jobs can speed up or provide value, go ahead with that". Earlier the same
day, part 1 was to be built ("definitely want the slow test job split").

**Governs:** `.github/workflows/rust.yml` (its scope, lints, suite, and test jobs) and `tools/ci_shards.py`
(which of sv-cli's test files each part runs). A pull request that changes these changes this record too, or says in
its description why it does not (`docs/adr/README.md`).

## Context

The Rust workflow's test job ran formatting, lints, and the whole suite in one job, one test program after another:
about eighteen minutes on 12 October 2026, of which the tests were 975 seconds. On the last full run on the owner's
Mac, `sv-cli`'s tests were 877 of 1,221 seconds, most of them waiting for an app to start in a container. Backlog 0270
measured cargo-nextest, which runs every test at once in one job, at 36 percent off the test step and a new tool in
CI; the owner declined it.

## Decision

**Four jobs where there was one.** `scope` decides between ADR-104's short path and the whole suite, as the old job's
first step did. `lints` runs formatting and lints. `suite` runs three parts side by side, each on its own runner:
`rest`, every crate but `sv-cli` and `sv-cli`'s own unit tests and doc tests; and `cli-1` and `cli-2`, `sv-cli`'s test
files dealt between them. Each part builds the workspace again, about two minutes, so the longest should end near
nine minutes.

**The files are dealt, not listed.** `tools/ci_shards.py` deals the test files in `sv-cli`'s tests folder in name order, one to each
part in turn, so a new file joins a part without anyone choosing one. On the run measured, the two came out at 424 and
423 seconds. `crates/sv-cli/tests/ci_shards.rs` fails when the parts together are not every file exactly once. Before
this merged, the tests the three parts list were compared with those `cargo test --workspace` lists: the same, none
twice.

**The required check keeps its name and covers everything.** `test`, the check `main` requires (ADR-051), always runs,
waits for the others, and fails unless `scope` succeeded and, on the whole suite, `lints` and every part of `suite`
did. A part that fails, is canceled, or never runs fails it. On the short path it runs ADR-104's tests itself.

**The credit log is read whole.** Each part writes its own `SV_CREDIT_LOG`, and beside it the census of what checks
withheld (the same name with `.withheld`), and passes both to `test` through GitHub's own
upload-artifact and download-artifact actions, pinned to a commit like every other step, and kept three
days. `test` fails when any part's two are not there, then reads the three of each as one with `tools/coverage.py
--credits`, as the old job read one. The releases pinned are the newest at least two weeks old (upload v7.0.1 of
April 2026, download v8.0.1 of March 2026), not the releases of the week before.

## Alternatives considered

- **cargo-nextest**, measured in backlog 0270: declined by the owner.
- **Each part checked by `main`'s ruleset directly**: the required check's name would change, a repository setting and
  the owner's, and a part added later would not be required until someone added it there.
- **The credit log checked in each part**: the check needs the whole suite's credits, since a check listed as never
  crediting may credit in one part and withhold in another.
- **Lists of files kept by hand**: a new file would be in no part until someone added it, and the suite would pass
  without running it.

## Consequences

- A pull request should be checked in about half the time it was, at three runners' build time. The repository is
  public, so the runner minutes cost nothing.
- Each part fetches the container images and signs in to Docker Hub with the owner's token, so a run makes about three
  times the pulls it did, through the Google mirror (ADR-051, Later, 9 October 2026), and the token is handed to three
  steps where it was one.
- Two of GitHub's own actions are new dependencies of this workflow. They move only the credit log, which names checks
  and requirements and holds no answer the app gave.
- **Broken on purpose, each put back:** a file left out of the deal (`ci_shards.rs` failed), and the deal giving one
  file to both parts (it failed again).

## Later, 13 October 2026: a fourth part, for sv-check alone (backlog 0350)

`rest` held `sv-check`'s 1,500 unit tests and 40 test files beside every other crate, and was the longest part (431 s
on the run measured after the split, against 392 s and 358 s for `cli-1` and `cli-2`): a crate list, not a dealt set.
`suite` now runs four parts: `check`, `sv-check` alone, with the test-only 7z reader its archive tests need (ADR-089);
`rest`, every other crate but `sv-cli`, with `sv-cli`'s own unit and doc tests; and `cli-1` and `cli-2` as before. The
four together run the same tests as the three did. `test` waits for, and reads the credits of, all four; before this
merged, the new `rest` was run locally with `SV_CREDIT_LOG` set and wrote both logs (2,711 credits and 2,677 withheld
lines), so `test` finds them. The review estimated `rest` near 280 s after the move and the longest part then
`cli-1`'s; the cost is one more runner's fixed time, about two and a half to three minutes, per full run. Dealing
`sv-cli`'s files by a recorded weight rather than by name stays a later step. The decision, the suite split into parts
side by side with the required check waiting for them all, is unchanged.

## Later, 13 October 2026: a folder can be one program (backlog 0339)

Four of `sv-cli`'s test files each started an example app in a container and waited for it, and `cargo test` ran
them one after another: on the run of #1736, `email_change_example` 63 s, `host_cookie` 54 s, and `seen_record` 54 s in
`cli-1`, and `loopback_start` 62 s in `cli-2`, 233 s in all, most of it waiting. They are now modules of one program,
`crates/sv-cli/tests/started_apps/`, whose six tests run on threads at once. `tools/ci_shards.py` deals a folder holding
a `main.rs` as one program, as Cargo builds it, so the rule is the same: every program in exactly one part, dealt by
name. With four names gone and one added, files after them in name order change parts (`report_lock` moves to
`cli-2`). Only tests that need nothing from one another go in that folder: none sends a signal, holds a folder's lock,
or runs an app in a folder another test also uses. Measured on this pull request's own run: `started_apps` took 103 s
where the four took 233 s, its longest test, `seen_record`'s, about 100 s of that; the Tests steps of `cli-1` and `cli-2`
went from 7 min 17 s and 4 min 54 s on #1736's run to 4 min 17 s each, and the parts' summed test times from 348 s and
214 s to 199 s and 173 s. The decision is unchanged.
