# ADR-108: The Windows program is published as a signed GitHub Release when the owner pushes a version tag

**Status:** accepted, 12 October 2026, in the pull request that builds it; proposed the same day with the backlog claim
(0120 step 2). The owner's word on 12 October 2026: go ahead with the Windows build and its Scoop install. Asked the
same day with a recommendation for each, the owner chose a release of the Windows program only ("this only needs to
cover Windows since the other two are already handled", by Homebrew on Mac and Linux), that the owner pushes the
version tag, and that the owner creates the Scoop bucket, empty.

**Governs:** `.github/workflows/release.yml`. A pull request that changes it changes this record too, or says in its
description why it does not (`docs/adr/README.md`).

## Context

Until 12 October 2026 `sv` had never been published as a program: the repository's releases were v1's paper tags, with
no files. Mac and Linux install it through Homebrew, which builds it from source, and anyone with Docker runs the
container image, which is signed (ADR-080). Windows had neither: `sv` has been built and tested there nightly since
10 October (`windows.yml`), but there was no program to download, so a Scoop install had nothing to fetch.

## Decision

**A release workflow, run by a tag.** When a tag `v*` is pushed, a Windows runner builds `sv` with `--release`, and
the job fails unless the tag is `v` and the version in `Cargo.toml`. The program, its `data/` folder beside it (where
`sv` looks first after `SV_DATA_DIR`, ADR-036), and the licence are zipped as `sv-VERSION-windows-x86_64.zip`. The zip
is unzipped elsewhere and run with the checkout's own data moved away, so the check is of the data inside the zip: it
must report its version and read an example app. Then it is signed where it was built, with the same `actions/attest`
step the image's publishing uses (anyone can check it with `gh attestation verify`), and attached, with its SHA-256,
to a GitHub Release of the tag.

**The owner pushes the tag.** A release is public and permanent, so the moment is the owner's; no session pushes a
version tag.

**Tried without publishing.** Run by hand, or on a pull request that changes the workflow, the same steps build, zip,
and check the program, and keep the zip as the run's file for three days; nothing is signed and nothing is published.

## Alternatives considered

- **Windows, Mac, and Linux in each release**: the owner chose Windows alone, since Homebrew and the container cover
  the other two.
- **A release on every merge to `main`**: every merge would be a published version, with nothing to tell the owner's
  releases from a session's.
- **winget**, beside or instead of Scoop: it takes a pull request to Microsoft's own repository for each version,
  reviewed by people there; Scoop reads a bucket the owner controls. winget stays possible later, from the same
  release.

## Consequences

- A Windows user can install `sv` once the bucket's manifest points at a release (backlog 0120 step 2), and the guide
  gains its Windows section (step 3).
- The job holds `contents: write`, to make the release, and the signing permissions, only in this workflow and only for
  this job; the token is not left in the checked-out folder.
- A new version is a tag the owner pushes after the version in `Cargo.toml` is raised.

## Later, 12 October 2026: the first release, the bucket, and a second name

The owner pushed `v0.1.0` that evening; the release carries `sv-0.1.0-windows-x86_64.zip` and its SHA-256, and the
zip downloaded on a Mac matched it. The owner made the bucket as `abbyshade111/scoop-stack-vet` (the name Scoop is
given does not need to match the Homebrew tap's), holding `bucket/sv.json` (the zip's address, its hash, and
`checkver` and `autoupdate` from this repository's latest release) and a workflow that, on a Windows runner, installs
`sv` from that manifest, checks an example app with it, runs Scoop's `checkver` on it, and adds the bucket by its
public address, on every change and weekly. It passed on the fifth run; the first four found that Scoop adds a bucket
only from a git address, and that **in PowerShell `sv` is its own alias for `Set-Variable`**, so `sv --version` there
printed nothing and ran nothing of StackVet's. Asked, the owner chose to install the program under a second name as
well, `stackvet`, which PowerShell has no alias for; `sv` stays the name everywhere else, and `sv.exe` and the Command
Prompt's `sv` work too. The guide's Windows section says to type `stackvet` in PowerShell. None of this has been tried
by hand on a person's own Windows computer.

## Later, 12 October 2026: Scoop is the Windows route, and StackVet in Docker there waits

Building the setup prompt library (backlog 0370) found that the settings starting StackVet in Docker cannot be made on
Windows: `sv connect --docker` takes only a path starting with `/`, and the folder is shown inside the box at its own
path, which a Windows path cannot be. Asked, the owner chose to keep the Windows route this record set up, StackVet
installed with Scoop and connected with `stackvet connect TOOL`, and to leave StackVet in Docker on Windows for later
(backlog 0375). The setup prompts and the guide's step 3 say so.

## Later, 13 October 2026: the release job runs inside an Environment that admits only tags (backlog 0422)

The deep review of 13 October (backlog 0417) read that the workflow ran on a pull request that changed it with
`contents: write` and the signing permissions, gated only by `if:` lines in the same file, so a branch with push
rights could sign and publish a release before any merge: the same shape as backlog 0289 for the image. Asked, the
owner made a GitHub Environment named `release` in the repository's settings, with one deployment rule, tags `v*`,
and no other protection, and this entry records it. The workflow is now two jobs: `windows` builds, zips, checks,
and keeps the zip, with `contents: read` and nothing else, on a tag, by hand, or on a pull request that changes the
file; `release` runs only on a tag, inside that Environment, and signs and attaches the zip `windows` checked, handed
over as an artifact (as the image's `publish` job takes the tested image). GitHub holds the Environment's rule outside
the file, so an edit to the `if:` lines by a branch no longer reaches the signing or the release. The same day the
owner made a second Environment, `publish`, for the image (ADR-051).
