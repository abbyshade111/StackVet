# ADR-108: The Windows program is published as a signed GitHub Release when the owner pushes a version tag

**Status:** accepted, 12 October 2026, in the pull request that builds it; proposed the same day with the backlog claim
(0120 step 2). The owner's word on 12 October 2026: go ahead with the Windows build and its Scoop install. Asked the
same day with a recommendation for each, the owner chose a release of the Windows program only ("this only needs to
cover Windows since the other two are already handled", by Homebrew on Mac and Linux), that the owner pushes the
version tag, and that the owner creates the Scoop bucket, empty.

**Governs:** `.github/workflows/release.yml`, `.github/rulesets.json`. A pull request that changes it changes this record too, or says in its
description why it does not (`docs/adr/README.md`).

## Context

Until 12 October 2026 `sv` had never been published as a program: the repository's releases were v1's paper tags, with
no files. Mac and Linux install it through Homebrew, which builds it from source, and anyone with Docker runs the
container image, which is signed (ADR-080). Windows had neither: `sv` has been built and tested there nightly since
10 October (`windows.yml`), but there was no program to download, so a Scoop install had nothing to fetch.

## Decision

**A release workflow, run by a tag.** When a tag `v*` is pushed, a Windows runner builds `sv` with `--release`, and
the job fails unless the tag is `v` and the version in `Cargo.toml`. The program, its `data/` folder beside it (where
`sv` looks first after `SV_DATA_DIR`, ADR-036), and the licence are zipped as `sv-VERSION-windows-x86_64.zip`. The zip
is unzipped elsewhere and run with the checkout's own data moved away, so the check is of the data inside the zip: it
must report its version and read an example app. Then it is signed where it was built, with the same `actions/attest`
step the image's publishing uses (anyone can check it with `gh attestation verify`), and attached, with its SHA-256,
to a GitHub Release of the tag.

**The owner pushes the tag.** A release is public and permanent, so the moment is the owner's; no session pushes a
version tag.

**Tried without publishing.** Run by hand, or on a pull request that changes the workflow, the same steps build, zip,
and check the program, and keep the zip as the run's file for three days; nothing is signed and nothing is published.

## Alternatives considered

- **Windows, Mac, and Linux in each release**: the owner chose Windows alone, since Homebrew and the container cover
  the other two.
- **A release on every merge to `main`**: every merge would be a published version, with nothing to tell the owner's
  releases from a session's.
- **winget**, beside or instead of Scoop: it takes a pull request to Microsoft's own repository for each version,
  reviewed by people there; Scoop reads a bucket the owner controls. winget stays possible later, from the same
  release.

## Consequences

- A Windows user can install `sv` once the bucket's manifest points at a release (backlog 0120 step 2), and the guide
  gains its Windows section (step 3).
- The job holds `contents: write`, to make the release, and the signing permissions, only in this workflow and only for
  this job; the token is not left in the checked-out folder.
- A new version is a tag the owner pushes after the version in `Cargo.toml` is raised.

## Later, 12 October 2026: the first release, the bucket, and a second name

The owner pushed `v0.1.0` that evening; the release carries `sv-0.1.0-windows-x86_64.zip` and its SHA-256, and the
zip downloaded on a Mac matched it. The owner made the bucket as `abbyshade111/scoop-stack-vet` (the name Scoop is
given does not need to match the Homebrew tap's), holding `bucket/sv.json` (the zip's address, its hash, and
`checkver` and `autoupdate` from this repository's latest release) and a workflow that, on a Windows runner, installs
`sv` from that manifest, checks an example app with it, runs Scoop's `checkver` on it, and adds the bucket by its
public address, on every change and weekly. It passed on the fifth run; the first four found that Scoop adds a bucket
only from a git address, and that **in PowerShell `sv` is its own alias for `Set-Variable`**, so `sv --version` there
printed nothing and ran nothing of StackVet's. Asked, the owner chose to install the program under a second name as
well, `stackvet`, which PowerShell has no alias for; `sv` stays the name everywhere else, and `sv.exe` and the Command
Prompt's `sv` work too. The guide's Windows section says to type `stackvet` in PowerShell. None of this has been tried
by hand on a person's own Windows computer.

## Later, 12 October 2026: Scoop is the Windows route, and StackVet in Docker there waits

Building the setup prompt library (backlog 0370) found that the settings starting StackVet in Docker cannot be made on
Windows: `sv connect --docker` takes only a path starting with `/`, and the folder is shown inside the box at its own
path, which a Windows path cannot be. Asked, the owner chose to keep the Windows route this record set up, StackVet
installed with Scoop and connected with `stackvet connect TOOL`, and to leave StackVet in Docker on Windows for later
(backlog 0375). The setup prompts and the guide's step 3 say so.

## Later, 13 October 2026: the release job runs inside an Environment that admits only tags (backlog 0422)

The deep review of 13 October (backlog 0417) read that the workflow ran on a pull request that changed it with
`contents: write` and the signing permissions, gated only by `if:` lines in the same file, so a branch with push
rights could sign and publish a release before any merge: the same shape as backlog 0289 for the image. Asked, the
owner made a GitHub Environment named `release` in the repository's settings, with one deployment rule, tags `v*`,
and no other protection, and this entry records it. The workflow is now two jobs: `windows` builds, zips, checks,
and keeps the zip, with `contents: read` and nothing else, on a tag, by hand, or on a pull request that changes the
file; `release` runs only on a tag, inside that Environment, and signs and attaches the zip `windows` checked, handed
over as an artifact (as the image's `publish` job takes the tested image). GitHub holds the Environment's rule outside
the file, so an edit to the `if:` lines by a branch no longer reaches the signing or the release. The same day the
owner made a second Environment, `publish`, for the image (ADR-051).

## Later, 14 October 2026: the checks that start the app are said to be untried on Windows, before the fact (backlog 0510)

The owner asked whether Windows users should be warned about running without the Docker fence. What this record set
up leaves the checks that start the app (`sv report --run`, the fence of ADR-019) needing Docker Desktop in
Linux-container mode on Windows, and they have never been tried there by hand; the nightly Windows run leaves the
container tests out. The report was already honest after the fact. Now the warning comes where a Windows user decides
what to expect: `sv doctor` built for Windows adds a line beside its Docker line, as *can't tell*, which counts as
nothing missing (`doctor::WINDOWS_RUN_UNTRIED`); the setup page's Windows section says the same in place of "needed
later only", its Windows prompt has the AI tool say it and not promise the full report, and prompt 6 says it first on
Windows; the guide's step 3 and section 6 say so in a few words, naming a Mac or Linux computer as the known way.
Nothing about the fence changed. When somebody tries `sv report --run` on Windows, these sentences change to what was
seen (`crates/sv-cli/tests/windows_run_untried.rs` holds them).

## Later, 26 October 2026 (the fifth weekly review)

The 12 October entry says `sv connect --docker` takes only a path starting with `/` and so cannot be used on Windows. ADR-153 (25 October 2026) built that: `check_docker_on` and `inside_path` in `crates/sv-cli/src/connect.rs` take a Windows `docker.exe` path and mount the folder under `/c/...`. "Docker on Windows for later (backlog 0375)" is done. The decision for the Windows workflow is unchanged.

## Later, 21 November 2026: the bucket and the tap protect `main` (backlog 0120)

At the owner's word, `abbyshade111/scoop-stack-vet` and `abbyshade111/homebrew-stackvet` each have a ruleset, "Protect
main", like this repository's: no deletion or force-push, changes through a pull request only, merge commits only, no
one bypassing it, and their install workflows' jobs required (`install` for the bucket; the four `install` jobs for the
tap). Auto-merge is on in both. So a manifest or formula that does not install cannot reach `main`, where Scoop and
Homebrew read it. Backlog 0120 holds the details. The release workflow is unchanged.

## Later, 21 November 2026: the bucket's and the tap's rules are written down (backlog 0690)

The "Protect main" rulesets of the previous entry are in `.github/rulesets.json`, beside this repository's, and the
weekly `.github/workflows/rulesets.yml` compares them with GitHub (ADR-051, Later, the same day). A change to either
package repository's rules, a renamed install job among them, is made in that file too.

## Later, 21 November 2026: the release carries `cv` too, in a zip of its own (backlog 0694)

ADR-157 planned "one release, two packages". At the owner's choice, the release workflow builds ConfigVet's `cv` beside
`sv` (`-p sv-cli -p cv-cli`) and zips it apart, `cv-<version>-windows-x86_64.zip` with its own copy of `data/` and the
licence, so the bucket's `cv` manifest installs `cv` alone. The zipped `cv` is checked as `sv`'s is: unzipped elsewhere
with the checkout's data moved away, it prints its version and reads a Dockerfile written for the check. A step asks
PowerShell whether it already has a command named `cv`, as it has `sv` for `Set-Variable`; if it ever does, the
workflow fails and the manifest needs another name. The release job signs both zips and attaches both with their
SHA-256. The first release to carry `cv` is v0.3.0, which the owner tags; the formula for `cv` in the tap builds
`main` until then, and the bucket's manifest waits for that release's zip.

The tap's "Protect main" ruleset requires the formula's two new jobs, `install-cv (macos-latest)` and `install-cv
(ubuntu-latest)`, beside the four `install` jobs, at the owner's word the same day; `.github/rulesets.json` says so, and
`python3 -I tools/rulesets_check.py --gh` read it matching.

## Later, 21 November 2026: the bucket and the tap take merge commits only in their settings too (backlog 0709)

Their "Protect main" rulesets already allowed merge commits only; their own settings still offered squash and rebase
merging, which the ruleset refuses but the merge button shows. At the owner's word both are turned off, and
`.github/rulesets.json` records it, compared weekly by `tools/rulesets_check.py` (ADR-051, Later, the same day).

## Later, 21 November 2026: a release only from a tag on `main` that the owner approves (backlog 0712)

The entry of 13 October says the `release` Environment's rule, tags `v*`, is held outside the workflow file, so no
branch's edit can sign or publish. The security review of 21 November (A2) corrected that: any tag `v*` enters it,
wherever the tag points, and the Environment had no reviewer. Three things now stand between a tag and a release:

- **The owner's tag ruleset, "Release tags":** on `refs/tags/v*`, creating, moving, or deleting a tag is refused to
  everyone but a repository administrator, the owner. The sessions' App cannot make a release tag, so the owner pushes
  each one. `.github/rulesets.json` records it and `tools/rulesets_check.py` holds it each week.
- **The owner as required reviewer on the `release` Environment:** the signing job waits for the owner's approval in
  GitHub's own page; administrators cannot skip it (`can_admins_bypass` is off).
- **The signing job's first step** asks GitHub whether `main` holds the tagged commit, and stops, signing and
  releasing nothing, unless GitHub says "ahead" or "identical"; a failed request stops it too. Run as the job would,
  it passed for v0.3.0's commit and stopped for a branch commit ("behind").
  `crates/sv-cli/tests/release_from_main.rs` fails when the step is missing, comes after signing, compares anything
  but the tagged commit with `main`, or lets another answer through; each of those breaks turned it red.

What it does not do: the step is in the workflow file at the tagged commit, so it holds for a tag on `main`, whose
file is the reviewed one. A tag elsewhere is kept out by the ruleset and the reviewer, and a session acting as the
owner's own account passes the ruleset as the owner would; the reviewer's approval is the owner's own act each time.

## Later, 22 November 2026 (`av`'s zip, from v0.3.1)

The release workflow builds AgentVet's `av` beside `sv` and `cv`, and gives it a zip of its own,
`av-<version>-windows-x86_64.zip`, with the data it reads, the licence, and its SHA-256, signed and attached as the
other two are (backlog 0724; ADR-159). The owner's choices, 22 November 2026, each asked with a recommendation: `av`
first ships in v0.3.1, and has its own zip as `cv` has, so a Scoop manifest installs `av` alone.

Before the zip is kept, the workflow shows on the Windows runner that the unzipped `av` starts, that its report of an
empty folder exits 2 and says what it did not look at, that its pass-through ends 0 in front of a program that only
prints (which it does only when it found the rules that cut keys in the data beside it), and that PowerShell has no
command of its own named `av`. That last run is also the first time `av proxy` is run on Windows at all: its own
tests are for Unix.

`av` is not put in the container image: it starts the tool server, which is Docker itself where `sv` runs through
Docker, reads records in the person's own folders, and takes their key's passphrase at their terminal.

Not changed: what is signed and how, the `release` Environment, and that only a tag on `main` publishes. v0.3.1 is the
owner's to tag, after the version in `Cargo.toml` says 0.3.1.
