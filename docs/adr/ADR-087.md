# ADR-087: A `creates` entry may name where its record is read back, so the owner field is tried on it

**Status:** accepted, 11 October 2026, at the owner's word ("yes to the config setting"), in the pull request that builds it
(backlog 0006, part 13(a)).

**Governs:** `crates/sv-check/src/signed_in/owner_field.rs`. The shape of a `creates` entry (`read`, `id-field`) is
recorded here too, and is in `crates/sv-manifest/src/lib.rs`, which the records on the manifest govern (ADR-015, ADR-024,
ADR-045); those are named in the pull request's description. A pull request that changes the owner-field check changes
this record too, or says in its description why it does not (`docs/adr/README.md`).

## Context

The gap analysis of 7 October 2026 (finding 13(a)) found that the owner-field check ran on `owned`'s create only. An app
that takes an owner field on another create, such as a comment, was never tried for it, and a report could still say the
check had run. `creates` entries are sent for the rate limit, but nothing could read them back, so an owner set through
them could not be seen.

## Decision

1. A `creates` entry takes two optional keys: `read`, the path where the record is read back, with `{id}` for the id the
   create answer gave (or the `Location` the answer sends, when `{id}` is left out); and `id-field`, the field of a JSON
   answer holding the id, defaulting to `id`. An entry without `read` behaves exactly as before.
2. The owner-field check (V15.3.3, High when found) runs on each entry that names `read`. It uses the steps of the check on
   `owned`: the first user creates a record through the entry and reads it back to learn its owner; the second user sends a
   control create without the owner field, then one with it set to that owner; the first user is shown each. A finding is
   made only when the first user is shown the claimed record and not the control, as for `owned`.
3. The check runs with the second user's sign-in, which the `owned` section sets up. A `creates` entry with `read` and no
   `owned` section is said to be not assessed, and the report says what to add, rather than skipped silently.

## Consequences

- An app that takes an owner from a request on any create the owner lists can now be found, not only on `owned`'s.
- An entry without `read` is still only rate-limited; the report does not claim the owner field was checked on it.
- Nothing is sent that the owner did not list. The owner-field requests are made through the same routes as the
  rate-limit requests, with the same marker and session rules.

Governs: unchanged for ADR-015, ADR-024, ADR-045, ADR-028 (see the pull request), and this record is new.
