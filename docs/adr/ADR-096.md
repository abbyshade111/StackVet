# ADR-096: The header, cookie, and content-type checks ask every route stackvet.toml names

**Status:** accepted, 11 October 2026, in the pull request that builds it. Proposed the same day in the claim of
backlog 0232, part 1 (group A). The owner's word of 10 October 2026 asked for more samples in each group ("go with
your recommendation and add to the backlog to add more checks to each of these"), and asked on 11 October that the
backlog be worked off without asking each time. Built as proposed; the one addition is below, under Decision.

**Governs:** `crates/sv-check/src/probes.rs` (the anonymous requests, which answers each header check judges, and
when its credit is whole) and `crates/sv-cli/src/lib.rs` (the one list of anonymous requests a run makes). A pull
request that changes these changes this record too, or says in its description why it does not
(`docs/adr/README.md`).

## Context

ADR-053 (Later, 10 October 2026) marked as *checked in part* every running check that credits a requirement from one
sample where the requirement names more. Group A of that inventory is the header, cookie, and content-type checks
read from the app's anonymous answers: `probe.security-headers` (V3.4.3 to V3.4.6), `probe.cookie-attributes`
(V3.3.2, V3.3.4), `probe.content-type` (V4.1.1), `probe.opener-policy-missing` (V3.4.8), and `probe.csp-no-report`
(V3.4.7). Each reads one to three answers: the health path, the root page, and the answer for a missing page. Their
requirements name more: V3.4.4 and V3.4.6 "all" and "every" HTTP response, V4.1.1 every response with a message
body, V3.4.8 all responses that render a document, and V3.3.2 and V3.3.4 each cookie.

## Decision

- **More answers.** The anonymous probes also send one GET, with no session, to each distinct path stackvet.toml
  names under `[stack.run.users]` (sign-in, sign-up, sign-out, the private and admin pages, the password and email
  changes, account deletion, the upload route, and the owned-record paths), leaving out a path with a placeholder in
  it and the health path and root, which are already asked.
- **Judged whatever the status.** Each check reads those answers as well, whatever their status: a redirect to the
  sign-in page, a refusal, and a method not allowed are HTTP responses as much as a page is, and V3.4.4 and V3.4.6 say
  every one. Each check keeps its own scope within them: content type only on answers with a body, the opener policy
  only on answers that are HTML documents, the CSP's reporting only where there is a policy, and cookies only where
  one is set. A finding names each route that fell short.
- **When the credit is whole.** Plain *checked* only when stackvet.toml names at least one such route, every one of
  them answered, and every answer judged passed. Otherwise the credit stays *checked in part*, as now. The credit says
  how many answers it read and which routes.
- **The CSP's reporting, on every policy.** `probe.csp-no-report` read only the health path's policy; it now reads
  the policy on each named route's answer too, and a finding names each answer whose policy reports nowhere. Its
  credit still needs a policy on the health path to read.
- **Not in this part.** The error-page check (`probe.error-detail-leak`) stays in part: it provokes one kind of error,
  and more kinds are a different change. Requests as a signed-in user (group B) and every page the app has, beyond
  what stackvet.toml names, are not asked.

## Alternatives considered

- **Judge only the routes that answered with a page (2xx).** Fewer findings about redirects and refusals, but V3.4.4
  and V3.4.6 name every response, and a check that skipped most of them would not speak for "every".
- **Crawl the app's links for more pages.** Closer to "every page", but what a crawl reaches varies run to run, a
  crawl's own requests are harder to keep within the fence's limits, and the owner's list is what the rest of `sv`
  holds to.

## Consequences

- An app whose sign-in page or private-page redirect lacks a header now has a finding naming that route, where before
  it could be credited in part from its home page alone.
- An app whose named routes all answer with the headers is *checked* on these requirements, not in part.
- A run makes a few more anonymous requests, one per named route; the count of unanswered questions includes them.

## Later, 14 October 2026: the reporting credit needs a policy on every named route (backlog 0419)

V3.4.7 asks that the Content-Security-Policy say where to report what it blocks. The reporting credit read only the
answers that carry a policy, and was whole "on all N routes" when every named route answered, whatever it carried, so a
named route with no policy at all was left out of the reading and the credit stayed whole. For this credit, every route
now means every named route answered with a policy: when one answered without, the credit is in part and its words name
only the health path. The missing policy is still the security-headers finding, and the credit still needs the health
path's policy.
