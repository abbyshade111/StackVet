# ADR-092: A note lists the commits an AI coding tool made straight onto the default branch

**Status:** accepted, 11 October 2026, at the owner's word ("agree with all three", then "yes, build it that way"), in the
pull request that builds it. Proposed the same day in backlog 0258, after the Cursor build pushed to `main` directly four
times, twice after the owner had turned on a rule requiring pull requests (design entry 0368).

**Governs:** `crates/sv-check/src/git.rs` (the reader of the default branch's commits, and the trailers it reads; git runs
through it, with the overrides of ADR-032), and `crates/sv-check/src/config.rs` (the note named config.ai-commits-off-merge).
A pull request that changes these changes this record too, or says in its description why it does not
(`docs/adr/README.md`).

## Context

Pull requests are the only way a change reaches `main` that another person looks at, and a rule can require them. In the
Cursor build the tool pushed to `main` directly, and the owner found the bypass only by looking. `sv` saw none of it: its
build-loop record holds only the calls the tool makes to `sv`, and `sv` opens no network connection, so it cannot read
branch protection or rulesets. What `sv` can read is the repository's own history, with git and no network.

## Decision

- **The note reads the default branch's own line of commits.** `main`, else `master`, else HEAD, with `git log
  --first-parent --no-merges`. A merged change came in through a pull request, and is not read. A commit on a branch
  `main` never took is not read.
- **A commit counts when a trailer says an AI coding tool made it.** An `Assisted-by:` line counts whatever it names, since
  the repository's rules ask for that line from any tool. A `Co-Authored-By:` line counts when its name is one of a short
  list of AI tools (Claude, Anthropic, Cursor, Copilot, Codex, Gemini, ChatGPT, OpenAI, Aider, Windsurf, Muse Spark, Devin).
  A person named in `Co-Authored-By:` does not count. The list is a heuristic, and grows by a dated entry here when a new
  tool is seen.
- **The result is an `Info` note, never a failure and never a credit.** It names how many commits were found, up to ten
  with their hashes, tools and subjects. When there are none it says so. It cites no requirement, so it is not in the
  credit list the suite checks.
- **Its limits are stated in the note.** It sees only what a commit says about itself. A commit that names no tool is not
  seen, and whether a hosting rule held is in the hosting service's settings, which `sv` does not read.
- **Not assessed, not passed, when git cannot say** (no repository, or git cannot read the history).

## Alternatives considered

- **A list of tool names alone.** Misses any tool not on the list, and the owner asked that it catch any AI tool.
- **Reading GitHub's rulesets and branch protection.** The most direct answer, but it needs the network, which `sv` does
  not open (CLAUDE.md), and a token. Declined for now; the owner can revisit it.
- **Flagging every commit on `main` that is not a merge.** The owner's own commits from before the pull-request rule would
  all be flagged, which is the noise problem again. The trailer is what tells an AI-made change apart.
- **A needs-attention finding.** It would fail a report on a fact the owner may already have accepted. A note leaves the
  decision with the owner.

## Consequences

- The note appears in every report of a repository that has an AI-attributed commit on its default branch. It does not
  change the report's status or its count of findings that need attention.
- The repository's own rules ask for the trailer (`CLAUDE.md`), so commits made under those rules are read.

## Later, 12 October 2026: a commit's message cannot forge or hide a record (backlog 0313)

The reader asked `git log` for each commit's hash, subject, and message in one stream, split on two separator
characters. A message may hold those characters itself, so a person's commit could add a record with a made-up hash
and subject naming a tool, or carry a separator before its own trailer and drop out of the note. Now the commits'
real hashes are read first, one to a line, and each commit's message is found in the stream by a marker its real hash
makes, looked for from the end: a message cannot hold its own commit's hash, and an older message cannot hold a newer
commit's, so the last marker for each commit is its real one. A record is kept only for a real hash, and the subject
is read from the message's first paragraph, as git's own subject is, rather than from a field a separator could move.
Held by `crates/sv-check/src/git_separator_tests.rs`.
