# ADR-125: Ending sessions is tried from the manifest: a user ends their others, and an admin ends a user's

**Status:** accepted, 16 October 2026, in the pull request that builds it (backlog 0492, its running-app half). The
proposal is the deep review's of 13 October 2026 (backlog 0417), released for building by the orchestrating session
with the pointer proposals on 14 October, and assigned to session honesty on 15 October. Written by session honesty.

**Governs:** `crates/sv-check/src/signed_in/sessions_end.rs`, the end_other_sessions and admin_end_sessions fields of
`crates/sv-manifest/src/lib.rs::UsersSection`, and their lines in `crates/sv-manifest/src/spec.rs`. A pull request
that changes what these checks send, what they credit, or what they cite, changes this record too, or says in its
description why it does not (`docs/adr/README.md`).

## Context

V7.5.2 (L2) asks that users can view and, having authenticated again, end any or all of their active sessions. V7.4.5
(L2) asks that administrators can end the active sessions of one user or of all users. Neither had a check, and no
code read can show either: whether a session is really ended is seen only by trying it.

## Decision

- **Two optional entries in `[stack.run.users]`.** `end-other-sessions`: the request a signed-in person sends to end
  their other sessions, with `{password}` for the password asked again. `admin-end-sessions`: the request an admin sends
  to end a user's sessions, with `{user}` for the user's address; it needs `seed` and `admin`, as the admin pages do.
- **When.** Both end the first user's sessions, so they run after every check that uses that session, and before the
  password change, which may change the first user's own password when the manifest has no `signup`.
- **V7.5.2.** The first user signs in twice, and each session must open the first private page. From the first, the
  request is sent with a wrong password; if the second session is then refused, that is a finding: other sessions can
  be ended without the password. Then with the right password: the second session must be refused and the first still
  open. Left working is a finding. A request with no `{password}` that ends the other session is a low finding: the
  password is not asked again. Refused with the right password, or answered by a crash, is not judged either way. The
  credit is in part: one other session, and viewing the sessions is not tried.
- **V7.4.5.** The first user signs in afresh, the admin sends the request, and the first user's session must then be
  refused. Left working is a finding. The credit is in part: one user's one session, and every user's is not tried.
- **V7.1.2** asks the documentation how many sessions one account may have. The run says, as a step, that the first
  user's two sessions both stayed valid, which is a design choice and neither a finding nor a credit.
- **A crash is not a session ended.** Every credit and finding that rests on a session being refused is listed in the
  run's tables of what rests on a refusal (ADR-021), and the crash guard's scenarios include both checks.

## Consequences

- Two requirements with no check now have one, at `sv`'s own tier and in part.
- The code-read half of backlog 0492, V7.1.1's session timeout read from the code, is backlog 0612.
- Held by `crates/sv-check/src/signed_in/sessions_end_tests.rs` and the crash guard's scenarios in
  `crates/sv-check/src/signed_in/mod.rs`.
