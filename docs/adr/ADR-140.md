# ADR-140: The bill of materials leaves out lockfiles in test code and in folders named as not the app

**Status:** accepted, 23 October 2026, in the pull request that builds it; proposed the same day with the claim for
backlog 0656, at the owner's answer of that day to backlog 0647's choices: "SBOM skips test lockfiles".

**Governs:** `crates/sv-check/src/sbom.rs::build_app_in`, `crates/sv-check/src/sbom.rs::what_was_read`,
`crates/sv-cli/src/static_scan.rs::inventory`, where the report and sv sbom read it (`crates/sv-cli/src/assemble.rs`,
`crates/sv-cli/src/main.rs::cmd_sbom`), and their tests
(`crates/sv-check/src/sbom/left_out_tests.rs`). A pull request that changes which lockfiles and manifests the bill of
materials reads changes this record too, or says in its description why it does not (`docs/adr/README.md`).

## Context

The bill of materials reads every lockfile and manifest in the app's folder (ADR-037 for Python). StackVet's report on
itself said its list was not complete (`sbom.incomplete`) because it read the sample lockfiles under
`crates/sv-scan/tests/fixtures` as what StackVet ships. A test fixture's lockfile is not what the app installs.

## Decision

- **Lockfiles and manifests in test code** (ADR-139's reading) **and in folders named as not the app**
  (`[repository] not-the-app`) are left out of the bill of materials.
- **It says so:** what the bill of materials says it read names how many were left out and why, as it already names
  what it could not read.
- **A lockfile left out never makes the list complete on its own account,** and an app whose only lockfile is in such
  a folder is said to have none read.

## Where the build differs

- **Two lists, not one.** The known-vulnerability checks read every lockfile in the folder (`build_in`, as before), so
  a vulnerable package in a sample or a fixture is still found and listed apart: "naming a folder never hides its
  vulnerability" (ADR-031). What the app ships is a second list, the inventory (`build_app_in`), with the lockfiles and
  manifests in test code (ADR-139's reading) and in the folders named as not the app left out and named. The inventory
  decides whether the list is complete (V15.1.2, the finding or the credit), and is what `sbom.cdx.json` and `sv sbom`
  publish. A first build left test code out of `build_in` itself, which every caller reads, and `sv check`'s tests of
  a set-apart folder's vulnerability went red; that is how the two lists came about.
- **Folders named as not the app** are read with the list as resolved, after the guard that refuses one which would
  set aside all the app's code (ADR-031), in the report and in `sv sbom` alike.
- **Said, not hidden:** what the inventory says it read ends with how many were left out and the first three by name,
  and `sv sbom` names them all. An app whose only lockfile is a test's has an empty inventory, which credits nothing,
  as an app with no packages has. An inventory complete because only fixtures were unread is complete: a fixture's
  packages are not what the app installs.
- **Held by** `crates/sv-check/src/sbom/left_out_tests.rs`: with test code read into the inventory, the fixture test and
  the empty-list test fail; with the listing not split, the not-the-app test fails; and the whole list must still hold
  a fixture's packages.
