# ADR-146: The TURN relay's own settings file is read, and a relay that refuses internal addresses is credited in part

**Status:** proposed, 24 October 2026, with the claim for backlog 0625's third part; accepted in the pull request
that builds it.

**Governs:** the TURN check (which settings are read, from which files, and what each concludes), a module of
`sv-check` that the pull request accepting this record names by its path, and its tests, and the TURN checks' entries
in `tools/coverage.py`. A pull request that changes which ranges must be
refused, which quotas count, or what a clean result credits, changes this record too, or says in its description why
it does not (`docs/adr/README.md`).

## Context

V17.1.1 (level 2) asks that a TURN relay, which carries a call's media through when two people cannot reach each
other directly, lets people reach only addresses that are not reserved for special purposes: no internal networks,
broadcast, or loopback. A relay that does is a way into the network it sits in. V17.1.2 (level 3) asks that it cannot
be worn out by a user opening many ports. Nothing in `sv` spoke to either. The most used relay is coturn, set up by
a `turnserver.conf` file or by the same settings given as flags to its container. Its own example configuration
(`examples/etc/turnserver.conf`, read 24 October 2026) says: `denied-peer-ip` takes an address or a range, and an
address both denied and allowed is allowed; `no-multicast-peers` refuses broadcast addresses (224.0.0.0 and above,
and FFXX); loopback peers need `allow-loopback-peers`, which replaced `no-loopback-peers`, to be let through;
`user-quota` and `total-quota` default to 0, no limit; and private ranges are not mentioned, so nothing refuses them
unless the file does.

## Decision

- **What is read:** every `turnserver.conf` in the app's folder, and a compose file's service whose image is coturn,
  its `command` flags (`--denied-peer-ip=…`, `--no-multicast-peers`). Nothing is run, and nothing is asked of a running
  relay.
- **V17.1.1, credited in part when the settings refuse every reserved range:** `denied-peer-ip` covering 0.0.0.0/8,
  10.0.0.0/8, 100.64.0.0/10, 169.254.0.0/16, 172.16.0.0/12, and 192.168.0.0/16, and IPv6's fc00::/7 and fe80::/10;
  `no-multicast-peers` set; and `allow-loopback-peers` not set. An `allowed-peer-ip` inside one of those ranges undoes
  it, since coturn lets allowed win. Any of these missing is a finding that names what is missing. The credit says it
  read the file, not the running relay, and that coturn older than 4.5.2 let loopback through by default.
- **V17.1.2, credited in part when `user-quota` and `total-quota` are both set above 0;** either unset or 0 is a
  finding. It stays a level-3 requirement, so it is in a report only for an app held to level 3.
- **No file, no word:** a hosted TURN service, or none, leaves both requirements not verified, never credited, and the
  check says nothing; V17 applies only to apps with WebRTC already (the `webrtc` condition).

## Alternatives considered

- **Probe the running relay.** Rejected: it would need `sv` to run the relay and send it TURN traffic, which it does not
  do, and a relay in the repository is often only for development.
- **Find only, never credit.** Rejected: the file is what decides a self-hosted coturn's behavior, and reading every
  range it must refuse is real evidence about the relay the app ships, in part.

## Consequences

- An app that ships a coturn configuration letting people reach its private network is told which ranges to refuse.
- One that refuses them all is credited in part with V17.1.1, which before had no check; the report says what was read.
