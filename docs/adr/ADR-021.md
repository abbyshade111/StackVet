# ADR-021: A crash's or a rate limiter's answer is never read as the app refusing

**Status:** accepted. Built from 28 to 29 September 2026 in four pull requests (#412, #416, #418, #420), and written
down here on 4 October 2026, because the first weekly review of the decision records found it had no record
(BACKLOG, "Records owed", item 1). Its reasons are in DESIGN, "A rate limiter's answer is not the app's" and "A crash
is not a refusal", each with a later part.

**Governs:** `crates/sv-check/src/signed_in/mod.rs`, `crates/sv-check/src/signed_in/cookies.rs`, `crates/sv-check/src/signed_in/form_tokens.rs`, `crates/sv-check/src/signed_in/requests.rs`, `crates/sv-check/src/signed_in/answers.rs`, `crates/sv-check/src/signed_in/patient.rs`, `crates/sv-check/src/signed_in/signin.rs`,
`crates/sv-check/src/signed_in/codes.rs`, `crates/sv-check/src/signed_in/once.rs`, and since 8 October 2026
`crates/sv-check/src/script.rs`, `crates/sv-check/src/signed_in/mod.rs::RESTS_ON_A_REFUSAL`, and since 14 October 2026
`crates/sv-check/src/signed_in/limit.rs`, `crates/sv-check/src/signed_in/forgery.rs`. A pull request that changes any of
these changes this record too, or says in its description why it does not (`docs/adr/README.md`).

## Context

Many of `sv`'s checks on the running app give credit because the app said no: a private page refused to a stranger, a
signed-out session refused, another user's record refused. When these were written, any answer that was not a
success counted as that no.

Two kinds of answer are not the app saying no. A rate limiter's answer (HTTP 429, or a 503 that says when to come
back) means the request was stopped before it reached the check it was asking about. A crash (any other 5xx), or no
answer at all, means the app failed; it says nothing about whether the app would have let the request through. Read as
refusals, both turned into passes the app never earned.

It was found from a report by an agent in another project that was integrating `sv`: a critical finding it listed as
"F-0001" had got a 429 from the app's rate limiter. That report never reached this repository, and the owner closed
F-0001 without it on 30 September 2026. Looking for it turned up the opposite fault, a false pass:
`probe.private-page-anonymous` credited V8.2.1 ("refused to somebody not signed in") when the limiter had answered and
the page's own check never ran.

## Decision

Every request the signed-in checks send, and since 29 September the anonymous ones too, goes through one place
(`Patient` in `crates/sv-check/src/signed_in/patient.rs`; `ask_anonymously` for the anonymous probes), and that place
decides what the answer was.

- **A rate limiter is waited out once.** A 429, or a 503 with `Retry-After`, is the limiter (`rate_limited`). The
  request is sent again after the app's `Retry-After`, capped at 60 seconds, or after 5 when it gives none. All the
  waiting in one run is capped at 300 seconds (`MOST_WAITING`). Checks that want to see the limiter, such as those
  that guess passwords or send bursts, are not waited for.
- **A limiter that keeps answering credits nothing in the run.** Every pass in the run becomes not assessed, with
  advice to run again with the limiter relaxed or a longer wait. It is deliberately coarse, since no record says which
  conclusion rests on which request. Findings are kept, with a note that they may rest on the limiter: hiding a real
  finding is the worse fault.
- **A crash withholds only what rests on it.** A 5xx other than the limiter's, or a request with no answer, is recorded
  as a crash. A pass or a finding that rests on a request that crashed becomes not assessed, naming the requests and
  saying "Fix the error, and run it again." The others stand, because a crash is the app's answer to one request and
  says nothing of the rest. Which pass rests on which request is a table: `RESTS_ON_A_REFUSAL` for passes (29 rows when
  it was written, 36 on 4 October 2026) and `RAISED_ON_A_REFUSAL` for findings raised from a refusal.
- **An anonymous answer still from the limiter is left out** of what the probes read, and the report lists it as a
  gap.

## Alternatives considered

- **Fixing each check where it reads its answer.** Set aside: the same reading was in about thirty places, and "the
  fix is where every request passes, not at the thirty places".
- **The crash rule as broad as the limiter's.** Set aside on purpose: a limiter that keeps answering puts every request
  in doubt, a crash only the one it answered.
- Two sessions built the limiter rule in parallel (#411 and #412). The owner merged #412; the five-minute cap from
  the other was carried into #416.

## Consequences

- **Undoing it quietly brings back passes that rest on an answer the app never gave**: 29 when this was built, 36
  by the table today, each crediting a requirement because something was refused.
- A run behind a rate limiter takes longer: up to a minute per limited request, five minutes in all.
- An app that crashes, or whose limiter will not let up, gets not assessed where it once got a pass, with the reason.
  That is the intended cost.
- Not tested end to end against a real app behind a real limiter; the tests use the fake app's switches. The checks
  of the sign-in provider (`oidc.rs`) and of the app's own MCP server were not looked at for the limiter reading.

## Later, 5 October 2026: a delay counts as pushing back only when every attempt past the limit shows it

The password-guessing (V6.3.1) and code-guessing (V6.6.3) checks also count an attempt past the stated limit that
took markedly longer as the app pushing back. Until the deep review's H16 that was one time against one: the last
attempt against the first, each including the time `docker exec` takes to start the request, so one slow start
credited a limiter that was not there, and a slow first answer hid one that was. Built by session securevibe-e9 at
the owner's asking, in branch `claude/securevibe-e9-h16`.

- **The baseline is the quickest attempt within the limit,** since the container's time only ever adds.
- **Two attempts are made past the limit, and both must be markedly slower** (four times as long, and at least
  900ms longer). For passwords, the sign-in page fetched beside each must not be as slow, since no limit on wrong
  passwords slows it.
- **One slow and one not, or a slow page beside them, is not assessed, never a pass or a finding,** with the times.
  A different answer, or a refusal, still settles it as before.
- **Each check now makes the number allowed plus two attempts**, and the most it will make is 26.

Held by `a_delay_counts_only_when_every_attempt_past_the_limit_shows_it`,
`an_app_that_slows_every_attempt_past_the_limit_is_credited_and_one_slow_attempt_is_not`
(`crates/sv-check/src/signed_in/signin.rs`), and
`a_code_guessing_delay_counts_only_when_both_codes_past_the_limit_show_it` (`crates/sv-check/src/signed_in/codes.rs`).
The time is still measured from outside the container; timing the request inside it would take the container out
of the number altogether, and is not done.

## Later, 5 October 2026: nor is a refusal to somebody signed out, or without the page's token

`probe.action-done-twice` now sends its copies as two users (DESIGN, "Later, 5 October 2026: two users, not one"), and
credits the action when one user's copies go through and every copy from the other is refused. The crash sweep found
that a second user whose sign-in or token had silently failed was refused for that, and the refusal credited. The same
rule as this record's, one step further: a refusal counts only from somebody shown signed in, holding the token the
request asks for, and still signed in afterwards. Otherwise the check is not assessed, saying which was missing.

## Later, 5 October 2026: a sign-in the limiter refuses is named, and the credits stay withheld

When the limiter is still answering a request to the sign-in path after the wait, `Patient` notes it as a refused
sign-in, and the run adds one gap naming those sign-ins: the limit working, not the app failing the checks or
securevibe.toml being wrong, with what to change. A first user's sign-in refused this way no longer reads as a mistake
in securevibe.toml. This record's rule is unchanged: every credit is still withheld while the limiter answers
anything, because a refused sign-in can look exactly like a refusal a check is waiting for. DESIGN, "Later, 5 October
2026: a sign-in the app's limit refuses is named, and the spec says how many there are".

## Later, 7 October 2026: a page shell is neither the private page served nor refused

From the gap analysis (`docs/GAP-ANALYSIS.md`, 2.2; BACKLOG, item 8). A single-page app, the kind a React or Vite
build makes, sends everybody the same page for every address and draws it in the browser from what it fetches next.
So `/account` answered a stranger 200, and `probe.private-page-anonymous` reported a private page served to anyone,
high, when nothing private had been sent. Every check that needed the signed-in control then read "not assessed".

The same question as this record's: which answers are the app's answer to the question asked. Before the private
pages are asked, the front page (`/`) is asked once, as nobody. A private page whose answer to nobody is a success
with exactly the front page's body, short enough to have been kept whole (under `sv_check::probes::KEPT_CHARS`), is
the page shell: it is not judged, and every check after this one is given the private pages that are left. A body as
long as the kept part is never taken for a shell, because a server-rendered page may only begin as the front page does.

When every private page is a shell, V8.2.1 is not assessed, saying which pages and to list the addresses the page
fetches (`/api/me`) under `private` instead; the spec says the same. When some are left, the credit names the shells
as not judged. A finding is never turned into a credit by this: a shell is set aside, not counted as refused.
`crates/sv-check/src/signed_in/requests.rs` (`is_page_shell`) and `crates/sv-check/src/signed_in/page_shell_tests.rs`; DESIGN, "A single-page app's page shell
is not its private page".

## Later, 7 October 2026: a request sent as another site carries no `Authorization` header

From the gap analysis (`docs/GAP-ANALYSIS.md`, 2.1; BACKLOG, item 7). The two requests `sv` sends as another site would
(`probe.cross-site-request-accepted`, V3.5.1, and `probe.preflight-skipped`, V3.5.2) were built from the signed-in
session, and for an app signed in by a token that kept `Authorization: Bearer …`. A browser never adds that header to a
request another site makes, so an API that keeps its token in the page and takes any Origin was reported high for a
request no other site could send.

Which answers are the app's answer to the question asked: the question is "would the app take this from another site",
and only what a browser would carry can answer it. Both requests now go with the session's cookies and without the
`Authorization` header.

- **A token and no cookie.** Nothing a browser would carry signs anybody in, so neither request is sent: both
  requirements are not assessed, saying so. Whether the app also takes a cookie as a session is not something the run
  saw.
- **A token and a cookie.** Taken with the cookies alone is a finding, as before: the cookie signs the person in from
  any site. Refused is no longer credited, because with the token left off a refusal may only mean the cookies sign
  nobody in; it is not assessed, saying why.
- **A cookie and no token.** Unchanged.

So a credit for V3.5.1 or V3.5.2 now needs a session a browser would send from another site.
`crates/sv-check/src/signed_in/forgery.rs` (`as_another_site_sends`); DESIGN, "A request from another site carries no
`Authorization` header".

## Later, 8 October 2026: one rule for what an answer is, and every suite waits the limiter out

The architecture assessment of 8 October 2026 (BACKLOG, "From the architecture assessment of 8 October 2026", item 6)
found the rule this record states written in seven places with three definitions: `Patient` (which also recorded
crashes), the session check without sign-in cookies, the fetch suite, the burst check (with its own copy of what a
limiter's answer looks like), the one-at-a-time check (which counted a limiter's 503 as a crash and only a 429 as the
limiter's), the AI suite's bad-answer check, and the MCP suite's verdict, which read 429 as the limiter's and missed
the 503 with `Retry-After`. And the OIDC, MCP, and fetch suites took the app's answers as they came: a limiter's 429
on an MCP request was "not an answer", correctly, but the request was never sent again after the wait, so a limiter
that answered once cost the suite its whole question.

Now the rule is one function, `answer_of` (`crates/sv-check/src/signed_in/answers.rs`): an answer is the app's own
(`Answered`), or nothing came back (`Silent`, which a status of 0 also is), or the app crashed (`Crashed`, a 5xx that
is not the limiter's), or a rate limiter answered in its place (`Limited`: 429, or 503 with `Retry-After`, with the
seconds it asks). The seven places read it; the one-at-a-time check now counts a limiter's 503 as the limiter's, and
the MCP suite's verdict now reads a limiter's 503 as not an answer, which are the two readings that changed. The OIDC,
MCP, and fetch suites go through `Patient` as the signed-in suites do (the run's script, `crates/sv-check/src/script.rs`):
a limiter's answer is waited out once and the request sent again, a limiter that keeps answering is said, every credit
behind it is withheld, and what rests on a crash is withheld, exactly as this record has it for the signed-in suites.
The AI suite is not wrapped: it waits a limiter out itself at the two places an answer matters, and its rate check
(C11.2.2) sets out to make the app refuse, which a wait and a second try would unmake. The waiting is one budget for the
run, `MOST_WAITING` (300 seconds), shared by every suite, where each suite had its own; a run can no longer wait five
minutes in each of five suites, and the sidecar's life is built from the same number (ADR-025, Later, 8 October 2026).

Held by `one_rule_says_what_an_answer_is` (`crates/sv-check/src/signed_in/mod.rs`),
`the_mcp_suite_waits_a_limiter_out_once_and_says_when_it_kept_answering` and
`the_run_waits_for_a_limiter_at_most_once_over_all_its_suites` (`crates/sv-check/src/script.rs`). **Governs** gains
`crates/sv-check/src/script.rs`, where the suites are given the wait.

## Later, 14 October 2026 (backlog 0423): one reading past the limit, and one meaning of "refused outright"

The wrong-password check (V6.3.1, `signin.rs`) and the wrong-code check (V6.6.3, `codes.rs`) now read their answers
past the limit through one function, `past_the_limit` in `crates/sv-check/src/signed_in/limit.rs`. A crash or no

## Later, 14 October 2026 (backlog 0384): a made-up name answered alike is not assessed, not a finding

With no `signup` in stackvet.toml, the wrong-password check (V6.3.1) makes its wrong guesses against a user name no
account has, so as not to lock out the accounts the other checks use. An app that counts wrong passwords on each real
account, the usual design, never locks a name that has no account. So when the app answered that name alike every time,
the check used to report "Wrong passwords can be tried without limit" against apps that lock real accounts exactly as
stated; the second loop trial found one (`haiku-a-1`). That case is now not assessed, and the report says to add
`signup` so the check can make an account of its own to try. Nothing else changes: a made-up name the app pushes back
on still counts (whatever the limit counts by, it refused past the stated number), the one-more-let-through finding
still stands, and with `signup` an app that answers alike every time is still found. The fake app's
flaw that locks only accounts that exist is the witness
(`crates/sv-check/src/signed_in/signin/made_up_name_tests.rs`).

## Later, 15 October 2026: after the push-back, the right password (backlog 0524, 0561, ADR-119)

Where the wrong-password check (V6.3.1) saw the app push back with a different answer (a refusal or another status,
not a delay), it now sends the account's own password once, straight after, under a `guess-` id since it belongs to
the guessing. If that signs in and opens the first private page, the limit refuses only wrong passwords: guessing
goes on at full speed and the right guess gets in. That is a finding ("After the limit, the right password still
signs in", high) and nothing is credited. If it is refused too, the credit stands, in part as before, and says so. A
limit that only slows attempts down is not asked, since the right password getting in there is how it should work.
The fake app's lockout that checks the password first is the witness
(`crates/sv-check/src/signed_in/signin/right_after_limit_tests.rs`).

## Later, 15 October 2026: after the code limit, the right code (backlog 0561, ADR-119)

The wrong-code check (V6.6.3, `codes.rs`) already sent the right code after the wrong ones, but credited a limit that
answered the wrong ones differently even when the right code then signed in. That limit refuses only wrong codes, so
it is now the finding "After the limit, the right emailed code still signs in" (high), and nothing is credited, as
for passwords above. A limit that only slows the guesses down is read as before. The fake app's code limit that checks
the code first is the witness (`crates/sv-check/src/signed_in/codes/right_after_limit_tests.rs`).

**15 October 2026: the once check's solo tries, and `once.reset` (backlog 0574, the owner's answer (a)).** `once` takes
an optional `reset`, a request that puts the one thing back when the user holding it sends it (cancelling the
booking, say). With it, before the race, each user sends the action alone and then `reset`: a user refused alone may
not do it at all, so the race is not judged and says so; a `reset` not accepted leaves the race unjudged too. Without
it, the race is judged as before, and the credit, still in part, says neither user was shown able to take it alone.
This changes what the credit for V2.3.4 says and adds a key a builder may write; the spec says what it is for.

## Later, 15 October 2026: an answer shorter than its `Content-Length` is no answer (backlog 0598)

In the clean Cursor + Flash run of 15 October 2026 the sign-in and sign-up pages answered 200 with a `Content-Length`
of over 5,000 bytes and no body at all: the app's handlers rendered twice, and uvicorn, finding the body longer than
the length it had already sent, failed with "Response content longer than Content-Length". A browser showed the pages
blank. The run read the status and headers as an answer, said the app "answered 68 of 68", and turned the blank pages
into findings about what they lacked, among them "no sign-out link".

What counts as the app answering now includes its body: an answer that came with fewer bytes of body than its
`Content-Length` said is read where it arrives (`sv-run`'s transport, all three ways a request is sent) as no answer,
one of the things this record says is not an answer, so every check treats it as it treats silence and none judges
the blank page. An answer that has no body by HTTP's rules is never held to its length: one to `HEAD`, and 1xx, 204,
and 304. The run writes each down as "id (status, N of M bytes)", reads the first line of the app's output that
speaks of a `Content-Length` before its container goes, and says them once, as one gap with that line, redacted,
beside them. They leave the count of answers ("answered 63 of 68"). An empty body with a `Content-Length` of 0, or a
body with no length said, is an answer as before: nothing says it was cut.

## Later, 15 October 2026: a crash on an ordinary sign-up is a finding of its own (backlog 0528)

A crash is still not an answer: what it would have answered stays withheld, as above. But a server error on a request
a person could make is itself a weakness (CWE-755), and the three-tool trial of 14 October 2026 set one aside with no
word of it: a 73-character password crashed a sign-up whose password library refused anything over 72.

- **Which requests.** `sv`'s sign-ups with ordinary values only: the two test users, the control account, and the
  long password (`ORDINARY_SIGNUPS`). Not the probes that send something odd on purpose, where a crash may be the
  probe's own doing.
- **What it says.** One low finding, `probe.crashed-on-ordinary-request`, under V16.5.3 ("fails gracefully and
  securely, including when an exception occurs"). It names each request and its status, and its fields by name and
  length, never a value.
- **What it is not.** A finding only: a sign-up that did not crash shows nothing about every other request, so it is
  never a credit.
