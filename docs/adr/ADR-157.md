# ADR-157: ConfigVet, a companion for deployment configuration on `sv`'s engine, with a binary of its own and read-only access to live hosting accounts that `sv` never gains

**Status:** accepted, 20 November 2026, in the pull request that built its first part (backlog 0686, decision 2);
proposed the same day. Asked for by the owner on 20 November 2026. They chose a shared engine with a command of its
own, named ops and DevSecOps engineers as its readers, and asked that it read live hosting accounts through their APIs.
Only decision 2 is built; the rest is the plan, and "As built", below, grows with each part. The design is the design
entry "ConfigVet, a companion for an app's deployment configuration (20 November 2026)"
(`docs/design/0396-configvet-a-companion-for-an-app-s-deployment-configuration.md`).

**Governs:** the design entry above; the network fence, drawn and listed in `docs/ARCHITECTURE.md` ("The fence"), which
this record leaves unchanged for sv; what the shared crate depends on (`crates/sv-core/Cargo.toml`), which must stay
light enough for ConfigVet to build on without the checks; the YAML reader both binaries share
(`crates/sv-yaml/src/lib.rs`); and ConfigVet's crates (`crates/cv-rules/*`, `crates/cv-cli/*`), its defaults table
(`data/config-defaults.json`), its live clients (`crates/cv-live/*`), and the test that keeps them out of sv
(`crates/sv-cli/tests/cv_live_fence.rs`). A pull request that changes what ConfigVet may connect to, how it holds a
token, what a live reading is credited as, or whether sv can reach ConfigVet's live clients, changes this record too, or
says in its description why it does not (`docs/adr/README.md`).

## Context

`sv` reads an app's code and, behind its fence, the running app. Between the two is the layer that says how the app is
deployed: Dockerfiles, compose files, Kubernetes manifests, Terraform, proxies, CDNs, and the hosting accounts
themselves. `sv` reads part of it today, about forty `config.*` checks, GitHub Actions among them. But nothing in `sv`
knows a framework's or a platform's defaults, so it cannot say that a setting left out is unsafe. And `sv` opens no
network connection of its own beyond the four exceptions in "The fence", so it never sees the live accounts where an
ops engineer's real configuration is.

The owner wants that layer reviewed by a companion, ConfigVet, for ops and DevSecOps engineers, and wants it to read
live accounts. Reading a live account is the first time anything in this project would hold a credential to
production. That is why this decision needs a record before any of it is built.

## Decision

1. **One engine, one workspace, two binaries.** ConfigVet is built from crates in this workspace and ships as a
   binary of its own, `cv` (the owner's choice, 20 November 2026). It reuses the standards and applicability data
   (`sv-frameworks`), the folder walk (`sv-scan`), the finding, credit, and tier types, the outside-tool adapters (ADR-032), the report and
   its statuses (`sv-report`), the seal (ADR-034), the exit codes (ADR-029), and the OSCAL export (ADR-156). One rule
   has one home: a check `sv` already has stays in `sv`, and ConfigVet runs it rather than writing a second.
2. **The shared types move first.** `Finding`, `Verified`, `Tier`, and `Secret` move from `sv-check` into a small
   crate both binaries depend on, with no change in behavior, before ConfigVet's first check is written.
3. **Every rule of evidence holds unchanged.** Something not assessed is never a pass and never a failure, and a
   person's word ranks where ADR-022 puts it. A setting left out is a finding only when the default for the version in
   use is known from the vendor's own documentation and is unsafe. When the version or the default is unknown, the
   setting is *not assessed*. Defaults are data, each with its source and version range, and are held as citations are.
4. **`sv`'s fence does not change.** `sv` gains no network connection. ConfigVet's live clients sit in a crate that
   `sv-cli` does not depend on, and a test reads the workspace's dependency graph and fails if `sv`'s binary ever
   reaches it. The test is shown to work by adding the dependency and watching it go red.
5. **ConfigVet's live reading has its own fence**, which is all of:
   - **Off until asked for by name**, per provider (`cv live <provider>`). Never on by default, never from a report
     run, and never from ConfigVet's MCP server.
   - **The token from the environment or the provider's own credential helper**, never from an option (options are
     kept in shell history). Never written to any file, log, or report; shown only as `Secret::redact` shows a key.
   - **Read only.** A token the provider says can write is refused. Where a provider cannot say, the report says so
     before any finding, and the guide says how to make a read-only member or role for ConfigVet.
   - **A fixed list of requests compiled into the binary:** HTTPS with certificate checks, to each provider's named
     hosts only, each redirect checked before it is followed, `GET` or a GraphQL query from the list (never a
     mutation), and limits on the number of requests, response size, and time.
   - **Settings, never data:** an environment variable's name, never its value; never logs, database rows, or stored
     files. A provider endpoint that returns secret values is not on the list, whatever it is asked for.
   - **Every request is listed in the report:** method, host, path, and response status.
6. **A live reading is credited as the provider's account of its own settings.** It can make a requirement *checked*
   only for a setting's value, never for the behavior the setting is meant to cause; that stays `sv probe`'s and
   `sv run`'s to ask. Where the files and the account disagree, that is a finding of its own (drift).
7. **ConfigVet writes for ops engineers.** Its pages use the field's own terms, each linked to the glossary the first
   time it appears. `sv`'s pages keep their plain-language rule.

## Alternatives considered

- **A fully separate tool in its own repository.** Rejected by the owner on 20 November 2026: it would rebuild or copy
  the evidence model, the statuses, the seal, and the requirement data, and keep two catalogs in step by hand.
- **ConfigVet as a set of new `sv` commands (`sv config ...`).** Rejected: the live clients would then be in `sv`'s
  binary, and "`sv` opens no network connection of its own" would hold only by a flag. A crate boundary, held by a
  test, is a stronger guard than a flag.
- **Files only, no live accounts.** Simpler and safer. The owner chose live reading, because the account is what is
  running and the files are only what someone intended. Files stay ConfigVet's first build; live reading comes after.
- **ConfigVet's own scanners for AWS, Azure, and Google Cloud.** Not taken: Prowler, ScoutSuite, Steampipe, Checkov,
  and Trivy already cover them well. ConfigVet runs such tools through adapters and keeps its own rules for missing
  settings, the joins between layers, and drift.
- **Treat a missing setting as a finding whenever a hardening guide recommends setting it.** Rejected: unless the
  default is unsafe, that reports a preference as a weakness. A report that cries wolf teaches its reader to ignore it.

## Consequences

- An ops reader gets one report per app across its layers, with every gap named, in the same statuses `sv` uses, and
  reaching NIST SP 800-53 through ADR-156's crosswalk.
- The project holds a production credential for the first time. The cost is a second fence to design, test, and
  explain, and a security report against `cv live` becomes as serious as one against `sv`'s fence (`SECURITY.md`).
- The defaults table is new upkeep: every framework and platform it lists has to be read again when its next major
  version comes out.
- Moving the shared types out of `sv-check` touches most crates once, and gives `sv` the smaller core its own layering
  has wanted since 8 October 2026.

## The owner's answers (20 November 2026)

The design entry asked four questions. The owner answered two on 20 November 2026, asked for a recommendation on the other two,
and accepted both recommendations the same day:

- **The binary is `cv`.**
- **A live reading is credited as point 6 above says,** as recommended: *checked* for a setting's value as the
  provider reports it, never for the behavior the setting is meant to cause.
- **The first live provider after GitHub: Cloudflare,** recommended and accepted. Its settings are the
  ones that sit between the visitor and the app (SSL mode, the lowest TLS version accepted, HSTS, redirecting to
  HTTPS), so they speak to V12 and to the joins between layers. Its API tokens are built from named permissions,
  so a token can be made read-only. Whether a token can show ConfigVet its own permissions is to be confirmed
  from Cloudflare's documentation before the client is built; where it cannot, point 5's rule for a provider that
  cannot say applies. The owner added a further reason on 20 November 2026: the project's own website,
  stackvet.dev, is hosted on Cloudflare, so the first client can be tried on a real account the project owns,
  with a read-only token, before anyone else's. Vercel was weighed and put later: its tokens are scoped to a team rather
  than to permissions, so ConfigVet could not refuse one that can write, and its API can return environment
  variables' values, which point 5 forbids asking for.
- **The release: one release, two packages,** recommended and accepted. `sv` and `cv` are built
  from the same commit, with one version number and one signed release, and each is installed on its own:
  a `cv` formula beside `sv`'s in `homebrew-stackvet`, and a `cv` manifest beside it in `scoop-stack-vet`. No new
  repositories. Someone who installs `sv` gets no binary that can reach a live account.

This record becomes accepted, with an "As built" section, in the pull request that builds its first part.

## As built

### Part 1, 20 November 2026: the shared types (decision 2, backlog 0686)

- **`crates/sv-core`**, about 700 lines, depending on `serde` and `sv-scan` alone: no tree-sitter grammar and no
  check. It holds `Severity`, `Confidence`, `Secret`, `Location`, `Finding`, `Outranked`, `Tier`, and `Verified`, with
  every method they had; the lists those methods read (`INFORMATION_ONLY`, `TEST_FILE_INFORMATION`, `WORTH_A_LOOK`,
  and the path rules' names and languages); `quoted`, `found`, and the credit census; the two helpers
  `Secret::redact` calls (`cut_with_count`, `reads_as_words`); and the two rule ids the methods name.
- **Where it differs from the plan: the methods moved too.** The plan named the types. But Rust keeps a type's
  methods in the crate that defines it, and `withholds_credit`, `in_test_code`, and `worth_a_look` are what decide how
  a finding counts in a report. Leaving them in `sv-check` would have made ConfigVet either build `sv-check` or
  rewrite them, and a second copy of how a finding counts could drift from the first. That is why `sv-core` depends
  on `sv-scan`: two of the methods ask which files are test code and which language a file is in.
- **Nothing else changed.** `sv-check` re-exports each item under its old path (`sv_check::Finding`,
  `sv_check::finding::Finding`, `crate::verified::Tier`, `secrets::ASSIGNMENT_RULE`, `suite::NAME_MISMATCH`), so no
  other crate's code was edited. What settles a list of findings (`merge_same_place`, `one_per_line`,
  `mark_rust_test_code`, `mark_not_the_app`, `is_svs_own`) stays in `sv-check`. The credit census still names the
  check that made each credit, since `Verified::new`, `in_part`, and `found` are `#[track_caller]`.
- **Also listed:** the new crate in the workspace, in the Dockerfile's dependency layer, in `fuzz/Cargo.lock`, and in
  the crate table of `docs/ARCHITECTURE.md`.

### Part 2, 20 November 2026: `cv check`, files only (backlog 0687)

The owner settled four things before any code was written (20 November 2026): two crates, `cv-rules` and `cv-cli`;
`sv-check`'s YAML reader moved into a crate of its own rather than into `sv-core` or a new dependency; the first rules;
and a listing on the terminal with a `report.json`, the report pages, SARIF, the seal, and the OSCAL export waiting for
a later part.

- **`crates/sv-yaml`**, `sv-check`'s `yaml.rs` moved word for word but for `pub(crate)` made `pub`, over `tree-sitter`
  and `tree-sitter-yaml`. `sv-check` re-exports it as `crate::yaml`, so no check's code changed; `sv-core` stays free
  of tree-sitter, as decision 2 asks.
- **`crates/cv-rules`**, about 1,900 lines over `sv-core`, `sv-scan` (the one folder walk), `sv-frameworks` (the data
  folder), and `sv-yaml`; never `sv-check`. Four readers turn each layer into deployment units: a Dockerfile's stages
  (`ENV`, `USER`, and the chain of `FROM` a stage's name makes), a compose file's services (`image`, `build`,
  `environment` in both forms, `env_file`, `user`), Kubernetes workloads' containers (`env`, `envFrom`, and
  `runAsUser` and `runAsNonRoot`, the container's own outranking the pod's), and a Terraform plan's ECS container
  definitions (`environment`, `secrets`, `environmentFiles`, `user`). A plan is read, not `.tf` text, because a plan
  holds the values after variables and modules are worked out.
- **The five outcomes** (`outcome.rs`): set safe and missing with a safe default are credits, always in part, since one
  file saying so is not the running system; set unsafe and missing with an unsafe default are findings, the second at
  medium confidence because the deployment may set it somewhere the folder does not hold; unknown is a not-assessed
  line saying why. A value from a variable, a `valueFrom`, an `env_file`, an `envFrom`, or an image `cv` cannot read
  is unknown, never a pass.
- **The defaults table** (`data/config-defaults.json`), six entries, each read from the vendor's page on 20 November
  2026: Express's `env` (development when `NODE_ENV` is unset, Express 4 and 5) and its error handler's stack trace;
  Django's `SESSION_COOKIE_SECURE` and `CSRF_COOKIE_SECURE` (`False`, 4.2 to 5.2); the official `node` image's
  `NODE_ENV` and `USER` (neither set, images 22 and 24, read from the image's own Dockerfiles); and Docker's default
  user, root. A version outside what was read, or a range open at either end, leaves the setting not assessed.
  Kubernetes' default for `runAsUser` is not in the table: its API reference could not be read for it, so a pod spec
  that sets neither field is not assessed.
- **The first rules** (`rules.rs`): `cv.express-node-env`, citing V13.4.2 (debug modes off in production) and V16.5.1
  (no stack trace in an error's answer); `cv.django-session-cookie-secure` and `cv.django-csrf-cookie-secure`, citing
  V3.3.1, as a credit in part since the rule does not read the cookie-name prefix the requirement also asks for; and
  `cv.container-root`, citing no requirement, since none in ASVS 5.0 asks it of a container (the owner's choice). Each
  citation was written after reading the requirement's text in `data/frameworks/asvs-5.0.0.json`. The Django rule
  reads the app's settings module, not a deployment file, because that is where Django's settings are.
- **One rule, one home.** `sv`'s launch check already reports a Dockerfile's final stage setting `NODE_ENV` to
  `development` (`config.development-server-started`). `cv` lists that value as set unsafe and leaves the finding to
  `sv`, naming its rule; it reports the layers `sv` does not read. `cv` runs none of `sv`'s checks yet.
- **`crates/cv-cli`**, the `cv` binary: `cv check <folder> [--out <folder>] [--fail-on attention|not-assessed]`. It
  writes one file, `report.json`, into `--out`, by default `<folder>/cv-report`, and refuses a folder holding anything
  else, so it never writes over a person's files. Its exit codes are ADR-029's: 2 when a deployment file could not be
  read or the folder holds none. It depends on `cv-rules` and `sv-core` alone, and no crate of `sv`'s depends on it.
  No network connection is opened anywhere in this part.
- **Witnesses.** Each rule was turned off in turn and the tests read: `cv.express-node-env` off sent six tests red,
  `cv.django-session-cookie-secure` three, `cv.django-csrf-cookie-secure` two, and `cv.container-root` three. Breaking
  the safe-value test, the root-name test, and the unsafe-default branch each sent at least one named test red.
- **`sv`'s counts are unchanged.** `python3 tools/coverage.py --check` writes nothing new: `cv`'s citations are held
  in its rules' constants, not in the literal forms the script counts, so `docs/COVERAGE.md` still says only what `sv`
  can settle. ConfigVet's own counts are for the part that gives it report pages.
- **Also listed:** the three crates in the workspace, in the Dockerfile's dependency layer, in `fuzz/Cargo.lock`
  (`sv-yaml`, through `sv-check`), and in the crate table of `docs/ARCHITECTURE.md`; the defaults table in
  `data/README.md`; and a sentence under "The fence" that `cv check` opens no connection.

## Later, 20 November 2026: V14.2.5's cache half is ConfigVet's (backlog 0625, part 10)

V14.2.5 asks that caches keep only responses of the content type expected for the address, so a private page asked
for at an address ending `.css` is not stored and served to others. `sv run` can see one half of that: whether the app
answers such an address with the private page. It cannot see the other: whether a cache in front of the app, such as

in part, and that the second is ConfigVet's, read from the hosting account's cache settings once a live provider that
has them is built (Cloudflare's cache rules are the first candidate). Nothing in ConfigVet's plan above changes; this
names one requirement its live reading should speak to, to be cited only after reading the provider's settings.

## Later, 21 November 2026: part 4's two questions, answered before any code (backlog 0717)

**1. Can ConfigVet tell that a GitHub token is read-only? Only for a classic token, and a classic token never is.**
Read in GitHub's documentation on 21 November 2026 and tried the same day against this repository, read-only, with the
owner's `gh` sign-in:

- **A classic or OAuth token** (`ghp_`, and `gho_` as `gh auth token` gives) names its scopes on every response, in
  `X-OAuth-Scopes` (seen: `gist, read:org, repo, workflow`). GitHub's scopes page says `repo` grants "read and write
  access to code" and `public_repo` the same for public repositories, and lists no scope that reads a private
  repository's settings without writing. So ConfigVet refuses a classic token carrying `repo`, `public_repo`, or
  `workflow`, naming the scope; the owner's own `gh` token is refused.
- **A fine-grained token** (`github_pat_`) can be made read-only permission by permission, but no header or endpoint
  in the documentation read tells a token its own permissions. `X-Accepted-GitHub-Permissions` names what an endpoint
  needs, not what the token has: tried with a read-only fine-grained token the owner made, it came back on every
  request, successful or not, naming the endpoint's need (`administration=read`, say) whatever the token held. The design entry's "ConfigVet can check
  that" was wrong. Point 5's rule for a provider that cannot say applies: before any finding, the report says
  ConfigVet could not confirm the token is read-only, and the guide says how to make a fine-grained token with read
  access only. ConfigVet never sends a write to find out.
- **A GitHub App's installation token** shows its permissions only when it is made, so it cannot be checked later
  either; it is treated as a fine-grained token.

**2. Which settings, and what each speaks to.** Each is read with one `GET` from GitHub's REST reference, and each
answered for this repository on 21 November. A citation counts *in part* only (point 6), and each requirement's text
was read in `data/frameworks/` first:

- **The rules on the default branch** (`GET /repos/{o}/{r}/rulesets`, each ruleset, and `rules/branches/{branch}`;
  classic `branches/{branch}/protection` where there is no ruleset): who may bypass, the pull request and required
  check rules. AISVS Appendix C **AC.8.3**, in part: the settings that keep an agent from bypassing them, not the alert
  it also asks for. GitHub shows `bypass_actors` only to someone with write access to the ruleset, so without it the
  bypass list is *not assessed*.
- **Whether workflows may approve pull requests** (`actions/permissions/workflow`, its field for whether workflows may approve).
  **AC.8.4** and **AC.4.1**, in part: it keeps the workflow's own token from being the reviewer; it cannot show that
  a reviewer is a human or someone other than who asked for the change.
- **Each environment's protection** (`environments`, and `deployment-branch-policies`): required reviewers, whether
  they may approve their own runs, and which branches or tags may deploy. **AC.7.2**, in part: an Environment holds
  only for a job that names it (ADR-051 and ADR-081, Later, 21 November 2026), and this reads the setting, not the
  workflows that use it.
- **Secret scanning and push protection** (`GET /repos/{o}/{r}`, `security_and_analysis`). ASVS **V13.3.1** and
  **AC.4.2**, in part: they stop known secret patterns, not every secret, and AC.4.2's other five kinds of testing are
  not read. GitHub shows this only to an administrator, so for anyone else it is *not assessed*.
- **Which actions may run, and whether they must be pinned to a commit** (`actions/permissions`: `allowed_actions`,
  `sha_pinning_required`; `selected-actions` when it is "selected"). ASVS **V15.2.4**, level 3, in part: it says where
  actions may come from, not the dependency-confusion half.
- **The default permissions of a workflow's token** (`default_workflow_permissions`) and **approval of fork pull
  requests** (`fork-pr-contributor-approval`): reported, with no citation, since no requirement read speaks to either
  directly.
- **Kept out:** secret and variable values (`actions/secrets` returns names only, and even names are left out unless a
  check needs one), logs, and anything in the repository's files, which `sv`'s own checks already read (one rule, one
  home).

**What each needs, found the same day** with a fine-grained token the owner made for this repository alone, read-only
for Administration, Actions, and Environments (Metadata comes with it), kept in the owner's keychain and never shown,
every request a `GET`: the repository, its rulesets, and the rules on a branch need `metadata=read`; classic branch
protection and every `actions/permissions` endpoint `administration=read`; environments and their deployment branches
`actions=read` (the "Environments" permission was not asked for). All answered. Classic protection answered 404,
"Branch not protected", since this repository uses rulesets; `selected-actions` answered 409, which is how GitHub
says `allowed_actions` is not "selected". With Administration read, the token was shown `security_and_analysis` and
each ruleset's `bypass_actors`, which the documentation puts behind admin and write access; the token's owner is the
repository's administrator, so a member's token may not be, and each stays *not assessed* when GitHub leaves it out.
The guide asks for Administration and Actions, read-only, and nothing else.

## Later, 22 November 2026: part 4's Cloudflare questions, answered before any code (backlog 0732)

Read in Cloudflare's documentation (developers.cloudflare.com) on 22 November 2026; nothing was sent to Cloudflare's API
for these answers. Where a page did not say, that is written here as not stated, to be settled by the first read-only
try on stackvet.dev's zone.

**1. Can ConfigVet tell that a Cloudflare token is read-only? Only if the token may also read API tokens.**

- **The verify endpoint** (`GET /user/tokens/verify`, and `GET /accounts/{account_id}/tokens/verify` for a token an
  account owns) gives a token's id, status (active, disabled, or expired), and dates, and no permissions.
- **A token's permissions** (its policies) are given by `GET /user/tokens/{id}` (or the account's), which needs "API
  Tokens Read" ("Account API Tokens Read" for an account's token). That permission reads every token of the user or the
  account, not only this one: each one's name, policies, and the first and last characters of its value.
- **What tells the kinds apart:** a token's value starts `cfut_` (a user's) or `cfat_` (an account's); a Global API Key
  starts `cfk_`, and Wrangler's own sign-in token `cfoat_`. Older values have no prefix (a Global API Key was 37 to 45
  lower-case hex characters, a token 40 letters and digits). A Global API Key is sent as `X-Auth-Email` and
  `X-Auth-Key`, never as a bearer token, and can do anything the account can.
- **So:** ConfigVet refuses a `cfk_` or `cfoat_` value before sending anything, never sends `X-Auth-Key`, and stops
  unless verify says the token is active.
- **The owner's choice, 22 November 2026,** asked with a recommendation ("Yes, leave it out"): ConfigVet does not ask
  for "API Tokens Read", since it would let ConfigVet see every other token's name, permissions, and part of its value.
  So, as for GitHub's fine-grained tokens, point 5's rule for a provider that cannot say applies: before any finding,
  the report says ConfigVet could not confirm the token is read-only, and the guide says how to make one with Zone
  Read, Zone Settings Read, and Cache Rules Read only, for the one zone. ConfigVet never sends a write to find out.

**2. Which settings, and what each speaks to.** Each is one `GET` under `https://api.cloudflare.com/client/v4`, for the
zone found by `GET /zones?name=<zone>` ("Zone Read"). The settings are read one at a time with
`GET /zones/{zone_id}/settings/{id}` ("Zone Settings Read"), since reading them all at once is marked deprecated. A
citation counts *in part* only (point 6), and each requirement's text was read in `data/frameworks/asvs-5.0.0.json`:

- **`ssl`**, the SSL/TLS mode: `off`, `flexible`, `full`, `strict`, or `origin_pull`. Under Flexible, "all connections
  between Cloudflare and your origin are made through HTTP", so `off` and `flexible` are findings against **V12.3.1**
  (an encrypted protocol for every connection to the application). `full` encrypts that connection without checking the
  origin's certificate, a finding against **V12.3.2** (a TLS client validates the certificate it is given); `strict`
  credits both in part. **`ssl_automatic_mode`**: under Automatic SSL/TLS, Cloudflare may raise the mode by itself
  (never lower it, its documentation says), so the report says the value read is the one at that moment. A `GET` for
  it is not shown in the documentation; if it fails, it is not assessed.
- **`min_tls_version`** (`1.0` to `1.3`) and **`tls_1_3`** (`on`, `zrt` with 0-RTT, or `off`): **V12.1.1**, in part, for
  the visitor's side only: a lowest version under 1.2 is a finding, and TLS 1.3 off is one. The values allowed are not
  listed as such; the documentation's example sends `"1.2"`.
- **`always_use_https`** (`on` or `off`): **V12.2.1**, in part (no fall back to plain HTTP). It redirects every address
  of the zone, API endpoints too, which **V4.1.2** asks not to do; that is said, as information, never credited.
- **`security_header`**, HSTS: its `strict_transport_security` object (`enabled`, `max_age` in seconds,
  `include_subdomains`, `preload`, `nosniff`). **V3.4.1**, in part: off, or a `max_age` under one year (31,536,000), is a
  finding (off became *not assessed* after the try on stackvet.dev; "As built" below says why), and `include_subdomains` off is one at level 2 and up. `preload` is a step toward **V3.7.4** (the domain on
  the public preload list), which this cannot see: shown, never credited.
- **`automatic_https_rewrites`** (`on` or `off`): read and shown; no requirement read speaks to it, so none is cited.
- **The cache rules,** `GET /zones/{zone_id}/rulesets/phases/http_request_cache_settings/entrypoint`, each rule's
  expression and its `set_cache_settings` parameters (`cache`, `edge_ttl`, the cache key, `cache_deception_armor`).
  **V14.2.5**'s cache half (Later, 20 November 2026): what finding to make of a rule is settled when the rules of a
  real zone are seen, and until then a rule is shown, never credited. Which permission reads it is not settled by the
  documentation: the endpoint's own page lists account-wide rulesets permissions only, and the permissions page names
  both "Cache Rules Read" and "Cache Settings Read". If the owner's token is refused, the cache rules are not assessed.

**3. Where the token comes from:** `CLOUDFLARE_API_TOKEN`, the name Cloudflare's own Wrangler reads, and nothing else.
Not Wrangler's sign-in (its `cfoat_` token is the person's whole account), and never `CLOUDFLARE_API_KEY` with
`CLOUDFLARE_EMAIL`, a Global API Key. Never from an option, never written anywhere, shown only as `Secret::redact`
shows a key. The account, where an account's token needs it, is taken from the zone's own answer, not asked for.

**Limits:** the API allows 1,200 requests in five minutes for each token; ConfigVet sends at most about ten for one
zone, and stops at a fixed limit well under that.
