# ADR-157: ConfigVet, a companion for deployment configuration on `sv`'s engine, with a binary of its own and read-only access to live hosting accounts that `sv` never gains

**Status:** proposed, 20 November 2026. Asked for by the owner on 20 November 2026. They chose a shared engine with a
command of its own, named ops and DevSecOps engineers as its readers, and asked that it read live hosting accounts
through their APIs. Nothing is built. The design is the design entry "ConfigVet, a companion for an app's deployment
configuration (20 November 2026)" (`docs/design/0396-configvet-a-companion-for-an-app-s-deployment-configuration.md`).

**Governs:** the design entry above; the network fence, drawn and listed in `docs/ARCHITECTURE.md` ("The fence"),
which this record leaves unchanged for `sv`; and ConfigVet's crates, its defaults table, its live clients, and the test
that keeps them out of `sv`, each named here by its path when the pull request that builds it makes it. A pull
request that changes what ConfigVet may connect to, how it holds a token, what a live reading is credited as, or
whether `sv` can reach ConfigVet's live clients, changes this record too, or says in its description why it does not
(`docs/adr/README.md`).

## Context

`sv` reads an app's code and, behind its fence, the running app. Between the two is the layer that says how the app is
deployed: Dockerfiles, compose files, Kubernetes manifests, Terraform, proxies, CDNs, and the hosting accounts
themselves. `sv` reads part of it today, about forty `config.*` checks, GitHub Actions among them. But nothing in `sv`
knows a framework's or a platform's defaults, so it cannot say that a setting left out is unsafe. And `sv` opens no
network connection of its own beyond the four exceptions in "The fence", so it never sees the live accounts where an
ops engineer's real configuration is.

The owner wants that layer reviewed by a companion, ConfigVet, for ops and DevSecOps engineers, and wants it to read
live accounts. Reading a live account is the first time anything in this project would hold a credential to
production. That is why this decision needs a record before any of it is built.

## Decision

1. **One engine, one workspace, two binaries.** ConfigVet is built from crates in this workspace and ships as a
   binary of its own, `cv` (the owner's choice, 20 November 2026). It reuses the standards and applicability data
   (`sv-frameworks`), the folder walk (`sv-scan`), the finding, credit, and tier types, the outside-tool adapters (ADR-032), the report and
   its statuses (`sv-report`), the seal (ADR-034), the exit codes (ADR-029), and the OSCAL export (ADR-156). One rule
   has one home: a check `sv` already has stays in `sv`, and ConfigVet runs it rather than writing a second.
2. **The shared types move first.** `Finding`, `Verified`, `Tier`, and `Secret` move from `sv-check` into a small
   crate both binaries depend on, with no change in behavior, before ConfigVet's first check is written.
3. **Every rule of evidence holds unchanged.** Something not assessed is never a pass and never a failure, and a
   person's word ranks where ADR-022 puts it. A setting left out is a finding only when the default for the version in
   use is known from the vendor's own documentation and is unsafe. When the version or the default is unknown, the
   setting is *not assessed*. Defaults are data, each with its source and version range, and are held as citations are.
4. **`sv`'s fence does not change.** `sv` gains no network connection. ConfigVet's live clients sit in a crate that
   `sv-cli` does not depend on, and a test reads the workspace's dependency graph and fails if `sv`'s binary ever
   reaches it. The test is shown to work by adding the dependency and watching it go red.
5. **ConfigVet's live reading has its own fence**, which is all of:
   - **Off until asked for by name**, per provider (`cv live <provider>`). Never on by default, never from a report
     run, and never from ConfigVet's MCP server.
   - **The token from the environment or the provider's own credential helper**, never from an option (options are
     kept in shell history). Never written to any file, log, or report; shown only as `Secret::redact` shows a key.
   - **Read only.** A token the provider says can write is refused. Where a provider cannot say, the report says so
     before any finding, and the guide says how to make a read-only member or role for ConfigVet.
   - **A fixed list of requests compiled into the binary:** HTTPS with certificate checks, to each provider's named
     hosts only, each redirect checked before it is followed, `GET` or a GraphQL query from the list (never a
     mutation), and limits on the number of requests, response size, and time.
   - **Settings, never data:** an environment variable's name, never its value; never logs, database rows, or stored
     files. A provider endpoint that returns secret values is not on the list, whatever it is asked for.
   - **Every request is listed in the report:** method, host, path, and response status.
6. **A live reading is credited as the provider's account of its own settings.** It can make a requirement *checked*
   only for a setting's value, never for the behavior the setting is meant to cause; that stays `sv probe`'s and
   `sv run`'s to ask. Where the files and the account disagree, that is a finding of its own (drift).
7. **ConfigVet writes for ops engineers.** Its pages use the field's own terms, each linked to the glossary the first
   time it appears. `sv`'s pages keep their plain-language rule.

## Alternatives considered

- **A fully separate tool in its own repository.** Rejected by the owner on 20 November 2026: it would rebuild or copy
  the evidence model, the statuses, the seal, and the requirement data, and keep two catalogs in step by hand.
- **ConfigVet as a set of new `sv` commands (`sv config ...`).** Rejected: the live clients would then be in `sv`'s
  binary, and "`sv` opens no network connection of its own" would hold only by a flag. A crate boundary, held by a
  test, is a stronger guard than a flag.
- **Files only, no live accounts.** Simpler and safer. The owner chose live reading, because the account is what is
  running and the files are only what someone intended. Files stay ConfigVet's first build; live reading comes after.
- **ConfigVet's own scanners for AWS, Azure, and Google Cloud.** Not taken: Prowler, ScoutSuite, Steampipe, Checkov,
  and Trivy already cover them well. ConfigVet runs such tools through adapters and keeps its own rules for missing
  settings, the joins between layers, and drift.
- **Treat a missing setting as a finding whenever a hardening guide recommends setting it.** Rejected: unless the
  default is unsafe, that reports a preference as a weakness. A report that cries wolf teaches its reader to ignore it.

## Consequences

- An ops reader gets one report per app across its layers, with every gap named, in the same statuses `sv` uses, and
  reaching NIST SP 800-53 through ADR-156's crosswalk.
- The project holds a production credential for the first time. The cost is a second fence to design, test, and
  explain, and a security report against `cv live` becomes as serious as one against `sv`'s fence (`SECURITY.md`).
- The defaults table is new upkeep: every framework and platform it lists has to be read again when its next major
  version comes out.
- Moving the shared types out of `sv-check` touches most crates once, and gives `sv` the smaller core its own layering
  has wanted since 8 October 2026.

## The owner's answers (20 November 2026)

The design entry asked four questions. The owner answered two on 20 November 2026, asked for a recommendation on the other two,
and accepted both recommendations the same day:

- **The binary is `cv`.**
- **A live reading is credited as point 6 above says,** as recommended: *checked* for a setting's value as the
  provider reports it, never for the behavior the setting is meant to cause.
- **The first live provider after GitHub: Cloudflare,** recommended and accepted. Its settings are the
  ones that sit between the visitor and the app (SSL mode, the lowest TLS version accepted, HSTS, redirecting to
  HTTPS), so they speak to V12 and to the joins between layers. Its API tokens are built from named permissions,
  so a token can be made read-only. Whether a token can show ConfigVet its own permissions is to be confirmed
  from Cloudflare's documentation before the client is built; where it cannot, point 5's rule for a provider that
  cannot say applies. Vercel was weighed and put later: its tokens are scoped to a team rather
  than to permissions, so ConfigVet could not refuse one that can write, and its API can return environment
  variables' values, which point 5 forbids asking for.
- **The release: one release, two packages,** recommended and accepted. `sv` and `cv` are built
  from the same commit, with one version number and one signed release, and each is installed on its own:
  a `cv` formula beside `sv`'s in `homebrew-stackvet`, and a `cv` manifest beside it in `scoop-stack-vet`. No new
  repositories. Someone who installs `sv` gets no binary that can reach a live account.

This record becomes accepted, with an "As built" section, in the pull request that builds its first part.
