## Context

Some requirements can be checked by reading the code or asking the running app. Many cannot: they ask how the app is
built, what its rules are, or for something a person must look at, such as the padlock on the live site. For those,
`sv` has only what somebody says, and it is usually the owner's AI coding tool that writes it down, in
`securevibe.toml` and `security-notes.md`, because the owner is not a programmer.

v1's ADR-006 set the rule that carries over: AI review alone is never a pass, and a requirement only a person can
check never passes on its own. `sv` needed more than that rule. It needed to say whose word each answer is, and how
much it is worth.

On 27 September 2026, in the owner's first run in VS Code, the tool wrote nine of the thirteen sections of the notes
from the code and marked each with its own italic line. `sv` threw that line away along with its own italic lines,
and reported all nine as *documented by the owner*.

## Decision

Every answer is credited at the tier of whoever gave it, and an answer that does not say who gave it is the tool's.
The tiers, as the report names them (`Status` in `crates/sv-report/src/lib.rs`), with the ones that rest on
somebody's word below *checked*:

- **checked**: an automated check, of the code or the running app.
- **documented by the owner**: a section of `security-notes.md` under `Written by: owner`.
- **checked by hand by the owner**: a `[checked-by-hand]` entry by the owner, saying what was done (`how`) and when
  (`on`); it counts for 90 days.
- **attested by the owner**: a design answer in `securevibe.toml` with `by = "owner"`.
- **stated by the AI coding tool**: the same answers with `by = "ai-tool"` or `Written by: AI coding tool`, or with
  nothing saying who. In the project's words, "it is the author grading its own work".
- **not verified**: nothing at all.

Rules that hold it together:

- **No mark means the tool's.** "The file is usually written by the tool, so crediting the owner on nobody's say-so is
  the direction that overstates" (the owner's decision, 27 September 2026, for the notes; the design answers already
  worked this way). A mark naming anyone else is named as unreadable, not guessed at.
- **A person can confirm the tool's answer** (`confirmed = { by, on, ... }`, `crates/sv-check/src/confirm.rs`). It then
  counts at the person's tier and is shown as confirmed, because writing `by = "owner"` "would say they gave the answer;
  they checked somebody else's". The tool cannot confirm its own answer, and a confirmation pointing at a file lapses
  when the file changes after it.
- **A person's word never settles a test.** *Attested*, *checked by hand*, and *stated* stay on the list of tests to
  write, and a finding or a check outranks them: "Letting the word retire the test is how *attested* would quietly
  become *checked* with nobody deciding to make it so."
- **What the tool records is the tool's.** Since 4 October 2026, `securevibe_record_answer` writes every answer it
  records as `Written by: AI coding tool` and offers no way to say "the owner"; the owner changes the line
  themselves (the owner's decision that day).

## Alternatives considered

- **Letting `by = "owner"` stand for a confirmation.** Set aside for the reason quoted above: it would credit the owner
  with an answer they only checked.
- **A named reviewer above the owner.** Set aside: "`sv` cannot tell who anyone is", so no name can outrank another.
- Nothing else is written down as considered.

## Consequences

- An answer the tool gave is asked again in the interview until a person gives or confirms it, so the owner sees what
  is still the tool's word.
- **`sv` cannot tell who typed a name.** Every tier above *stated* rests on a mark anybody with the file can write; what
  `sv` does is make the rule plain to the tool, refuse to write the owner's mark itself, and show every answer with its
  source. Nothing in a file can stop a tool that edits it from writing `Written by: owner`.
- A file changed on the same day as the confirmation that points at it is not seen as changed.


## Later, 4 October 2026: the owner's tiers need a seal

ADR-026 changes part of this record. *Documented by the owner*, *attested by the owner*, and *checked by hand by the
owner* now need the owner's answer to have been recorded through `sv review`, which seals it; `by = "owner"` or
`Written by: owner` written into a file any other way counts as *stated by the AI coding tool*. A confirmation counts
only when sealed in the same way. The tiers and their order are unchanged. The consequence above, "Nothing in a file can
stop a tool that edits it from writing `Written by: owner`", still holds of the file; what changed is that writing it no
longer earns the owner's tier.

## Later, 4 October 2026: a section ends at any heading

An answer is what sits under its section's heading, and until now a section ended only at the next section's heading.
A heading of somebody's own (`## A note from me`) ended nothing, so what followed it became the answer to the section
above. A section nobody answered was then counted as answered, at the tier of the note's `Written by:` line, or as the
AI coding tool's word when the note had none. Reproduced end to end on 4 October (BACKLOG, "A heading of the owner's own
in `security-notes.md`"), before and after the same day's change that keeps the owner's text (R7), which already made
`sv`'s own headings end a section.

At the owner's choice that day, any heading of the first three levels ends the section above it. What follows a
heading of somebody's own is part of no answer and credits nothing. It is kept word for word with the other text that
is not under a question (R7's section near the top, which the report does not read), and the report lists each such
heading, with the section it followed, as a gap: "what is under 1 heading of your
own in security-notes.md". A deeper heading (`####`) stays part of the answer it is in, so an answer can still have
parts. The seal `sv review` places is held to the same boundary. The other way out, reporting such a heading as a
problem with the file, was set aside: notes of the owner's own are allowed. The report uses its list of gaps rather
than a new kind of note because it already says there that a `Written by:` line nothing was made of was not read; a new
kind of note would have changed all four report formats.

## Later, 5 October 2026: an unmarked answer is the tool's to count, not to throw away

The deep review of `sv` at `eff3f17` (R8) found that `securevibe_record_answer` replaced any section not marked
`Written by: owner`, so an owner's answer written without the line was lost. Crediting is unchanged: an answer with no
mark still counts as the tool's. What changed is what the tool may write over: only a question with nothing under it,
or a section marked `Written by: AI coding tool`. An unmarked answer, one marked as anybody else's, and the owner's are
refused, nothing is written, and the reply says that the owner can edit the answer or delete it. Whose word an
answer is, and whether it may be destroyed, are separate questions, and the second takes the side that keeps text.
Decided by the session that built it, following the rule the owner's coordinator set for R8 (DESIGN, "The AI coding
tool writes over only its own answer").

## Later, 5 October 2026: `planned`, an answer that is worth nothing yet

A fourth design answer, `planned`, for a decision made before there is code: `where` names the file it will be in.
No tier above changes, because `planned` joins none of them: it credits nothing, by anyone, and is never evidence. What
it adds is a way to hold the decision to the code once there is some. While the app has no code (the scan read no
source file and no dependency manifest) it is listed as planned, not built yet. Once it has code, a named file that is
not there is a low finding, *decided, never built*, less sure than a stale pointer because the work may be in another
file; a named file that is there is a reminder to change the answer to `yes` or `no`; and a plan with no `where` is
reported as one `sv` cannot follow. The owner chose a new answer over reading `design-decisions.md` (backlog,
"Decisions as planned, then held to").

## Later, 9 October 2026: a person confirming a security notes section the tool wrote

**Status:** accepted, 9 October 2026, in the pull request that builds it; proposed the same day with the backlog claim
(the gap analysis of 7 October 2026, finding 22(c)).

A design answer or a check made by hand that the AI coding tool gave can be confirmed by a person through `sv review`,
and is then shown as confirmed, never as the person's own (above). A security notes section had no such path: an owner
who agreed with a section the tool wrote changed its line to `Written by: owner` and sealed it, and the report called it
*documented by the owner*, with nothing left to say the tool drafted it.

Proposed: `sv review` offers a section marked `Written by: AI coding tool` for confirming, by name, as it does the
others, and the tool cannot confirm its own. Its seal covers who wrote the section as well as the answer, so changing
the line afterwards breaks the seal instead of turning the tool's draft into the owner's word. The section then counts
at the documented tier, as an owner's sealed section does, the same rank as the other confirmations, and is shown as
"written by the AI coding tool, confirmed through sv review". Sections marked `Written by: owner`, and their seals, are
unchanged, so no seal already written stops holding.

As built: the confirmed seal is made over its own domain, `security-notes-confirmed`, beside the requirement and the
answer (`notes_confirmed_fields` in `crates/sv-check/src/seal.rs`), and credited as `notes.confirmed`. Nothing else
records the name typed: the seal shows `sv review` recorded it, as it does an owner's section. Held by
`crates/sv-check/src/notes/confirmed_tests.rs`, `crates/sv-cli/src/review/confirm_notes_tests.rs`, and
`crates/sv-cli/tests/notes_confirmed.rs`. The same holds in `design-decisions.md`, read by the same code.

## Later, 14 October 2026: a question may carry the lines it is about, and they credit nothing

**Status:** accepted, 14 October 2026, in the pull request that builds it (backlog 0487, the owner's decision of 13
October 2026 to build this first, alone, and try it on one chapter's questions).

In the Antigravity trial the AI coding tool gave the owner tips about the code with each question, and several did not
hold once the owner asked for the lines (backlog 0397). Now a question can come with the lines itself.

- **A locator finds and does not judge.** Each one is in `data/locators.json`, read by `crates/sv-check/src/locate.rs`.
  It names the questions it serves and the function names that count, and gives a tree-sitter query per language.
- **Kept apart from the rules on purpose.** Locators are not in `ast-rules.json`, and nothing that makes a finding,
  credits a requirement, or holds a rule back can read them. A locator that finds nothing therefore says nothing about
  the requirement either way.
- **What a question may carry.** At most three places (`human::MOST_POINTERS`), and how many more there were. Each
  place is the line with the one before and the one after, redacted as a finding's lines are (`secrets::redact_text_in`,
  which shows a key as `Secret::redact` does), and cut to 200 characters a line.
- **Every place comes with one fixed sentence** (`human::POINTERS_SAY`): "These are where to look, not evidence:
  StackVet found them by their names and did not read what they do."
- **What it changes about the requirement: nothing.** A requirement with lines to look at is exactly as verified as one
  without, and an answer is still credited at the tier of whoever gave it (above).
- **Where the lines are shown:**
  - the questions the AI coding tool is given (`sv questions` and the MCP `questions` section), with each piece of the
    app's text inside the fence (deep review R9);
  - report.html, under "What only you can check".
- **Where only the file and line are shown:** compliance.md, whose table cells hold no lines of code, and `report.json`
  and the MCP structured result, which hold none of the app's code.
- **The trial: V8.** One locator, `locate.authorization-checks`, serves V8.1.1 and V8.3.1. It finds functions whose
  names say they check a role or a permission, in Python, JavaScript, and TypeScript, both where each is written and
  where it is used.
  - **Left out on purpose:** names that only sign a person in, such as `login_required`, which would send the owner
    to the wrong lines.
  - **Not covered yet:** the field-level questions (V8.1.2, V8.2.3) and the multi-tenant check (V8.4.1), which ask about
    something these names do not show. The fourteen proposals that assume this (0488 to 0499) wait on what the trial
    shows, as the owner decided.
- **How it is held:**
  - `crates/sv-check/src/locate/locate_tests.rs`, among other things, checks that every question a locator names is
    one a catalog asks.
  - `crates/sv-cli/tests/question_pointers.rs` runs it end to end. It checks the lines in the questions and in
    report.html; the file and line only in compliance.md and `report.json`; a password beside the check redacted; and
    the requirement still not verified.
