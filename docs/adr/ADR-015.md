# ADR-015: What the owner says can add requirements and never remove one, and silence is not a "no"

**Status:** accepted. Decided with `sv`'s design (DESIGN, "Claims, and what corroborates them"), narrowed on
26 September 2026 (DESIGN, "Finding nothing does not answer for the owner"), written down here on
27 September 2026.

**Governs:** `crates/sv-frameworks/src/applicability.rs`, `crates/sv-frameworks/src/condition.rs`,
`data/tech-signatures.json`, `crates/sv-manifest/src/lib.rs`, `data/applicability-v2.json`,
`data/claim-corroborators.json`. A pull request that changes
any of these changes this record too, or says in its description why it does not (`docs/adr/README.md`).

## Context

Which requirements apply to an app depends on about twenty-five yes-or-no facts about it: does it have
sign-in, take uploads, take payments, use AI, and so on. v1 learned these from its wizard. `sv` has no
wizard. The owner's AI coding tool writes them into `securevibe.toml`, and `sv` reads the code to check
them.

Getting one of these wrong in one direction is harmless: the owner is asked to meet a requirement they did
not need. Getting it wrong in the other direction is the failure that matters: a requirement the app needed
is reported as "not applicable", and nobody looks at it again.

## Decision

Each answer in `securevibe.toml` is a **claim**, and `sv-manifest::resolve` combines it with what the code
shows:

- **Either one saying yes is a yes.** A claim of "no" cannot switch off a requirement the code shows
  applies; the code wins, and the disagreement is a finding. A claim of "yes" is honored even when nothing in
  the code shows it.
- **A "no" needs the owner.** It takes effect only when the owner wrote it and nothing in the code
  contradicts it.
- **Silence stays silence.** When the owner has not answered, the requirements that turn on the answer are
  *not assessed*. This holds even when the scan looked and found nothing, because not finding a CI file in
  the copy `sv` read is not finding the pipeline absent.

There is one place where the scan's silence does remove requirements, and it is deliberate: the **derived**
conditions, which the owner is never asked, such as whether the app parses XML or serves GraphQL. The code
answers those, and when it finds nothing, the answer is "no". It is limited to technologies that always leave
a trace: a library in a manifest, or a standard-library import in the source. The matching is loose on
purpose (`data/tech-signatures.json`), because matching too much only ever adds requirements.

## Alternatives considered

- **Infer every answer from the code.** Sign-in can be written from a hash function and a database table and
  leave no library behind. Answering "no sign-in" because no sign-in library appears would switch off
  fifty-three ASVS requirements on the strength of a missing dependency.
- **Take the manifest's word.** A careless or over-confident manifest would then become an over-confident
  report.
- **Let a scan that found nothing answer for a silent owner.** This was the rule for `ci-cd` and `iac` until
  26 September 2026. On a manifest that answered nothing, it marked twelve requirements not applicable while
  the claim's own note said that finding nothing "is not the same as finding it absent".

## Consequences

- An owner who leaves a question unanswered sees requirements *not assessed* rather than excluded. The
  report looks less complete, and it is accurate.
- A wrong "yes" costs the owner work. A wrong "no" is caught whenever the code shows the capability, and is
  otherwise the owner's own statement, shown as theirs.
- The derived conditions are the exception, and they need watching. A technology added to the list has to
  be one that cannot be used without leaving a trace, or its "no" is a guess.
- Enforced by tests on `resolve` in `crates/sv-manifest/src/lib.rs`, and by one that runs `sv report` on a
  bare manifest. Putting the pre-26-September line back fails both.

## Later, 9 October 2026: infrastructure and CI files are looked for wherever an app keeps them

The gap analysis of 7 October 2026, finding 16 (`docs/GAP-ANALYSIS.md`, 3.8), the corroborators half, taken by session
securevibe-e2. `iac` and `ci-cd` are the only claims whose absence is an answer (`absenceIsEvidence` in
`data/claim-corroborators.json`), so the files they look for decide what "nothing found" means. `Dockerfile`, the
compose files, and `Chart.yaml` were looked for only at the root, and an app with its Dockerfile in `deploy/` was
answered "nothing found", which agreed with an owner who had said "no infrastructure configuration".

A file pattern `**/name` now matches a file or folder of exactly that name at any depth (`matching_path` in
`crates/sv-scan/src/lib.rs`); a name that merely ends in it does not match, and folders the scan does not enter, such
as `node_modules`, still count for nothing. `iac` uses it for `Dockerfile`, `Containerfile`, `docker-compose.yml`,
`docker-compose.yaml`, `compose.yaml`, `compose.yml`, and `Chart.yaml`, and adds `cdk.json`; `ci-cd` adds
`.travis.yml`, `cloudbuild.yaml`, `cloudbuild.yml`, and the `.buildkite` folder. The rule of this record is unchanged:
finding a file is a yes, and finding none still answers only an owner who said no. The change is in the direction this
record cares about: fewer apps are answered "nothing found" when they have the files. `data/claim-corroborators.json`
carries this record's rule and was governed by no record; it is added to the Governs list. Tests:
`crates/sv-scan/tests/corroborators_any_depth.rs`.

## Later, 10 October 2026: an unread package list makes an absence incomplete (backlog 0236)

A technology looked for by the package it is installed as was reported "not used" when the app's package list was

## Later, 13 October 2026: an owner's "no" does remove requirements, and the record's title says it does not (backlog 0332)

The deep review of 12 October 2026 found the comment on `resolve` in `crates/sv-manifest/src/lib.rs` saying "both
directions add requirements; neither removes one", and calling that the safety argument. That is not what the code
does, and it is not what this record decides. The decision above says a "no" "takes effect only when the owner wrote it
and nothing in the code contradicts it". When it takes effect, the requirements gated on it are not applicable. This
happens on the owner's word alone where no corroborator exists, and the report marks such a claim as taken on the
manifest's word. The Consequences already say so: a wrong "no" "is otherwise the owner's own statement, shown as
theirs". This record's title has the same overstatement as the comment: an owner's "no" can remove requirements, but
only one the code does not contradict. The comment now says this. The rule and the code are unchanged.

## Later, 14 October 2026: an empty host is listening on every address too (backlog 0399)

In the owner's trial an AI coding tool changed a Python server's default host from `"0.0.0.0"` to `""` after Bandit's
B104 flagged the first, and the finding went away though the server listened on every address as before: in Python an
empty host given to `socket.bind` or `http.server` binds every address. The Python signs of `internet` in
`data/claim-corroborators.json` now include an empty host as the address tuple takes it (`(("", ` and `(('', `), a
`HOST` that defaults to empty (`"host", "")` and `'host', '')`), and `"::"`, the same for IPv6. Finding one is a yes,
which only adds requirements; finding none settles nothing, as before. `sv run`'s preflight reads the same forms as
listening on every address. Other languages keep `0.0.0.0` alone: an empty host means every address only where the
server reads it that way, and Python's `socket` and `http.server` are the ones the trial showed.

`sv` has no finding of its own for an app that listens on every address, and does not add one. Bandit's B104 and
Semgrep's `avoid-bind-to-all-interfaces` report it when the outside tools run. `sv`'s own word on it would contradict
`sv run`, which needs the app to listen on every address to reach it from a second container, and an app meant for a
phone on the same Wi-Fi needs the same. Which requirement it would speak to is not plain either. Whether the app is
meant to be reachable is the owner's answer to `internet`, which these signs corroborate.

## Later, 14 October 2026: V6.6.2 has a condition of its own, which an emailed code answers (backlog 0468)

V6.6.2 asks that out-of-band codes be bound to the sign-in that asked for them, and `sv` checks an emailed sign-in code
against it (`EMAIL_CODE_UNBOUND`, from an `email-code` entry under `[stack.run.users]`). But it was gated on
`out-of-band-auth`, whose question names phone, SMS, and push only, so an owner with emailed codes answered "no"
truthfully and V6.6.2 was excluded while the check that speaks to it ran. The owner chose on 14 October 2026, as
recommended, a new condition for V6.6.2 alone, `out-of-band-or-email-code`: "Does the app send sign-in codes by phone,
SMS, push notification, or email?", with the reason "This app does not send sign-in codes by phone, SMS, push
notification, or email." It is yes when `stackvet.toml` has an `email-code` entry, whatever `out-of-band-auth` says;
otherwise it is `out-of-band-auth`'s answer as given, silence included. What corroborates `out-of-band-auth` (a phone,
SMS, or push provider in the code) corroborates it too, so it can only add V6.6.2, as every claim here can. V6.6.1 stays
on `out-of-band-auth`: it is about phone and SMS codes. The owner's "no" with nothing in the code to say otherwise is
still taken on their word, and labeled as such. The tests are in `crates/sv-manifest/src/email_code_condition_tests.rs`
and `crates/sv-frameworks/tests/emailed_codes.rs`; each of the three parts (the `email-code` entry, the shared
corroborator, and the data's condition) turns one of them red when it is undone.

## Later, 15 October 2026: what only the tests show counts neither way, and `media_type` is no corroborator (backlog 0538)

In the three-tool trial of 14 October 2026, two contradictions rested on single words: `httpx`, declared in
requirements.txt for the tests' client, read as the app calling outside services, and FastAPI's `media_type=` read as
the app sending pictures to a model. The AI coding tool removed the one and moved the other out of requirements.txt to
make them go away, and the container could no longer run the app's tests. Three changes:

- **`media_type` is removed** from `multimodal-ai`'s Python patterns in `data/claim-corroborators.json`. An image block
  sent to a model is still found by its `"type": "image"`, and so are the other vendors' field names.
- **What only the tests show is neither a yes nor a no.** A pattern found only in a test file (`is_test_path`, moved to
  `sv_scan::files` from `sv_check::finding`, which re-exports it), or a declared Python or npm package that only test
  files import, answers the condition with nothing (`Evidence::OnlyInTests`, value none), and says what it saw. It is
  not a yes, since tests are not what the app does; it is not a "nothing found" either, since the same code in a test
  may stand for code the app has where no pattern reaches. So it never contradicts the owner, and the owner's own
  answer stands as for any claim the code cannot settle. A package that no file is seen to import (a server, a plugin,
  one imported under another name, such as `Pillow` as `PIL`) counts as before. Imports are read as lines
  (`sv_scan::imports`), for Python and JavaScript or TypeScript only.
- **A contradiction is worded so it does not read as something to make go away:** the code names something that
  usually means the app does this, so the requirements are switched on; if the app does not do this, leave the code as
  it is and tell the person; the requirements stay switched on. In the report's claim line, `stackvet_check`, and
  `sv scope`.

The tests are in `crates/sv-scan/tests/only_in_tests.rs` and `crates/sv-scan/src/imports/imports_tests.rs`.

## Later, 15 October 2026: the derived condition `mtls` (backlog 0495)

The owner's choice of 14 October on backlog 0495. V12.1.3 (mTLS client certificates validated before their identity
is used) now turns on `mtls`, a condition derived from the app's own code like `xml`: the server's TLS settings asking
for a client certificate (`requestCert`, `ClientAuth`, `CERT_REQUIRED`, `setNeedClientAuth`, and their kin, in the
languages `sv` reads), a header a proxy sets with a verified certificate (`x-ssl-client`, `SSL_CLIENT_`), or a front
server's settings file in the repository (nginx, Apache, Caddy, Traefik), which `sv` does not read for what it says and
so counts as the app possibly asking for one. Found, the requirement applies as before; not found, with every file
read, it does not apply, with the reason "the app asks for no client certificate". One rule at the requirement itself,
not beside `tls`: rules at one scope are OR-ed, and an app that asks for a client certificate is doing TLS. A
certificate checked by a load balancer outside the repository cannot be seen; the signature's note says so. The tests
are `crates/sv-scan/tests/mtls.rs`, with two fixture apps.

## Later, 16 October 2026: the derived condition `saml` (backlog 0500)

V6.8.3 asks that each SAML assertion be used only once, and so speaks only to an app that takes sign-ins through SAML.
Until now it sat under V6.8's rule, the `oauth` claim, and was asked of every app that signs in through another
service. A derived condition `saml` now places it alone: a SAML library among the app's pinned packages (`passport-saml`
and `@node-saml/*`, `samlify`, `python3-saml`, `pysaml2`, `djangosaml2`, `ruby-saml`, `omniauth-saml`,
`onelogin/php-saml`, `crewjam/saml`, Spring's SAML 2 provider, OpenSAML), or one named in the code, and V6.8.3 applies;
neither, with every file and package list read, and it does not, with the reason "no SAML library is used, so there are
no SAML assertions to replay". A list nobody pinned leaves it not known, as for every derived condition. One rule at the
requirement itself, so it replaces the section's `oauth` rule for V6.8.3 alone (the most specific scope wins), which is
right: SAML is sign-in through another service. A SAML exchange written by hand on an XML parser is not seen, and its
V6.8.3 would be called not applicable; the signature's note says so. The tests are `crates/sv-scan/tests/saml.rs` and
`crates/sv-frameworks/tests/saml_assertions.rs`, red with the rule moved and with the packages taken out.
