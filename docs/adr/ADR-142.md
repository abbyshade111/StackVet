# ADR-142: The code rules read the calls inside Rust's standard macros, and a clean result in Rust says so

**Status:** accepted, 24 October 2026, in the pull request that builds backlog 0660, which was filed that day while
building backlog 0649's Rust example and taken next in the backlog's order.

**Governs:** `crates/sv-check/src/ast/macro_args.rs` (which macros are read, and how), where read_file runs the
rules a second time on the copy (`crates/sv-check/src/ast.rs::read_file`), the Rust words in a clean result
(`crates/sv-check/src/ast/macro_args.rs::SAID`, added in `crates/sv-check/src/ast.rs::clean_rules`), how a format! is judged piece by piece
(`crates/sv-check/src/ast/fixed.rs::format_pieces_safe`, Later, 24 October 2026), and their tests
(`crates/sv-check/src/ast/macro_args_tests.rs`, `crates/sv-check/tests/clean_rust_macros.rs`,
`crates/sv-check/tests/rust_example.rs`). A pull request that changes which macros' arguments are read, or what a clean
Rust result says about them, changes this record too, or says in its description why it does not
(`docs/adr/README.md`).

## Context

Tree-sitter's Rust grammar keeps a macro's arguments as an unparsed run of tokens (`token_tree`). No code rule's query
saw a call written inside `format!(…)`, `println!(…)`, `vec![…]`, or `assert!(…)`, so `format!("{:x}",
md5::compute(b))` was not found by the weak-hash rule, and every rule that reads Rust was blind in the same place. Rust
puts many calls inside macros, and a clean result in Rust said nothing of it: "nothing found" was wider than what had
been looked at, which the first rule of evidence forbids. The example app of backlog 0649 held the case as known, on
a line marked `sv:missed`.

## Decision

- **The standard macros whose arguments are expressions are read as calls.** The list is `READ` in
  `macro_args.rs`: `format!`, `format_args!`, `print!`, `println!`, `eprint!`, `eprintln!`, `write!`, `writeln!`,
  `vec!`, `assert!`, `assert_eq!`, `assert_ne!`, their `debug_` forms, `panic!`, `todo!`, `unimplemented!`, and
  `unreachable!`, also when written with a path (`std::println!`).
- **How:** a copy of the file has each such `name!(…)` rewritten byte for byte as the call `name (…)` (the `!` made a
  space, the delimiters made parentheses), parsed again, with nested macros found a round at a time. Nothing moves, so
  a line in the copy is the line in the file. The same rules run on the copy, and only a match lying wholly inside a
  rewritten macro's arguments is kept, never the rewritten macro itself (a call on its result, `format!(…).len()`, is
  kept: it is code written there). A finding the first reading already made is not made twice.
- **What stays unread, and is said to:** a macro of the app's own or a library's (whose arguments may not be
  expressions), `vec![value; count]`, and every macro in a file that did not parse cleanly. A clean result for a rule
  in Rust now says "inside the standard macros' arguments too, such as `format!`, `println!`, and `vec!`, but not
  inside a macro of the app's own or a library's", beside the Rust files it read.
- **No requirement is credited anew.** The rules and their citations are unchanged; they find more, and a clean
  result says more exactly where it looked.

## Alternatives considered

- **Teach each rule's Rust query to look inside `token_tree`.** Rejected: the arguments are flat tokens, not
  expressions, so a query cannot see `md5::compute(b)` as a call there; each of 18 rules would need a reading of its
  own.
- **Rewrite the file once and read only the copy.** Rejected: a rule that already reads a macro from outside (the SQL
  rule's `execute(&format!(…))`) would see a different shape, so the first reading stays as it was, and the copy adds
  only what lies inside.
- **Read every macro's arguments.** Rejected: a macro of the app's own or a framework's may take something that is not
  an expression (a pattern, a type, a route), and reading it as one could make findings that are not there.

## Consequences

- A Rust app's report can find, in the standard macros' arguments, every fault the Rust rules already find elsewhere.
  `examples/rust-notes` marks two (`format!` and `format!` around `format_args!`) as faults, and one, `assert!` around
  `std::write!`, as safe.
- Each Rust file with a standard macro is parsed and queried a second time; Rust files are a small share of most apps.
- A finding in a macro of the app's own is still missed, and the clean result says it is not looked at.

## Later, 24 October 2026: `format!` read piece by piece, and the HTML rule reads Rust (backlog 0661)

`ast.html-from-value` now reads Rust: Axum's `Html(…)` and Actix's `.body(…)` on a response whose content type is
HTML, given HTML built right there with `format!` or `+`. A `Html(page)` whose page is a name is not reported, since
it is most often a template's own output, which escapes.

HTML is written by joining fixed markup to escaped values, and the rule is safe when every piece is fixed text or
escaped (`safeArgumentPiecesRead`). A `format!`'s arguments reach that reading as one unread run of tokens, so it now
reads them itself: the format string is fixed text; a name written inside it (`{name}`) is a value from outside,
unless a `name = …` argument gives it; and each argument after the string must be fixed text, a number, or escaped
(`html_escape::encode_text`, `ammonia::clean`, and the like), a named one by its value. Any other macro is still judged
by its text as a whole, and `&value` is read as its value. Only the HTML rule reads pieces, so no other rule's result
changes. A template's own `|safe`, inside a template file, is not read, and the rule's Rust words say so.
