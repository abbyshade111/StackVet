# ADR-138: The path rule reads where a value came from: a path built from a request is a thing to fix

**Status:** accepted, 23 October 2026, in the pull request that builds it; proposed the same day with the claim for
backlog 0653, at the owner's answer of that day to backlog 0647's choices, asked how StackVet should tell a real fault
from the false alarms its path rule raised on its own code: "A: read the source (Recommended)".

**Governs:** `data/ast-rules.json` (the two path rules, one reading a request's input and one any value),
`crates/sv-check/src/finding.rs::PATH_FROM_REQUEST_LANGUAGES`, `crates/sv-check/src/finding.rs::worth_a_look`,
`crates/sv-check/src/ast.rs::name_set_to`, `crates/sv-check/src/ast.rs::SETTERS`, the words beside such a finding in
`crates/sv-report/src/lib.rs`, and their tests (`crates/sv-check/src/ast/path_from_request_tests.rs`,
`crates/sv-check/src/finding/path_apart_tests.rs`). A pull request that changes what the path rules report as a thing
to fix, or list apart, changes this record too, or says in its description why it does not (`docs/adr/README.md`).

## Context

V5.3.2 asks that "when the application creates file paths for file operations, instead of user-submitted filenames, it
uses internally generated or trusted data, or if user-submitted filenames or file metadata must be used, strict
validation and sanitization must be applied." `ast.file-path-from-value` reports every file call whose path is not
written out, and never asks where the value came from. On StackVet's own code it listed 150 things to fix, none from a
request; the one place a less trusted party hands `sv` a path, the MCP server, already validates it. The owner: "otherwise
actual issues will get overlooked." The findings and the choices are the design entry
`docs/design/0394-the-path-rule-s-false-alarms-and-how-test-code-is-read-23.md`.

## Decision

- **A path built from a request's input is a thing to fix,** at a higher confidence than today: a framework's request
  value reaching the file call in the same function, directly or through names followed as `ast/followed.rs` follows
  them. What counts as a request's input is a list per framework, kept in `data/` beside the rule.
- **Any other value is still a finding, counted and shown in full, and listed apart as worth a look,** with what the
  rule could not tell said beside it. V5.3.2 needs attention exactly when it does now: which list a finding is on
  changes, not whether it counts.
- **Rust gains the safe forms the other languages have,** fixed text through names and a join under a constant.
- **The cost is said, not hidden:** a request's value that reaches the call through a helper in another file, or
  stored and read back, is listed apart rather than among the things to fix. The rule's `looksForIn` says what it reads.

## Where the build differs

- **A rule of its own.** `ast.file-path-from-request` reads the same file calls as `ast.file-path-from-value`, and
  reports only a path built from a request's input (high severity, medium confidence, findings only, so it credits
  nothing). On one line the two merge, as findings sharing a CWE do, and the request rule's is kept. The old rule keeps
  its id, so a finding someone has already set aside under it still matches.
- **Where a request's input is read:** Python, JavaScript, TypeScript, Go, PHP, Ruby, Java, Kotlin, C#, Rust, and shell,
  each with its frameworks named in the rule's `looksForIn`. In C, C++, Dart, and Swift it is not read yet
  (`nothingToFind` says so), and there an old-rule finding stays among the things to fix: listing it apart where a
  request's input is not looked for would hide one that is.
- **Listed apart, not hidden:** an old-rule finding is worth a look only in a language the request rule reads, and only
  when no other rule reported the line; a Semgrep rule agreeing keeps it a thing to fix. The reports say beside it what
  StackVet could not see, and that it still counts. On StackVet's own code, V5.3.2's status and the 31 requirements
  that need attention were the same before and after.
- **Following names deeper:** a rule option, `argumentNamesDepth` (3 here, 1 for every other rule), follows a value
  through up to three names. Rust's `let`, `if let`, and `while let`, and a handler's extractor parameter
  (`Path(name): Path<String>`, read as set to its type), are followed too; no other rule reads Rust names.
- **Found while building:** the first Rust pattern took `.file_name()` as an upload's name, and std's `Path::file_name`
  is everywhere: StackVet's own `main.rs` was reported. An upload's name is now followed back to the `Multipart`
  extractor instead.
- **Not built:** Rust's safe forms (a name followed back to fixed text, a join under a constant). Rust's path findings
  from other values are listed apart now, so they no longer crowd the things to fix; they remain in backlog 0653.
- **Held by** `path_from_request_tests.rs` (each language both ways, three names deep, Rust's bindings, a value made
  safe, and `Path::file_name`) and `path_apart_tests.rs` (where a finding is worth a look, and the merge). With the
  following kept to one name, with Rust's patterns not read, or with the listing apart taken out, each fails.


## Later, 24 October 2026: the request-forgery rule reads Rust's request input the same way (backlog 0661)

`ast.fetch-address-from-request`, an outgoing request whose address the incoming one chose (server-side request
forgery), read no Rust. It now reads Rust with this record's reading of a request's input: a handler's extractor
parameter (`Query`, `Path`, `Form`, `Json`, or `Multipart` in Axum or Actix) or the request's `uri()`, the same
`argumentPatterns` the path rule uses for Rust. The outgoing requests it reads are `reqwest`'s `get`, `post`, and the
rest (`reqwest::blocking` too), a client's methods (`client.get(…)`, and `client.request(method, …)` with the address
second), and the `http` crate's `Request::get(…)` and `Request::builder().uri(…)`; an address that starts with a fixed
host, written out or in `format!`, is the app's own.

Its `argumentNamesDepth` becomes 2, for every language it reads. In Rust an extractor is always one name more
(`let url = q.url.clone()` is set from `q`, whose type is `Query<…>`), and the depth is the rule's, not a language's.
In Python, JavaScript, and Go this follows one more name than before, so it can find more and never fewer; the rule
only ever reports (`findingsOnly`), so it credits nothing either way, as before. Its witnesses in all four languages
still hold.

## Later, 24 October 2026: the request-body rule reads Rust, and a name is followed only when it is the whole value (backlog 0661)

`ast.request-body-passed-whole`, a record saved from the whole request body as it came (mass assignment), now reads
Rust: diesel's `values(…)` and `set(…)`, and sea-orm's `from_json` and `set_from_json`, given the body an Axum or
Actix `Json` or `Form` extractor read. To follow `values(&body)` back to `Json(body): Json<NewUser>`, the rule now
reads names (`argumentNamesRead`, two deep), in every language it reads.

Read as this record's other rules read names, every name in an argument counts, so `values((name.eq(&body.name),
…))` and a struct built field by field from the body would read as the body passed whole, which is the safe form the
rule's fix asks for. So a new option, `argumentNamesWhole`, follows only an argument that is itself a name (`body`,
`&body`, `body.0`, `body.into_inner()`, `body.clone()`, Python's `**data`), at each step, never a name inside a larger
value. Only this rule sets it. In JavaScript it now finds `const body = req.body; User.create(body)`, and still not
`User.create(body.name)`; Python's form, which matches the request in the argument's own text, is unchanged. The rule
only ever reports, so it credits nothing either way, as before.

## Later, 25 October 2026: Rust's safe forms, built (backlog 0653)

What this record left "Not built". `crates/sv-check/src/ast/followed_rust.rs` spares a Rust path every part of which
is fixed in the app's own code, for both path rules (the two that set `safeNamesRead`): a string or raw string, a
constant named in capitals (as the other languages' patterns read one), a compile-time macro such as
`env!("CARGO_MANIFEST_DIR")`, `Path::new` or `PathBuf::from` of a fixed path, a fixed path's `join` (and
`with_extension`, `with_file_name`, and the conversions like them) of fixed paths, a reference to one, and a name its
function sets only to fixed paths, followed up to three names deep. A parameter of that name, an assignment to it, or a
`let` that binds it some way this does not read leaves the call judged as before. On StackVet's own code, `sv report`
that day had 3,405 path findings in Rust files under `crates/` without this and 3,337 with it: 68 spared (65 in test
code, and 3 `Path::new(env!("CARGO_MANIFEST_DIR")).join(...)` reads of the repository's own files), none newly
reported. Held by `crates/sv-check/src/ast/rust_safe_path_tests.rs`; with the reading not hooked in, with parameters,
reassignments, a join's arguments, or constants not read, or with names not followed, each turns a test red.
