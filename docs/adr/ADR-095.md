# ADR-095: Low-severity findings are grouped by rule in the reports, and listed in full in a file beside them

**Status:** accepted, 11 October 2026, at the owner's word to build the four items the trial needs first ("Go ahead
with those four"), in the pull request that builds it. Proposed the same day in backlog 0250, from a real report in which
76 of 89 findings were low severity and one line per occurrence made the report long.

**Governs:** `crates/sv-report/src/lib.rs` (the grouping, its order and the name of the file), `crates/sv-report/src/markdown.rs`
and `crates/sv-report/src/html.rs` (the one line per rule in each report, and the file of every low finding), and
`crates/sv-cli/src/report_files.rs` (the report folder's seventh file). A pull request that changes these changes this
record too, or says in its description why it does not (`docs/adr/README.md`).

## Context

A report the owner reads should put the findings that matter where they are seen. In the Cursor build's report most of
the findings were low severity, many of them one rule firing in many places, and each took a full section. Nothing about
them was wrong, but a person had to scroll past them to reach the rest.

## Decision

- **In `security.md` and the report page, low-severity findings are one line per rule:** the rule, how many times it
  fired, and the files, most first. Every other finding is shown in full, as before.
- **Every low-severity finding is in full in `low-findings.md`,** beside the report, written and sealed with the other
  report files. When there are none, the file says so.
- **Nothing is dropped and nothing changes what counts.** The count of things to fix is the same; each low finding still
  counts as a finding. `report.json` and `findings.sarif` keep every occurrence, as before.
- **Only low severity in the app's own list is grouped, and never a finding about a key or password.** Findings listed
  apart (in test code, in a bundled library, only worth a look, or outranked) keep the listing they have. Critical, high and medium findings are
  always shown one by one, and so is any finding about a key, whatever its severity: the note on it says whether it reads
  like a real key, and a line per rule would hide that. Information in test code keeps its own section (ADR-091).
- **A group says how many of its findings the baseline holds,** and each is marked in full in `low-findings.md`, so
  comparing with a baseline loses nothing.

## Alternatives considered

- **Group every finding by rule.** A rule that found one serious problem would hide it in a line; only low ones are grouped.
- **Leave the low ones out of the reports.** They would look fixed or never found; the line says how many and where.
- **Only `report.json`.** The person reads the page, not the file a program reads, and `low-findings.md` is readable.

## Consequences

- A report folder now holds seven files; the MCP server offers the new one as a resource, and the scan of an app leaves a
  folder of only these files out, as before.
- Reports with many low findings are shorter on the first screen; a report with none reads as before.
