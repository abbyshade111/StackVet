# ADR-097: The browser's typed-text check on every text form stackvet.toml names

**Status:** accepted, 12 October 2026, in the pull request that builds it. Proposed the same day in the claim of backlog
0232, part 6 (group F). The owner's word of 10 October 2026 asked for more samples in each group, and on 11 October that
the backlog be worked off without asking each time. Built as proposed; one detail is added below, on the forms' tokens.

**Governs:** `crates/sv-manifest/src/lib.rs` (the browser section of stackvet.toml), `crates/sv-manifest/src/spec.rs` (what the spec
says of it), and `crates/sv-check/src/browser.rs` (the check). A pull request that changes these changes this record
too, or says in its description why it does not (`docs/adr/README.md`).

## Context

`probe.text-rendered-as-markup` (V3.2.2, which asks that content meant as text be shown as text, never run as markup)
types a marker that is also markup into the one form `browser.text-form` names, opens the page that shows it
(`shows`, or wherever the form leads), and credits V3.2.2 in part when it is shown as text: one form and one page
(ADR-053, Later). An app usually has several places where a person's text is shown (notes, comments, a profile name),
each perhaps rendered by other code, and the settings have room for one.

## Decision

- **A list beside the one.** `browser.text-forms = [{ form = "/notes/new", shows = "/notes" }, { form = "/profile" }]`
  names several, each with the page that shows what was typed (`shows` left out means wherever the form leads).
  `text-form` and `shows` keep working as one entry; giving both the one and the list is refused with a plain message,
  as other contradictions in stackvet.toml are.
- **Each form typed into.** The same marker, made distinct for each form, is typed into each, and each page that shows
  it is read in the browser. One form whose page runs it is a finding naming that form; the credit names every form
  whose text was shown as text.
- **When the credit is whole.** Only when two or more forms were named, each was typed into and its text found on its
  page, and every one was shown as text. A form that could not be typed into, or whose text was not found, leaves the
  credit in part and says which.
- **A token for each form.** With one form named, its text carries the run's token, as `text-form` always did. With
  several, form `i` carries the run's token with `f<i>z` after it, so no form's token is the start of another's and one
  form's text is never taken for another's on a page that shows both.
- **Nothing else changes.** The other browser checks (the sign-out control, storage after signing out, what pages send
  elsewhere) are not touched.

## Alternatives considered

- **Find the forms by crawling the signed-in pages.** More forms, but the browser would type into forms nobody named,
  some of which change things (a profile, a setting), on a test copy perhaps, but not one the owner chose.
- **Make `text-form` itself a list.** Shorter, but each entry needs its own `shows`, and a list of tables is clearer
  than two lists kept in step.

## Consequences

- An app that names two or more text forms, each shown as text, is *checked* on V3.2.2, not in part.
- stackvet.toml gains one optional key; files without it read as before.

## Later

**14 October 2026: the report says when no form is named** (backlog 0503, found by session documentation answering
0389). With no `browser` table, or one that names no form, the check returned at its first line and the report said
nothing of it, so the reasons under V3.2.2 came from other checks and the owner was not told what one line in
stackvet.toml would let `sv` try. Now the signed-in checks, with no text form named, add a not-assessed line under
V3.2.2 (`browser::NO_TEXT_FORM`): the typed-text check was not made, `sv` looks for no form of its own, and
`browser = { text-form = "...", shows = "..." }` under `[stack.run.users]` makes it. A line in the report only: nothing
is credited or taken away, and no status moves. The backlog item asked for it when the run signs in; it is said
whether or not signing in worked, since it is true either way and the suite holds that every run names each
requirement the correct app's run names (`signed_in::asked_tests`), which a run with a broken sign-in did not. Recorded here rather than in a record of its own, since it says what
this record's check did not do. Held by `crates/sv-check/src/browser/tests/no_text_form_tests.rs`, with no `browser`
table, with one and no form, with a form, and with a sign-in that did not work; and by
`the_browser_is_asked_only_what_securevibe_toml_names`, which before said nothing was reported under V3.2.2.
