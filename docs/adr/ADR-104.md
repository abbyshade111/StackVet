# ADR-104: A pull request that changes only backlog items runs only the tests that read them

**Status:** accepted, 12 October 2026, in the pull request that builds it; proposed the same day with the backlog claim
(0272). The owner asked the same day whether claims could merge without being "so bogged down", and chose this plan
over a separate workflow: "file it and build it before group G".

**Governs:** `.github/workflows/rust.yml` (the test job's first step, and which of its steps run), and
`tools/ci_scope.py` (which pull requests take the short path). A pull request that changes these changes this record
too, or says in its description why it does not (`docs/adr/README.md`).

## Context

`main` requires two checks before a pull request merges, "Decision records" and "test", along with code scanning
(the ruleset "Main - ADR Check"). "test" is the test job of the Rust workflow: formatting, lints, and the whole suite,
about a quarter of an hour on 12 October 2026, whatever the pull request changes. A claim changes one line of one
backlog item, yet it waited as long as a build, and CLAUDE.md has every build wait for its claim to merge. On
12 October #1519, a claim of one new item, took 21 minutes from opening to merge, and #1508, claims and done notes only,
took 30.

The workflow said why it filters nothing by path: the tests read `data/`, `docs/`, and `examples/` as well as the
crates, so a change to a document can break a guard. That is true of most documents (the decision records, the design
entries, CLAUDE.md, and the data files are each read by tests across the suite). It is true of the backlog items only
through four tests: the board's (`backlog_board.rs`), the two that build the documentation pages from every item
(`docs_page.rs`, `docs_page_tabs.rs`), and the one that holds every record number a document cites to a real record
(`decision_records.rs`). The fourth was found by the claim for this record: its first run cited this record's number
before the record existed, and `decision_records.rs` failed it. The short path also runs `record_numbers.rs`, whose tool reads every item's number (backlog
0265), and the new tool's own test.

## Decision

The test job keeps its name and still reports on every pull request. A separate workflow that skipped it would leave
a required check that never reports, and GitHub would block the pull request for good. The job's first step lists the
files the pull request changes, comparing the merge commit GitHub tests with its first parent, the `main` it merges
into. `tools/ci_scope.py` reads that list.

- **Every file is a backlog item:** a Markdown file directly in `docs/backlog/` or `docs/backlog/done/`. The job runs
  the four tests that read them, the numbering tool's (`record_numbers.rs`), and this tool's own, and
  nothing else: no formatting, lints, Docker, rest of the
  suite, or credit log.
- **Anything else:** one other file, no files, a run on `main` (push, nightly, or by hand), or an answer the step
  could not give. The job runs everything, as before. Every gated step asks whether the answer is `false`, not whether
  it is `true`, so a missing or misspelled answer runs the whole suite, not none of it.

The whole suite still runs on every commit to `main` (ADR-051). A fault the short path lets through is found there
within the quarter hour, and fixed forward under CLAUDE.md's rule. Nothing about what `sv` checks, or what a report
says, changes.

## Alternatives considered

- **A separate workflow for claims, with path filters.** Path filters skip a workflow without reporting its check, and
  "test" is required, so a claim would wait forever. Making "test" not required is a repository setting, which is the
  owner's, and would weaken every other pull request.
- **Every document on the short path.** Most documents are read by tests across the suite, so this would let real
  faults through.
- **Running the backlog tools without building `sv-cli`.** Faster, but the four tests assert things the tools alone
  do not, such as the documentation pages' tabs. The short path runs the real tests, so it checks what they check.

## Consequences

- A claim or a done note should merge in a few minutes rather than a quarter hour: the toolchain, one build of `sv-cli`'s
  tests, and five of them. Code scanning is also required and is not shortened by this; how long it takes on a
  claim is still to be measured (backlog 0272).
- `backlog.py done` also rewrites references to a moved item in other files. A done note that does so changes more
  than backlog items and takes the whole suite, as it should.
- A pull request that changes a backlog item and anything else takes the whole suite.
- The short path's only gap is a test outside those four that reads a backlog item. A new test that does must be
  added to the short path's step, or it is first seen failing on `main`.

## Later, 12 October 2026: the short path in the `test` job that waits for the others

ADR-106 split the test job into four. The decision of which path a pull request takes moved into a job of its own,
`scope`, with the same tool and the same fail-safe rule, and the short path's tests now run in `test`, the required
check, which waits for the others. `ci_shards.rs` joins the tests the short path runs, since it reads the folder of
test files a backlog-only pull request cannot change but costs nothing to run. What this record decides is unchanged.
