# ADR-149: Malformed messages are sent to the app's signaling WebSocket, and a normal one after them must still be answered

**Status:** proposed, 24 October 2026, with the claim for backlog 0625's fourth part; accepted in the pull request
that builds it. Held the same day, at the owner's word ("Hold part 4"): a real WebSocket server read frames sent with
the handshake as a second request, so the sidecar must first learn to wait for the server's `101` (backlog 0625,
fourth part's own text). Nothing here is built on `main` until then.

**Governs:** the signaling probe and the stackvet.toml entry that names it (`crates/sv-manifest/src/lib.rs`, and its
line in the starter, `crates/sv-manifest/src/spec.rs`), how a WebSocket request's messages are written after its
handshake (`crates/sv-run/src/docker/probes.rs`), and their tests; the probe's own module is named by its path in the
pull request that builds it. A pull request that changes what is sent, or what an answer concludes, changes this
record too, or says in its description why it does not (`docs/adr/README.md`).

## Context

V17.3.2 (level 2) asks that a WebRTC app's signaling server, the part that passes call setup between two people,
keeps working when it is sent malformed messages. It applies only to apps with WebRTC (the `webrtc` condition). `sv`
already opens WebSocket handshakes to the paths stackvet.toml names (`websocket`, `websockets`), to see whether a
connection from another site is refused (ADR-118), but it has never sent a message over one. The probe sidecar sends
any bytes it is given over a socket with `nc` and reads until the server closes or 15 seconds pass, so a handshake
and the messages after it can go out as one request.

## Decision

- **A new optional entry under `[stack.run]`:** `signaling = { path = "…", message = "…", answer = "…" }`, the signaling
  WebSocket, a message the app answers when all is well (such as a ping, or joining a room), and a word its answer
  holds. Left out, V17.3.2 is not asked, and the report says how to name it. Which message is normal, and what its
  answer looks like, is the app's own, so `sv` does not guess.
- **Three connections, one after another,** to the copy of the app `sv` started, through the probe sidecar:
  1. the normal message alone, whose answer must hold the word, or nothing is concluded (the control);
  2. malformed messages: text that is not JSON, JSON of the wrong shape, a number too large for any field, an empty
     message, and a message far longer than any other; the server may close this connection, which is a fair answer
     to a client sending nonsense;
  3. the normal message again, on a fresh connection, whose answer must still hold the word.
- **What it concludes:** no answer on the third connection, after the first was answered, is a finding: the signaling
  server stopped working for everyone after one client's nonsense. Answered again is credited in part: a few kinds of
  malformed message, one client, one message after.
- **How the messages are written:** after a WebSocket handshake's headers, with no `Content-Length`, as a client writes
  frames, each masked as RFC 6455 asks of a client. Only a request that carries a WebSocket upgrade is written this way;
  every other request is unchanged.

## Alternatives considered

- **Read the signaling code for message validation.** Rejected: whether the server stays up is behavior, which the
  running app shows directly, and validation can be anywhere.
- **Send the malformed and the normal message on one connection.** Rejected: closing a client that sends nonsense is a
  fair answer, and would read as the server stopping.

## Consequences

- A signaling server that falls over, or stops answering, after a malformed message is told so.
- A run with `signaling` named sends three more connections' worth of messages to the app.
