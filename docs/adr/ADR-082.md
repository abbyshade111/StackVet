# ADR-082: What `sv` saw of the running app kept beside the report, with credentials removed

**Status:** accepted, 10 October 2026: every decision is built (see the four "Later" entries below). Was proposed, 9 October 2026, with the backlog claim (0226, part 3, item A). The owner's decision, the same
day: "yes to A, C, and D". Each part is accepted in the pull request that builds it, which says where the build
differs from this plan. Written by session paper-facts. Part 1 (the probe exchanges) accepted 9 October 2026, and
part 2 (what the stand-ins received) 9 October 2026, part 3 (the app's log lines) 10 October 2026, and part 4 (each outside tool's own report, on request) 10 October 2026,
each as built (Later, below).

**Governs:** `crates/sv-cli/src/report_files.rs`, the list of files a report folder holds,
`crates/sv-check/src/secrets.rs`, whose redaction everything kept here passes through, `crates/sv-cli/src/seen.rs`,
which builds the record, `crates/sv-report/src/seen.rs`, which writes it, and `crates/sv-run/src/stand_ins.rs`,
which reads what the stand-ins received, and `crates/sv-check/src/logs.rs`, whose log checks name the lines they read. The files that write the other records
join this list when they are written. A pull request that changes what these say about the kept records
changes this record too, or says in its description why it does not (`docs/adr/README.md`).

## Context

The observability review of 9 October 2026 (backlog 0226) found that `sv` keeps its conclusions and almost nothing of
what it saw. Each probe's response (status, headers, and up to 4,000 characters of body, `ProbeResponse`), the app's
log that the logging credits are read from, what the stand-in services received (the test model's requests, the test
sign-in provider's, the mail), and each outside tool's raw output are held in memory and dropped when the run ends. A
person who asks why a requirement was credited from the running app, or why a probe found something, can read only
the sentence `sv` wrote about it.

## Decision

`sv` keeps a record of what it saw beside the report, in the report folder, every time it writes a report with the
running app, so a person can follow a credit or a finding back to the exchange it rests on.

1. **What is kept.** For each probe request: an id, the method, the path, the status, the response headers, and the
   body excerpt `sv` already keeps. From the stand-in services: the test model's record of what it was sent, the paths
   it was asked for, the sign-in provider's requests, and each mail's recipient, subject, and time (not its body). From
   the app's log: the lines a logging check matched, and a short tail. Each finding and credit read from the running
   app names the ids of the records it rests on.
2. **Credentials removed first.** Everything kept passes through `secrets::redact_text` before it is written, and
   `sv`'s own test accounts' passwords and secrets are replaced as the seed failure already does. A test plants a key
   built from pieces in each kind of record and fails if it reaches the file.
3. **Bounded.** A fixed most per kind of record and in total, with the report saying what was left out.
4. **Under the seal and in the bundle.** The record is one of the report folder's files, sealed with the report
   (ADR-034), and `sv bundle` refuses it as it refuses any file holding a credential.
5. **Said plainly.** The report says the record is there, what it holds, and that it is the app's own text, which can
   hold personal data the app was given during the run (only `sv`'s own test accounts are signed in).
6. **Outside tools' raw output** is kept only when asked for (`--keep-tool-output`), since it can be large and holds
   the app's code; the tool's version, arguments, and exit code are recorded always (review part 2, item 14).

## Alternatives considered

- **Keep nothing more** (today): every "why" answered by prose alone. Rejected by the owner.
- **Keep it outside the app's folder**, beside the history: safer from the AI coding tool's reading, but then it does
  not travel with the report it explains, and the seal could not cover it.
- **Keep it only when asked**: the record would be missing exactly when a surprising result was not expected.

## Consequences

A report folder holds one more file after a run with the app. It holds the app's text, so it needs the same care as
the app's logs: the report says so, and the redaction is tested by breaking it. The paper and the trial scorers can
read probe outcomes from it rather than from the report's words.

## Later, 9 October 2026: part 1 built, the probe exchanges (backlog 0229, part 1)

Accepted for the probe exchanges, as built by session paper-facts. A report folder now holds a sixth file,
`seen.json`, in the one table of report files (`report_files.rs`, and `sv-scan`'s names held to it by the compiler),
so the seal covers it, the MCP server offers it, and `sv bundle` refuses it with any other report file that holds a
credential, each without a list of its own to keep. For each question asked of the running app as somebody not signed
in, it keeps the id, the method, the path, the status, the headers, and the body excerpt the run already held; the
questions that got no answer, or that the app's rate limiter answered, are listed by id; at most 200 answers are kept,
and the file says how many were left out. Where the build differs from the plan above:

- **The file is written every time**, not only after a run with the app: without one it says that nothing was asked
  and why to look in the report. A fixed set of six names keeps every list held to the table the same length, and a
  missing file would read as a report that lost one.
- **Credentials removed, in two passes.** The value of a header that carries a session or a sign-in (`set-cookie`,
  `authorization`, and the others in `SESSION_HEADERS`) is taken out whatever it looks like, keeping the cookie's name
  and its attributes, which the checks read: a session id is random letters, and no rule for keys tells it from any
  other text. Then every header and body goes through `secrets::redact_text`. A test plants a key built from pieces in
  a body and a header, and a session id in a cookie, a sign-in header, and a named JSON value, and fails if any
  reaches the record.
- **A report sealed before this** has no `seen.json`, and its seal was made over five files: it now reads as not
  provably `sv`'s, with the reason saying so and to write the report again. The seal's own rules are unchanged
  (ADR-034, Later, the same day).
- **Not yet built**, and still to come under part 1: the signed-in questions' exchanges (the signed-in suites keep
  their own answers), and each finding and credit naming the ids of the answers it rests on. The ids in `seen.json`
  are the ones the probes read their answers by today, so a reader can match a probe's finding to its answer by the
  check's name, not yet by an id the finding carries.

## Later, 9 October 2026: part 2 built, what the stand-ins received (backlog 0229, part 2)

Accepted for the stand-in services, as built by session paper-facts. None of them sent its record back before: each
kept what it received in its own container, the checks asked it only the questions they needed, and the container
was removed with everything in it. Now, after the last question and before the containers are removed, `sv` reads
each one that ran (`DockerBackend::stand_ins`), and `seen.json` keeps it under `stand_ins`:

- **The test model:** what arrived for each message (the instructions it came with, the model asked for, the tools
  offered, what the app's tools returned, and the rest of what the checks read), and the tags fetched through it, from
  a new `GET /_sv/seen`. It never recorded request headers, so the key the app sends it is not there (and that key is
  `sv`'s own made-up one).
- **The test sign-in provider:** it kept no record before. It now notes each request's method, path, and the names of
  its query's parameters, never their values (a code, a state, a token), and hands them over at `GET /_sv/requests`;
  at most 500, then counted.
- **The mail catcher:** who each message was to, its subject, and when it came; never the body, which holds the reset
  links and codes sent to `sv`'s test accounts. A subject's runs of four or more digits and its web addresses are left
  out too, since an app puts a code there as often as in the body. That also leaves out a year in a subject, which is
  the cost of never keeping a code.

**Credentials removed, in two places.** `sv`'s own test secrets (the accounts' passwords, their two-factor secrets in
base32 in both cases, the sign-in provider's client secret, and the MCP token) are blanked by value in `sv-run`,
before anything is parsed, since only it knows them; the seed failure's blanking now uses the same list. Then
`sv-cli` passes every piece of text in the record, keys included, through `secrets::redact_text`, cuts each at 4,000
characters and each list at 200 entries, and counts what it cut. A stand-in that ran and could not be read is named
under `not_read`, rather than its record reading as empty.

## Later, 10 October 2026: part 3 built, the app's log lines (backlog 0229, part 3)

Accepted for the app's own output, as built by session paper-facts. The log checks found the lines they rest on (a
failed sign-in, a successful one, a refused request to a private page) and kept only a yes or no; the log was dropped
when they returned. Now `logs::evaluate` keeps each line it read a conclusion from, with what it was read for (for
example "the failed sign-in (V16.3.1, V16.2.1, V16.2.2, V16.2.4)"), whether the check then credited or withheld, and
the signed-in suite keeps the last 40 lines of the output beside them. `seen.json` holds both under `app_log`.

`sv`'s test secrets are blanked in the lines by value in `sv-run`, with the same list as the stand-ins' records, since
an app that logs a sign-in with its password logs the test account's; `sv-cli` then passes each line through
`secrets::redact_text` and cuts it at 4,000 characters, counting the cuts. Where the build differs from the plan: the
AI feature's own log check (`ai::logged`) reads the log separately and does not yet name its lines; that stays open
under this part.

## Later, 10 October 2026: part 4 built, each outside tool's own report on request (backlog 0229, part 4)

Accepted for the outside tools' own output, as built by session paper-facts. Each tool's run already kept its version,
arguments, exit code, and time in the report (backlog 0226, part 2, item 14). Its report, the SARIF it wrote, was read
and then thrown away. Now `sv report --tools --keep-tool-output` keeps each one, through `secrets::redact_text`, in
`seen.json` under `tool_output`, with which program wrote it and which rules its findings carry. Where the build differs
from the plan:

- **Opt-in, and only with `--tools`.** The plan said "when asked"; the flag is `--keep-tool-output`, and it is refused
  with a line saying it needs `--tools` rather than silently keeping nothing. `sv bundle` and the MCP server do not
  take it.
- **Never in `report.json`.** A tool's report holds the app's code, so it is held beside the others in `seen.json` only,
  sealed with the report, and the report's own record of the run says whether it was kept (`output_kept`). The
  plan's "records always" part is as built: the version, arguments, and exit code are in every report.
- **Cut at 2,000,000 characters** a tool, with the number cut said in the file.

## Later, 10 October 2026: part 1 built, the signed-in answers (backlog 0229, part 1)

Accepted for the signed-in suite's exchanges with the app, as built by session paper-facts. The signed-in suite sent
its questions and read the answers, but kept neither; each answer was dropped when its check returned. Now a wrapper
over the suite's HTTP (`signed_in/recording.rs`) keeps each question the app was sent and what it answered, in order,
and `seen.json` holds them under `signed_in`, numbered `signed-in-N`. A question with no answer is counted, not kept.
Where the build differs from the plan:

- **A request's headers and body are never kept.** The plan said "the request and the response"; the request carries
  the test accounts' passwords and session cookies, so only its method and path are kept, and the path with its
  credentials cut.
- **Only the app's answers.** The test model's and the test sign-in provider's answers are stand-ins' records, kept
  with the other stand-ins (part 2), and are not in `signed_in`.
- **Found by the real run, and fixed in this part.** A test password sent in an address is written with its `!` as
  `%21`, so blanking the raw text missed it; and the generic credential rule then took the blanking marker's first word
  for a password's value and cut it. Test secrets are now blanked in both forms, and the markers are left whole when
  the record is redacted. The stand-in records and the log lines take both fixes, since they share the same code.
- **Still open under part 1:** each finding and credit naming the answers it rests on. A finding has no id today, so
  that is a change to the finding type and every check that makes one, which this part does not make.

## Later, 10 October 2026: part 1's finding ids, for the probes (backlog 0229, part 1)

Accepted for the probes' findings, as built by session paper-facts. A finding named no answer before; a person could
read a finding's sentence but not which of the running app's answers it was read from. A finding now carries
`evidence`: the ids of those answers, the same ids `seen.json` keeps them under (`home`, `cors`, `trace`, and so on).
A finding that rests on none of the running app's answers keeps an empty list, and the field is left out of the
record then. Where the build differs from the plan:

- **The probes only, for now.** Every probe finding names its answers: the content-type, cookie, security-header, CORS,
  TRACE, error-page, JSON-callback, reflection, log, console, exposed-file, version, opener-policy, and CSP checks, and
  the GraphQL and WebSocket checks. Each names only the answers its condition was read from, collected as the check runs.
  The signed-in findings name none yet; in the real run those are the four signed-in findings (signup, upload, SVG,
  breached password), and that is the next piece of part 1.
- **Credits are not named yet.** A credit (`Verified`) keeps its own text and no ids; that is part of the same next piece.
- **The field is on every finding**, so `report.json` gains an `evidence` list for the findings that have one. Findings
  from the scan (secrets, code, configuration) carry an empty list, which is left out.

## Later, 10 October 2026: the signed-in credits name their answers, and the crash sweep reaches them (backlog 0229, part 1)

Built by session credit-names. Every signed-in credit site now names the answers it read, through its entry in the crash
sweep's table (`RESTS_ON_A_REFUSAL`), so no signed-in credit is left naming none. Sixteen rules were added to the table.
Three entries that named answers the checks never send were corrected:

- The step-skipped check named `flow-flow-b`. The check sends `login-flow-b0` to `login-flow-b2`, and the table now lists those.
- The done-twice check named `once`. It sends `once-a` and `once-b`, so the table names the `once-` prefix and its finding
  names those two.
- The wrong-current-password check named `private-wrong-current`, which is never sent. That name is dropped.

The crash sweep needs each listed rule found at fault by one of its scripted runs. Fifteen of the new rules had no such run,
so fifteen scenarios were added. Each switches on a flaw the scripted app already has, the same flaw the rule's own test
uses. A new test, `every_name_in_the_table_is_an_answer_some_run_sends`, fails on any name that no scenario's run sends, so a
misspelt name cannot leave a credit unnamed while the tests still pass.

Still open under part 1: the four running-app credits (grants, admin-by-address, private files, stayed-up). They read their
answers through their own helpers and are not in the table.

Tests, and what catches a break:

- `a_crash_never_turns_a_finding_into_a_pass` passes with the new scenarios. Break: the form scenario's flaw switched off, so
  the step no longer raises the rule. The sweep fails with `no scenario found these at fault: ["probe.preflight-skipped"]`.
- `every_name_in_the_table_is_an_answer_some_run_sends`. Break: `admin-action-` misspelt as `admin-actoin-`. The test fails,
  naming `probe.admin-action-ordinary-user: admin-actoin-`.
- The sv-check library tests: 1,437 pass, with `cargo fmt` and `cargo clippy --workspace --all-targets -D warnings` clean.
- Each break was restored by `git checkout` after the tree was committed, and the tree was clean afterwards.

## Later, 10 October 2026: the container's readings are kept, and the stayed-up credit names them (backlog 0229, part 1)

Built by session credit-names, as the owner chose between the two ways of closing the stayed-up credit: keep the readings,
and name them. `seen.json` gains `liveness`, one entry per reading of the app's container, taken between the stages of the
questions: its state from `docker inspect`, its restart count, its exit code, whether it ran out of memory, and whether its
health path answered. Each is numbered `liveness-N`, in the order taken. These describe the container, not the app's
answers, and the record says so by its field name. Their text goes through `redact_text` like the rest, and any credential
cut from it is counted.

The stayed-up credit names every reading it read. The stopped finding names the reading that showed the stop. With this, all
four running-app credits name their answers, and part 1 is done.

  Break: ids numbered from zero. The test fails with `["liveness-0", "liveness-1"]`.
- `tests/seen_record.rs` now also requires `liveness-1` in `seen.json` after a real run. CI runs it; it was not run locally,
