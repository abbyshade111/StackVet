# ADR-117: Rich text and user-supplied markup are asked about, and an AI feature is one way in

**Status:** accepted, 14 October 2026, in the pull request that builds it (backlog 0505). The decision is the owner's,
asked through the coordination board's waiting line and answered the same day: option A of three, "A new rich-text
capability in stackvet.toml, asked like the others; unanswered, V1.3.1 and V1.3.5 are not assessed; yes, or an AI
feature, makes them apply." Written by session wording.

**Governs:** `crates/sv-frameworks/src/condition.rs::RichText`, the rich-text field in
`crates/sv-manifest/src/lib.rs::Capabilities` and its claim, the line asking it in
`crates/sv-manifest/src/spec.rs::STARTER_MANIFEST`, and the four rules at V1.3.1 and V1.3.5 in
`data/applicability-v2.json`. A pull request that changes what turns either requirement on, or how an unanswered
`rich-text` is read, changes this record too, or says in its description why it does not (`docs/adr/README.md`).

## Context

V1.3.1 (level 1) asks that "all untrusted HTML input from WYSIWYG editors or similar is sanitized using a well-known
and secure HTML sanitization library or framework feature". V1.3.5 (level 2) asks that "the application sanitizes or
disables user-supplied scriptable or expression template language content, such as Markdown, CSS or XSL stylesheets,
BBCode, or similar". Neither says anything about AI. Both were gated on `ai` alone in
`data/knowledge/applicability.json`, a rule from SecureVibe v1, whose own app had no editor and showed people's text
as plain text, and whose AI feature's answers were the only HTML that could reach a page. `sv` checks other people's
apps, so an app with a rich-text editor, or comments written in Markdown, and no AI feature had both ruled out as not
applying, with nothing to show it had neither. Backlog 0403 had already reworded their reasons to say only what the
`ai` condition establishes; the gating stayed. Found by session wording building 0403 (backlog 0505).

## Decision

- **A new question, `rich-text`, under `[capabilities]`:** does the app take formatted text that people supply and
  show it, rich text from an editor, or Markdown, stylesheets, templates, BBCode, or similar? It is a claim like the
  others (`Condition::RichText`, source `claim`): it starts commented out in the starter file, and nothing in the code
  corroborates it yet, so an answer is taken on the owner's word and the report says so.
- **V1.3.1 and V1.3.5 each have two rules, OR-ed:** one on `rich-text`, one on `ai`. So either answered yes makes
  them apply; both answered no rules them out, with a reason that names both ("takes no rich text from an editor ...
  and has no AI feature whose answers it shows"); and `rich-text` unanswered, with no AI feature, leaves them not
  assessed, blocked on that one question, never ruled out (ADR-015: silence is not a "no"). With an AI feature, the
  unanswered question no longer matters: they apply.
- The v1 rules in `data/knowledge/applicability.json` stay as they are; the v2 rules replace them at their scope, as
  every v2 rule does.

## Alternatives considered

- **Both apply to every app** (option B): never wrong to ask, but an app that shows only plain text would carry two
  requirements nothing could ever settle, one at level 1.
- **Leave them on `ai` alone** (option C): the gap this record closes.
- **Find an editor or a Markdown library in the code and answer for the owner:** a library found would be a yes
  worth having, and may come later as a corroborator; finding none settles nothing (ADR-015), so it could not stand
  in for the question.

## Consequences

- Every app whose stackvet.toml does not answer `rich-text` and has no AI feature now has V1.3.1 and V1.3.5 not
  assessed, where they were ruled out: one more question on its open list, and its counts move by two from "does not
  apply" to "not assessed" (at level 1, one). No check credits either; they are not verified wherever they apply.
- Held by `crates/sv-frameworks/tests/rich_text.rs` (every no rules both out with a reason naming both; `rich-text`
  alone or an AI feature alone makes both apply; unanswered with no AI leaves both not assessed on `rich-text` alone)
  and `crates/sv-manifest/src/rich_text_condition_tests.rs` (the answer is read as given, an unanswered one stays
  unanswered, and the starter file asks it commented out). Each went red with its part undone.

## Later, 15 October 2026: how many requirements rest on a "no" nobody checked is counted, and whose word each answer is (backlog 0600)

In the clean Cursor and Flash run of 15 October 2026 (backlog 0577), the tool answered `false` on thirteen capability
lines it had not checked; "does not apply" rose to 79 on those answers alone, and nothing in the summary said how many
rested on them. Now, under the counts in compliance.md and the HTML report, one line counts the requirements that do
not apply only because stackvet.toml says no (each exclusion whose source is a claim the file answers `false`), names
those answers, and says `sv` did not check them (`sv_report::resting_on_a_no`); there is no line when none does. An
exclusion on the code's word, or on a yes (`no-auth`, from `auth = true`), is not counted. The table "What the app says
about itself" gains a column, "who said it": a capability line in stackvet.toml records nobody, so an answer given
there is read as the AI coding tool's, as a design answer with no `by` is, and the JSON report carries it as `by =
"ai-tool"`; an unanswered one reads "nobody". How a "no" is read does not change: it still rules requirements out
(ADR-015, backlog 0332), and the line only says on whose word. A way for a person to confirm a capability answer in
`sv review` is not built here; it is filed as backlog 0606. Held by `crates/sv-report/src/resting_on_a_no_tests.rs`
and `crates/sv-cli/tests/resting_on_a_no.rs`, each of which went red with its part undone.

## Later, 16 October 2026: a capability answer the owner confirmed is labeled theirs, and nothing more (backlog 0606)

The owner chose this on 16 October 2026. A capability line under `[capabilities]` is a bare `true` or `false` that
records nobody, so since backlog 0600 the report reads each as the AI coding tool's word. `sv review` now lists every
answer stackvet.toml gives, each with the plain question it answers, and the owner may confirm them all as theirs; it
seals `[capabilities-review]` over who, when, and each answer by its condition's name
(`crates/sv-check/src/capabilities_word.rs`). While an answer still says what was confirmed, the report shows it as
"yours, confirmed through `sv review`" (`sv_report::mark_confirmed`), and the sentence on requirements that do not
apply because of a "no" names those answers as the owner's, apart from the ones nobody recorded.

It changes nothing else, which was the choice: a confirmed "no" switches no requirement off, weighs no more in any
count, and the number of requirements resting on a "no" is the same. A person can miss what an AI tool added last
week, and ADR-015's rule stands: what the owner says never removes a requirement. An answer changed after it was
confirmed is unconfirmed again, the others staying confirmed; an entry written by hand without a seal that holds
confirms nothing. What is offered is the answers given under `[capabilities]` and `[repository]`: whether the app is
on the internet and held to level 2 come from `[app]` and `[data]`, which `[scope-review]` already confirms, and `tls`
is a setting with a default, so none of the three is offered, and an app that gives no capability answer is not asked.
Held by `crates/sv-cli/src/review/capabilities_tests.rs` and
`crates/sv-report/src/confirmed_claims_tests.rs`.
