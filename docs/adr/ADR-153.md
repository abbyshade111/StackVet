# ADR-153: `sv connect --docker` works on Windows: a Windows Docker path, the folder at a Linux-style path, and paths handed back in Windows form

**Status:** proposed, 25 October 2026, with the claim for backlog 0375; accepted in the pull request that builds it,
and the item done once the owner has tried it on Windows.

**Governs:** the settings that connecting through Docker writes (`crates/sv-cli/src/connect.rs`), and the MCP server's turning
of paths it hands back into the person's own form, which the pull request that builds it names by its path. A pull
request that changes how a Windows path is mounted or handed back changes this record too, or says in its
description why it does not (`docs/adr/README.md`).

## Context

On 12 October 2026 the owner chose the Windows route as StackVet installed with Scoop and connected with
`stackvet connect TOOL`, no Docker, with this fix left for later (ADR-108, Later; backlog 0375). Two things stop
`sv connect --docker` on Windows: it refuses a Docker path that does not start with `/`, and Docker on Windows is
`C:\Program Files\Docker\...\docker.exe`; and the settings show the app's folder inside the container at the same path
(`-v FOLDER:FOLDER`), and `C:\Users\you\app` is no path inside a Linux container.

On 25 October 2026 the owner asked to reopen 0375 "to fix the Windows docker issue(s)". Asked how to try it, since
GitHub's Windows runners run Windows containers alone, the owner chose: "Build, you try it". Asked what it should
cover, the owner chose: "connect --docker only".

## Decision

- **A Windows Docker path is taken** when `sv connect` runs on Windows: a full path from a drive's root
  (`C:\...\docker.exe`), read as `--keys` already reads one.
- **The app's folder is shown inside the container at a Linux-style path:** its drive letter, in lower case, then the
  rest with `/` for `\` (`C:\Users\you\app` is `/c/Users/you/app`). Docker Desktop is given the Windows path on the
  left of `-v`, which it reads, and the server's `--root` is the path inside.
- **What StackVet hands back is in the person's form.** The container is told the folder's Windows form in an
  environment variable, and the MCP server, where a path it returns is under its root, writes it under the Windows
  folder instead, so a report's links and a finding's file open in the AI tool on Windows. Nothing the checks read or
  conclude changes; only how a path is written in what is handed back.
- **Elsewhere nothing changes:** on Mac and Linux, and with an installed `sv`, the settings are as they were.
- **Tried by the owner:** the pull request carries a short guide for trying it on a Windows computer with Docker
  Desktop set to Linux containers, and backlog 0375 stays open until the owner's try confirms it.
- **Not covered:** `sv report --run` on Windows, which starts the app's own containers and is untried there by hand.

## Alternatives considered

- **Leave Windows to the Scoop route alone,** as chosen on 12 October 2026. The owner has now asked for the fix.
- **Mount the folder at a fixed place, such as `/app`,** and hand back paths under it. Rejected: two apps connected
  at once would both be `/app`, and a path under `/app` means nothing to the person either.
- **Build and merge on unit tests alone.** The owner chose to try it first.

## Consequences

- A person on Windows with Docker Desktop can connect their AI tool to StackVet in Docker, as on a Mac.
- The Scoop route stays the one the guide gives first for Windows until the owner's try confirms this one.
