# ADR-111: The outside tools run with every `sv report` and `sv bundle` unless `--no-tools` is given

**Status:** accepted, 13 October 2026, in the pull request that builds it (backlog 0394); proposed the same day
with the claim. The decision is the owner's: "yes, please file it and build after the report". Told before the build
that Semgrep fetches its rules from semgrep.dev every time it runs, the owner chose, of three ways, "Everything on,
Semgrep connects", over keeping Semgrep behind `--tools` until it can run from rules downloaded once, and over
waiting for that.

**Governs:** `crates/sv-cli/src/main.rs` and `crates/sv-cli/src/commands.rs` (the flags), `crates/sv-cli/src/lib.rs` (what a run without the tools says),
`action.yml` (it passes the option that leaves the tools out), and `.cargo/config.toml` (the tests' switch).
A pull request that changes these changes this record too, or says in its description why it does not
(`docs/adr/README.md`).

## Context

Until now the outside tools (Bandit, Semgrep, CodeQL, gosec, Brakeman, and the rest) ran only with `--tools`. The
owner has found their findings the most important ones a report holds, and a report made without the flag, which is
most of them, has none. On the haiku-a-5 trial app (12 October 2026) the tools added 20 seconds to a 21-second
report, 17 of them Semgrep's; CodeQL was not installed and the report said so, with how to install it. CodeQL builds
a database of the app first, and takes minutes on a larger app.

## Decision

1. **`sv report` and `sv bundle` run the outside tools by default.** `--no-tools` leaves them out. `--tools` is still
   accepted and changes nothing.
2. **A tool that is not installed is not a failure.** The "Outside tools" section says which ran, with their
   versions, and which did not and why. It changes the exit status only with `--fail-on not-assessed` (ADR-029).
3. **The MCP server is unchanged.** It still never runs them (ADR-066, decision 1).
4. **The GitHub Action passes `--no-tools`.** Its image carries none of the tools (ADR-081). It asks the image's own
   help first, so an image from before this record, which never ran them and does not know the option, still runs.
5. **Semgrep's connection to semgrep.dev comes with the default.** It is Semgrep's, not `sv`'s, and is named where
   `sv`'s network rule is (`CLAUDE.md`, the README): a report reaches semgrep.dev unless `--no-tools` is given or
   Semgrep is not installed. The run it makes is otherwise unchanged (`--metrics=off`).
6. **The tests do not run the tools.** `.cargo/config.toml` sets `SV_NO_TOOLS_FOR_TEST` for every process cargo
   starts, which only a debug build of `sv` reads, so a test runs the same with Semgrep installed as on CI without
   it, and never reaches semgrep.dev; `crates/sv-cli/tests/tools_by_default.rs` takes it away to test the default.

## Consequences

- A plain `sv report` takes longer: seconds on a small app, minutes when CodeQL is installed and the app is large.
  The progress lines name each tool as it starts, and `--no-tools` is the quick run.
- Every person who runs `sv` with Semgrep installed now runs the Semgrep rules, under the Semgrep Rules License,
  which allows them for internal use and not for resale; `sv` uses them only while nothing built on them is sold
  (the owner's condition of 26 September 2026), and the README says so where it describes the default.
- The tools run in the app's folder with the guards ADR-032 records; the default puts them in front of more apps,
  and those guards are unchanged.

## Later, 14 October 2026: the three places the words were not brought to

The decision's words reached `sv report --help`, the README, the guide, and the prompts, and three places still said
the tools need `--tools` (backlog 0429). The report's "Outside tools" section, when none ran, said "They run only with
`sv report --tools`"; it now says they run with every `sv report` at a terminal unless `--no-tools` is given, and that
the MCP server and the GitHub Action never run them, which is when that sentence appears. The short version's line of
what did not run, and `tools/coverage.py`'s words for the tools' kind of run in `docs/COVERAGE.md`,
`docs/REQUIREMENTS.md`, and `data/reach.json`, say the same. `sv bundle --help` names the tools running unless
`--no-tools` and Semgrep's connection to semgrep.dev, as `sv report --help` does (decision 5). A test holds `sv-report`'s
code to never naming `--tools`. What this record decides is unchanged.

## Later, 14 October 2026: CodeQL runs only when the owner turns it on (ADR-115)

CodeQL's license allows it only on an app released under an open-source license, for academic research, or with a
paid GitHub Advanced Security license. The owner chose on 13 October 2026 to keep it, off unless `stackvet.toml` turns
it on (`[tools] codeql = true`); off, it is not run and not named. The other outside tools still run with every
`sv report` unless `--no-tools`. ADR-115 records the decision.

**15 October 2026: a finding from a rule written for a framework the app does not use decides nothing (backlog
0521).** A Semgrep rule mapping may name its web framework (`framework` in `data/adapters.json`, written by
`tools/semgrep_rule_map.py`). Once the outside tools have run, a finding from such a rule is listed apart
(`Outranked::OtherFramework`) when the app's package lists in that framework's language were all read and none names
it, and is shown with that reason; it withholds no credit and sets no status. Without such a list, or with one
unread, whether the app uses the framework is not known and the finding counts as before. Template-only rules in the
Flask, Express, Rails, and Laravel packs are left untagged, as the template engine's.


**15 October 2026: Semgrep's rule for credentials written to a log decides nothing on a line that logs only ids
(backlog 0583).** `python-logger-credential-disclosure` fires on any logger call whose message mentions a password,
token, secret, credential, or API key and has a `%s`, whatever the call logs; in the Opus run of 15 October 2026 it
fired four times on lines logging a user id or a game id. Once the outside tools have run, `sv` reads the call the
finding points at (`crates/sv-check/src/logged_ids.rs`), and when its message is a plain string and every value it
logs is a name whose last part is an id (`id`, `user_id`, `game.id`, `accountId`, `uuid`) with no part named for a
secret (password, token, key, secret, credential, cookie, session), the finding is listed apart
(`Outranked::LogsOnlyIds`), shown with the names it logs, and withholds no credit. A message built with `%`, `+`,
`.format`, or an f-string, a value that is not a plain name, an `extra=` mapping, a call `sv` cannot follow, a finding
another tool also made, or one sharing its line with a problem of another kind, leaves the finding counting as before.
The rule is not set aside by name: a line that logs a password still counts. Held by
`crates/sv-check/src/logged_ids/tests.rs`, `crates/sv-check/tests/logged_ids.rs`, and
`crates/sv-report/tests/logged_ids.rs`, each of which went red with its part undone; nothing runs Semgrep itself in
these tests.

## Later, 20 October 2026: a rule's finding in a file of another language is listed apart (backlog 0615)

Semgrep's insecure-WebSocket rule is a text pattern that matched `ws://` in Rust comments, and was the only thing
behind V4.4.1 needing attention on `sv`'s own code. The owner chose on 20 October 2026 to give the rule the languages
it was written for, JavaScript and TypeScript, and to have `sv` set apart a match in a file of another language and
say so. `adapters::set_apart_other_languages` does it for any mapped rule that names its languages and no files of its
own, when the file's extension is outside all their parsers (`SEMGREP_EXTENSIONS`): the finding is
`Outranked::OtherLanguage`, listed apart like a framework the app does not use (Later, 14 October 2026), and decides
nothing. A rule of any language, or one whose `paths.include` names its files, is never judged by extension. The
rule's languages also narrow what a clean run of it credits, as they do for every rule: V12.3.1 from this rule only
for an app in JavaScript or TypeScript. `sv`'s own `ast.plaintext-websocket-url` still reads the address in code.

## Later, 21 October 2026: the table of commands moved into `commands.rs` (backlog 0324)

`sv`'s table of commands and the options each takes, where `--no-tools` is declared, moved out of `crates/sv-cli/src/main.rs`
into `crates/sv-cli/src/commands.rs`, word for word; `main.rs` still reads the option and acts on it. The Governs list
names both files. Nothing this record decides changes, and `sv --help` reads the same.

## Later, 23 October 2026: Bandit's B104 in a container is worth a look

Backlog 0658, at the owner's answer to backlog 0648's survey ("Container: worth a look (Recommended)"). `sv preflight`
tells an app to listen on every address (ADR-035), since inside the container `sv` starts it in that is the only way
to be reached, and Bandit's B104 reported that line as a thing to fix in 4 of 12 apps surveyed. When stackvet.toml runs
the app in a container (`[stack.run]` with an image and a start command), a B104 finding nothing else reported is set
apart as `ListensInContainer`: listed apart as worth a look, said beside it, and unlike the other reasons set apart
here, still counted, since outside a container the same line puts the app on the local network. Re-deciding what a
report lists apart keeps it, unless the finding is about a requirement the app is not held to. Held by
`crates/sv-check/src/adapters/listens_in_container_tests.rs` and `crates/sv-report/src/listens_in_container_tests.rs`:
with the reason added to those that decide nothing, or not put back after re-deciding, each fails.
