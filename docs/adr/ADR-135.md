# ADR-135: A program started with its arguments as a list, and no shell, is not a shell command built from a value

**Status:** accepted, 23 October 2026, in the pull request that builds it; proposed the same day with the claim for
backlog 0643, from the triage of StackVet's findings on its own repository (backlog 0633), which asks that a rule found
wrong is fixed, with a test that it still fires where it should.

**Governs:** `data/ast-rules.json` (the shell-command rule's Rust and Go queries, the names they match, and what the
report says they read), and its tests, `crates/sv-check/src/ast/shell_list_tests.rs` and the Rust and Go witnesses in
`crates/sv-check/src/ast/tests.rs`. A pull request that changes what `ast.shell-command` reads in Rust or Go changes this
record too, or says in its description why it does not (`docs/adr/README.md`).

## Context

`ast.shell-command` (V1.2.5, CWE-78) flags a command line built from a value and handed to a shell. In Rust it also
matches `Command::new(value)`, and in Go `exec.Command(value)`. Both start the named program with its arguments as a
list, and no shell reads them. StackVet's report on itself listed 16 such lines, every one of them this. V1.2.5 asks
that "operating system calls use parameterized OS queries or use contextual command-line output encoding": a list of
arguments is that parameterized call.

## Decision

- **In Rust and Go, the rule flags a shell named in the code,** `Command::new("sh")` (or `bash`, `zsh`, `dash`, with or
  without `/bin/` or `/usr/bin/`) given `-c` and a value, and `exec.Command("sh", "-c", value)`. These alternatives are
  already in the rule and stay.
- **A program started by `Command::new(value)` or `exec.Command(value)` with no shell is not a finding of this rule.**
  Which program a value names is another question (a program path from a stranger), and this rule does not say it
  answers it.
- **The rule's description for Rust and Go** (`looksForIn`) says what it reads, so the report's "what this looked for"
  is true.
- Held by a test that the shell forms still fire and the plain ones do not, in both languages.

## Where the build differs

- **A shell in a variable is still found.** The rule's Rust case `Command::new(exe)` was written on 25 September 2026
  so that "a shell named by a variable" would not be missed: it reported every `Command::new(value)`, whatever the
  arguments. Dropping it alone would have lost that. So the rule now reads the `-c`: a program, however it is named,
  given `-c` and then a value (`Command::new(shell).arg("-c").arg(cmd)`, `.args(["-c", cmd])`,
  `exec.Command(shell, "-c", cmd)`, `exec.CommandContext(ctx, shell, "-c", cmd)`) is a shell command built from a value.
  A program given `-c` that is not a shell (`git -c name=value`) is reported too; that can set what git runs, so it is
  worth a look.
- **What is missed:** a shell held in a variable and given its command without a `-c` written out beside it (the `-c` in
  a variable too, or in a list built elsewhere). The rule did not follow a list built in another statement before
  either.
- **Held by** `shell_list_tests.rs`: with the rule as it was, both of its tests fail; with the `-c` alternatives taken
  out, the second fails.
