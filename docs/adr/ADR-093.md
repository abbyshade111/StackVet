# ADR-093: A reviewer can say a test-file information finding is real, and then it counts

**Status:** accepted, 11 October 2026, at the owner's word ("let's go with option 1, a sealed entry"), in the pull request
that builds it. Proposed the same day in backlog 0259, as the step ADR-091 left not built.

**Governs:** `crates/sv-check/src/review.rs` (the verdict `counts`, what `judge` accepts for it, and the fingerprints
`apply` returns as counting), and `crates/sv-cli/src/assemble.rs` (the split that keeps test-file information out of the
findings, which now keeps a counted one in). A pull request that changes these changes this record too, or says in its
description why it does not (`docs/adr/README.md`).

## Context

ADR-091 keeps four Bandit rules in test code out of the findings, as information that a person reviews. It left the review
step to be built: a reviewer who reads one and finds it real had no way to make it count, so a real key or fault in a test
file could stay information for good. The review step already exists for findings a person sets aside, in
`[[finding-review]]` entries that `sv review` seals, and that is the path this decision takes.

## Decision

- **A new verdict, `counts`,** in a `[[finding-review]]` entry, says the reviewer has read a test-file information finding
  and it is real. It is valid only for a finding that is information (ADR-091): on any other finding the entry is refused,
  with a reason.
- **Only a sealed entry counts.** A `counts` entry that a person has not recorded through `sv review` is a proposal, and
  the finding stays information. The AI coding tool's own proposal does not count, as with the other two verdicts.
- **A counted finding is a finding.** It is in the findings list, and the report counts it as one; it is no longer in the
  information list. Nothing is hidden: the report's entry for it is the same as any finding.
- **It is not an accepted risk.** The verdict `accepted-risk` is for a real problem lived with for now, and it does not
  apply here; `counts` says the finding is a problem, and the fix is the reviewer's own decision.

## Alternatives considered

- **Move the rule out of the information list for that file.** A file-wide switch would make every finding in it count,
  including the ones a reviewer has not read, so the choice is per finding.
- **A separate file of verdicts.** A second place for decisions, with its own seal; the existing entries already carry
  the seal, the name of the person and the date.
- **Let the AI coding tool mark it.** It would make the tool's own word count as a finding, which the seal is there to
  prevent for every other verdict too.

## Consequences

- Reports with a counted test-file finding show one more finding, with its rule and file, and the information headline
  says one fewer item.
- The verdict list in `sv review` and in the guide gains `counts`; the guide says what it is for.
