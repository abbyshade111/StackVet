# ADR-156: A report's results exported as OSCAL assessment results, through a crosswalk from ASVS to NIST SP 800-53 chosen by reading both texts

**Status:** proposed, 26 October 2026, with backlog 0678; accepted in the pull request that builds it, which says
where the build differs from this plan. Asked for by the owner on 26 October 2026, after a conversation about fitting
StackVet into a DevSecOps and continuous-authorization (cATO) pipeline: "add a backlog item (with a proposed ADR) for
an ASVS-to-NIST 800-53 crosswalk and an OSCAL assessment-results export from report.json". Nothing here is built on
`main` until then.

**Governs:** what `report.json` holds, which the export reads (`crates/sv-report/src/json.rs`), and the Secure by
Design crosswalk's guard, which the new crosswalk is held to the same way (`crates/sv-check/tests/citations.rs`). The
crosswalk's data file, the script that keeps its control titles true to NIST's catalog, and the export's own module
are named by their paths in the pull request that builds them. A pull request that changes what a status is exported
as, or how a pair in the crosswalk is chosen, changes this record too, or says in its description why it does not
(`docs/adr/README.md`).

## Context

A continuous authorization to operate rests on evidence about a system's controls that arrives with every change, in
a form the authorizing official's tools read. In the federal and defense world those controls are NIST SP 800-53
Rev. 5's, and the machine-readable form is NIST's OSCAL (Open Security Controls Assessment Language), whose
*assessment results* model carries what an assessment observed, how (`EXAMINE`, `INTERVIEW`, or `TEST`), and what it
concluded about each objective.

`sv` grades an app against OWASP ASVS 5.0, AISVS 1.0, and the Secure by Design checklist, and writes what it concluded
as `report.json`, with every requirement in one of nine statuses (`Status` in `crates/sv-report/src/lib.rs`). None of
that reaches 800-53 today:

- **No mapping exists in `sv`.** ASVS 5.0's own text cites NIST SP 800-63B and SP 800-57 but never 800-53
  (`data/frameworks/asvs-5.0.0.json`). AISVS Appendix C's `mappings` field names 800-53 Rev. 5 for three of its 68
  requirements, and nothing reads that field.
- **No export exists.** A pipeline can keep `report.json`, `stackvet.sarif`, and `sbom.cdx.json` with each build, but a
  governance, risk, and compliance tool cannot read the first as control evidence without a converter, and SARIF
  carries findings, not the requirements that were checked and found sound.

The statuses already line up with OSCAL's three assessment methods, which is what makes an export worth having:
*checked* and *checked in part* are tests `sv` ran, *tested by the app's own tests* is a test the app ran, *documented*
is a document read, and *attested*, *checked by hand*, and *stated* are someone's word. And `sv`'s first rule,
something not assessed is never a pass and never a failure, is the rule an assessor needs from automated evidence.

## Decision (proposed)

1. **A crosswalk from each ASVS 5.0 requirement to the 800-53 Rev. 5 controls and enhancements that ask the same
   thing**, built as `data/sbd-asvs-crosswalk.json` was: chosen by reading both texts, each pair carrying a few words
   naming what the two ask in common, those words held by the citation guard to share vocabulary with both texts
   (`crates/sv-check/tests/citations.rs`), and every requirement listed, an empty list when nothing in 800-53 asks the
   same thing, so a new requirement cannot default silently. A pair means "asks the same thing", never "satisfies":
   800-53 controls are broader than any one ASVS requirement, and the crosswalk is many-to-many.
2. **The control titles and statements are NIST's, never written by hand:** a maintenance script, like
   `tools/atlas_references.py`, reads them from a pinned release of NIST's OSCAL catalog for 800-53 Rev. 5 and writes
   them into the data file, naming any cited control a newer release renames and refusing one it withdraws. It is run
   by whoever maintains the data, outside the sandbox. `sv` itself fetches nothing: the fence is unchanged.
3. **An export that reads a finished report and writes OSCAL assessment results**, run only when asked (proposed:
   `sv export --oscal <report folder>`), so a report folder holds nothing new unless the person asks for it. It
   records, for each requirement that applies:
   - **an observation**, with its method from the status: *checked*, *checked in part*, and *tested by the app's own
     tests* are `TEST`; *documented* is `EXAMINE`; *attested*, *checked by hand*, and *stated* are `INTERVIEW`. Its
     origin names who it rests on: `sv` as the assessment platform for its own checks, the app's tests for theirs, the
     owner for their sealed answers (ADR-026), and the AI coding tool for *stated*, never the owner;
   - **a finding with a concluded state only where `sv` concluded one:** *needs attention* is `not-satisfied` (reason
     `fail`), and *checked* is `satisfied` (reason `pass`) for the ASVS requirement's own objective. *Checked in part*
     and every answer tier are never `satisfied`: they are reported with the status `sv` gave them, and the export says
     so in words. *Not verified* is listed as not verified, never as either state;
   - **the 800-53 controls from the crosswalk as related controls of the ASVS objective, never as a verdict on the
     control.** No 800-53 control is marked satisfied from `sv`'s evidence alone.
4. **The export carries its provenance:** the report's seal (ADR-034), `sv`'s version and commit, the image digest
   when it ran in the published image (ADR-080), the commit of the app, and the date. A report whose seal does not show
   `sv` wrote it is refused, as it is over MCP.
5. **Held by tests against NIST's own schema:** the OSCAL JSON schema for the pinned version is committed beside the
   crosswalk, so the tests validate offline. One test breaks the status mapping on purpose (*checked in part* exported
   as `satisfied`) and must go red.

## Alternatives considered

- **Start from OpenCRE's links between ASVS and 800-53.** Worth reading as a first draft of the pairs, but not taken as
  given: a citation is a claim, and each pair is kept only after reading both texts and passing the guard.
- **Leave it to the pipeline to convert SARIF.** Rejected as the only route: SARIF carries findings, not requirements
  checked and found sound, nor the difference between a test and someone's word.
- **Mark an 800-53 control satisfied when every ASVS requirement mapped to it is checked.** Rejected: the crosswalk says
  two texts ask the same thing in part, not that ASVS covers a control. That would make `sv`'s evidence look stronger
  than it is, which the project's first rule forbids.
- **Write the OSCAL file into every report folder.** Not proposed: it adds a file to someone's folder by default, which
  is the owner's call (the first question below).
- **Send the results to eMASS or a GRC tool directly.** Rejected: it would open a connection of `sv`'s own and need an
  account. The pipeline uploads what `sv` writes.

## Consequences

- A cATO pipeline can read `sv`'s evidence for the application layer as OSCAL assessment results, with each result's
  method and source, alongside the infrastructure and operations evidence other tools give.
- The cost is the crosswalk itself: 345 ASVS requirements read against 800-53's controls and enhancements, and kept
  true as either changes. AISVS and Secure by Design are left to a later decision; Appendix C's three existing
  mappings could be read as a start.
- The export can show what `sv` cannot settle as plainly as what it can: 148 of ASVS's 345 requirements can be credited
  at all (`docs/COVERAGE.md`), and an assessor sees every other one as not verified, never as passed.

## Questions for the owner, before it is built

- An export only when asked, or an OSCAL file written with every report?
- Which OSCAL version to pin (the newest release when the build starts, unless the pipeline in mind needs another)?
- Also a plan of action and milestones (OSCAL's POA&M model) from the findings that need attention, or assessment
  results alone at first?
