# ADR-156: A report's results exported as OSCAL assessment results, through a crosswalk from ASVS to NIST SP 800-53 chosen by reading both texts

**Status:** accepted, 27 October 2026, in the pull request that built the export (backlog 0678, parts 4 and 5); proposed
26 October 2026. Where the build differs from the plan is "As built", below. Asked for by the owner on 26 October 2026, after a conversation about fitting
StackVet into a DevSecOps and continuous-authorization (cATO) pipeline: "add a backlog item (with a proposed ADR) for
an ASVS-to-NIST 800-53 crosswalk and an OSCAL assessment-results export from report.json".

**Governs:** what a report's JSON file holds, which the export reads (`crates/sv-report/src/json.rs`); the Secure by
Design crosswalk's guard, which the new crosswalk is held to the same way (`crates/sv-check/tests/citations.rs`); the
crosswalk (`data/asvs-800-53-crosswalk.json`), its guard (`crates/sv-check/tests/nist_crosswalk.rs`), and the script
that keeps its control text NIST's (`tools/nist_controls.py`); the export (`crates/sv-cli/src/oscal.rs`), its tests
(`crates/sv-cli/tests/oscal_export.rs`, `crates/sv-cli/tests/action_oscal.rs`), and the schema they hold it to
(`data/oscal-assessment-results-1.2.3.schema.json`). A pull request that changes what a status is exported
as, or how a pair in the crosswalk is chosen, changes this record too, or says in its description why it does not
(`docs/adr/README.md`).

## Context

A continuous authorization to operate rests on evidence about a system's controls that arrives with every change, in
a form the authorizing official's tools read. In the federal and defense world those controls are NIST SP 800-53
Rev. 5's, and the machine-readable form is NIST's OSCAL (Open Security Controls Assessment Language), whose
*assessment results* model carries what an assessment observed, how (`EXAMINE`, `INTERVIEW`, or `TEST`), and what it
concluded about each objective.

`sv` grades an app against OWASP ASVS 5.0, AISVS 1.0, and the Secure by Design checklist, and writes what it concluded
as `report.json`, with every requirement in one of nine statuses (`Status` in `crates/sv-report/src/lib.rs`). None of
that reaches 800-53 today:

- **No mapping exists in `sv`.** ASVS 5.0's own text cites NIST SP 800-63B and SP 800-57 but never 800-53
  (`data/frameworks/asvs-5.0.0.json`). AISVS Appendix C's `mappings` field names 800-53 Rev. 5 for three of its 68
  requirements, and nothing reads that field.
- **No export exists.** A pipeline can keep `report.json`, `stackvet.sarif`, and `sbom.cdx.json` with each build, but a
  governance, risk, and compliance tool cannot read the first as control evidence without a converter, and SARIF
  carries findings, not the requirements that were checked and found sound.

The statuses already line up with OSCAL's three assessment methods, which is what makes an export worth having:
*checked* and *checked in part* are tests `sv` ran, *tested by the app's own tests* is a test the app ran, *documented*
is a document read, and *attested*, *checked by hand*, and *stated* are someone's word. And `sv`'s first rule,
something not assessed is never a pass and never a failure, is the rule an assessor needs from automated evidence.

## Decision

1. **A crosswalk from each ASVS 5.0 requirement to the 800-53 Rev. 5 controls and enhancements that ask the same
   thing**, built as `data/sbd-asvs-crosswalk.json` was: chosen by reading both texts, each pair carrying a few words
   naming what the two ask in common, those words held by the citation guard to share vocabulary with both texts
   (`crates/sv-check/tests/citations.rs`), and every requirement listed, an empty list when nothing in 800-53 asks the
   same thing, so a new requirement cannot default silently. A pair means "asks the same thing", never "satisfies":
   800-53 controls are broader than any one ASVS requirement, and the crosswalk is many-to-many.
2. **The control titles and statements are NIST's, never written by hand:** a maintenance script, like
   `tools/atlas_references.py`, reads them from a pinned release of NIST's OSCAL catalog for 800-53 Rev. 5 and writes
   them into the data file, naming any cited control a newer release renames and refusing one it withdraws. It is run
   by whoever maintains the data, outside the sandbox. `sv` itself fetches nothing: the fence is unchanged.
3. **An export that reads a finished report and writes OSCAL assessment results**, run only when asked (proposed:
   `sv export --oscal <report folder>`, and an input on the GitHub Action that runs it), so a report folder holds
   nothing new unless the person asks for it. It records, for each requirement that applies:
   - **an observation**, with its method from the status: *checked*, *checked in part*, and *tested by the app's own
     tests* are `TEST`; *documented* is `EXAMINE`; *attested*, *checked by hand*, and *stated* are `INTERVIEW`. Its
     origin names who it rests on: `sv` as the assessment platform for its own checks, the app's tests for theirs, the
     owner for their sealed answers (ADR-026), and the AI coding tool for *stated*, never the owner;
   - **a finding with a concluded state only where `sv` concluded one:** *needs attention* is `not-satisfied` (reason
     `fail`), and *checked* is `satisfied` (reason `pass`) for the ASVS requirement's own objective. *Checked in part*
     and every answer tier are never `satisfied`: they are reported with the status `sv` gave them, and the export says
     so in words. *Not verified* is listed as not verified, never as either state;
   - **the 800-53 controls from the crosswalk as related controls of the ASVS objective, never as a verdict on the
     control.** No 800-53 control is marked satisfied from `sv`'s evidence alone.
4. **The export carries its provenance:** the report's seal (ADR-034), `sv`'s version and commit, the image digest
   when it ran in the published image (ADR-080), the commit of the app, and the date. A report whose seal does not show
   `sv` wrote it is refused, as it is over MCP.
5. **Held by tests against NIST's own schema:** the OSCAL JSON schema for the pinned version is committed beside the
   crosswalk, so the tests validate offline. One test breaks the status mapping on purpose (*checked in part* exported
   as `satisfied`) and must go red.

## Alternatives considered

- **Start from OpenCRE's links between ASVS and 800-53.** Worth reading as a first draft of the pairs, but not taken as
  given: a citation is a claim, and each pair is kept only after reading both texts and passing the guard.
- **Leave it to the pipeline to convert SARIF.** Rejected as the only route: SARIF carries findings, not requirements
  checked and found sound, nor the difference between a test and someone's word.
- **Mark an 800-53 control satisfied when every ASVS requirement mapped to it is checked.** Rejected: the crosswalk says
  two texts ask the same thing in part, not that ASVS covers a control. That would make `sv`'s evidence look stronger
  than it is, which the project's first rule forbids.
- **Write the OSCAL file into every report folder.** Rejected by the owner on 27 October 2026: it adds a file to
  someone's folder by default that most people cannot read and do not need (the owner's answers, below).
- **A POA&M export from the start.** Left for later by the owner on 27 October 2026: it needs facts `sv` does not have
  (the owner's answers, below).
- **Send the results to eMASS or a GRC tool directly.** Rejected: it would open a connection of `sv`'s own and need an
  account. The pipeline uploads what `sv` writes.

## Consequences

- A cATO pipeline can read `sv`'s evidence for the application layer as OSCAL assessment results, with each result's
  method and source, alongside the infrastructure and operations evidence other tools give.
- The cost is the crosswalk itself: 345 ASVS requirements read against 800-53's controls and enhancements, and kept
  true as either changes. AISVS and Secure by Design are left to a later decision; Appendix C's three existing
  mappings could be read as a start.
- The export can show what `sv` cannot settle as plainly as what it can: 148 of ASVS's 345 requirements can be credited
  at all (`docs/COVERAGE.md`), and an assessor sees every other one as not verified, never as passed.

## As built (27 October 2026), and where it differs from the plan

Parts 1 to 3 (the crosswalk, its control text, and its guard) went in first, in their own pull request; the export and
the documents went in second.

- **The crosswalk:** all 345 ASVS 5.0 requirements listed, 192 paired, 224 pairs over 82 controls and enhancements,
  from NIST SP 800-53 Rev. 5 version 5.2.0 as published in oscal-content `v1.6.0`. Four drafted pairs were dropped on
  reading as asking a different thing. The guard compares each pair's words with the ASVS text and with the control's
  title and statement, as written by `tools/nist_controls.py`.
- **OSCAL 1.2.3, the newest release on 27 October 2026,** pinned as the owner answered: `OSCAL_VERSION` in
  `crates/sv-cli/src/oscal.rs` and the committed schema move together.
- **Two ways to export, not one (differs from Decision 3).** The plan was `sv export --oscal` alone. In the GitHub
  Action the key that seals a report lives in the container and is thrown away with it, so a later export step could
  never show the report is `sv`'s and would refuse it. So `sv report --oscal FILE` writes the file in the same run, from
  the report it has just written and sealed, and `sv export --oscal [FOLDER] [--out FILE]` writes it later from a report
  this computer can show `sv` wrote (sealed here, or sealed elsewhere and moved, as `sv compare` accepts). The file is
  never written into the report folder, which would stop the folder being `sv`'s (H6); both refuse a path inside it.
  When `--oscal` was given and the file could not be written, the report still stands and `sv report` exits 3. The
  Action's input `oscal` (default `false`) passes `--oscal` into a folder of its own and keeps the file as a second
  artifact; it refuses an image whose `sv` does not know the option.
- **The format settles Decision 3 itself.** An OSCAL finding must conclude `satisfied` or `not-satisfied`, with nothing
  between. So *checked* and *needs attention* are findings, every other status that rests on something is an
  observation with no finding, and *not verified* is an objective with nothing observed.
- **The reviewed controls are the ASVS requirements (an addition).** OSCAL's `reviewed-controls` means the controls
  assessed, so 800-53 controls are never listed there: they are links of each ASVS objective, `rel="related"`, each
  saying "not assessed as a control". OWASP publishes ASVS 5.0 as JSON and CycloneDX but not as an OSCAL catalog, so the
  objectives are defined in the document itself, in the requirement's own words, with ids made lower case (`v6.2.1`),
  and the back matter names ASVS 5.0.0 and the 800-53 release. `sv` writes no assessment plan; `import-ap` points at a
  resource saying so.
- **Only ASVS (as the plan said).** AISVS and Secure by Design results stay in `report.json`.
- **Provenance (Decision 4):** `sv`'s version and commit, the SHA-256 of `report.json` as its seal was checked against
  it, the seal line, the run's id, and the app's commit when the app folder is known (`sv report`, or `sv export` given
  the app folder). `sv` cannot know its own image's digest; the Action names the image whose signature it checked, by
  digest, in `STACKVET_IMAGE`, and the file records it as the pipeline's word. UUIDs are derived from the report's
  SHA-256, so the same report exports to the same bytes.
- **A test-only dependency:** `boon` 0.6.1 validates the document against NIST's schema in the tests, offline, and is
  in no build of `sv` (`crates/sv-cli/Cargo.toml`, under `[dev-dependencies]`). Chosen over `jsonschema`, which pulls
  in far more; it adds 43 crates to the lock file, most of them the Unicode tables of `url` and `idna`.
- **Broken on purpose:** exporting *checked in part* as `satisfied` in `oscal::told` turned three tests red, the
  end-to-end run of `sv report --oscal` over the Flask example among them.

## The owner's answers (27 October 2026)

The three questions this record asked were answered by the owner on 27 October 2026, agreeing with the recommendations
put to them:

- **An export only when asked.** `sv` writes the OSCAL file only when the person runs the export; a report folder holds
  nothing new by default. The GitHub Action (ADR-081) gains one input that turns the export on, so a pipeline sets it
  once and gets the file with every run. Nothing is lost by waiting: the export reads a finished, sealed report, so it
  can be made from any earlier report.
- **The newest OSCAL 1.x release when the build starts,** its exact number written in this record and beside the
  committed schema. Moving to a newer release is a pull request of its own that replaces the schema and runs the tests
  again, so a new OSCAL release never changes what `sv` writes without someone choosing it.
- **Assessment results alone at first, no POA&M.** A plan of action and milestones needs a person responsible,
  milestones, dates, and sometimes a decision to accept a risk, none of which `sv` knows; filling them in would be
  evidence `sv` did not gather. Each *needs attention* finding in the assessment results carries what a governance,
  risk, and compliance tool, or a person, needs to start an entry. A POA&M export is a backlog item of its own if a
  real pipeline asks for one, and would fill only what `sv` knows (the weakness, its source, the requirement, and the
  date found), leaving the rest marked for the system's owner.
