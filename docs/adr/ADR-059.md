# ADR-059: Every check that gives credit is seen withholding it in the test suite, or the build fails

**Status:** accepted, 8 October 2026, in the pull request that builds the gate (step 3 of backlog item 32), at the
owner's word ("go ahead with step 3 when it's merged"); proposed the same day with step 2 ("yes, please go ahead
with step 2"). Written by session securevibe-e2.

**Governs:** `tools/coverage.py` (its census of credits and of what is withheld), `crates/sv-check/src/verified.rs`
(its marker for a credit not given). A pull request that changes either changes this record too, or says in its description why it
does not (`docs/adr/README.md`).

## Context

A check is known to work when it says no with the thing it guards broken, not because it says yes on an app that
is fine (CLAUDE.md, "Break your own rule and watch what catches it"). Since 6 October 2026 CI writes down every
credit the test suite sees and holds it to the lists of checks that only ever give a finding; nothing held a
check to having been seen saying no. A check with a fault that made it credit every time would pass every test
of a good app and leave no trace (`docs/GAP-ANALYSIS.md`, 7.4).

Step 1 (pull request #1054) wrote down every finding a check makes (`finding::found`), beside the credits, and
`tools/coverage.py --withheld` listed the checks seen giving credit and never seen withholding: 10 of 125, each
of which withholds by design without a finding, by "not assessed" or by giving no credit, and each of which
already had a test saying so. Step 2 has each of those mark where it has run (`verified::unless_credited`), so a
credit not given is written down too.

## Decision

`tools/coverage.py --credits`, which CI already runs after the tests, also fails when a check the suite saw give
credit was never seen withholding it, by a finding or through `unless_credited`, in code that ships. A check that
genuinely cannot be made to withhold in a test is named in a list in `tools/coverage.py` with its reason, as the
findings-only lists are, and the list is expected to stay short.

## Alternatives considered

- **Leave it to the rule in CLAUDE.md.** It held for most checks, and the census found ten it could not see; it
  depends on whoever writes a check remembering, which is what the gap analysis found wanting.
- **Count "not assessed" by requirement.** A "not assessed" line names a requirement, not a check, and several
  checks share requirements: one check's "not assessed" would count as another's no.
- **Write the census at the report.** Simpler, but a check run by a unit test, as most are, would never be seen.

## Consequences

A new check that gives credit cannot reach `main` without a test in which it says no. The census runs only in
debug builds; `sv` as shipped writes nothing new. A check that makes findings through a path that does not go
through `finding::found` would be listed until it does; a test (step 3) can hold every place that builds a
`Finding` in shipping code to going through it.

## As built (8 October 2026)

`check_withheld` in `tools/coverage.py`, run by `--credits`, which CI already runs after the tests: it fails on
any check the suite saw credit and never saw withhold, unless the check is in `NEVER_WITHHELD` with its reason,
and on any check in that list that was seen withholding. The list is empty: at step 2, all 125 checks the suite
saw credit were seen withholding too. `unrecorded_findings`, run by `--check`, which a test runs, fails on any
place in shipping code that builds a `Finding` without handing it through `finding::found`, so a new check
cannot leave the census by building its findings another way. Breaks: a finding built without `found`, a check's
marker removed, and the gate switched off, each caught (DESIGN, "Step 3: the gate").

## Later, 8 October 2026: per requirement, not only per check

The review of 8 October (item 5) found the census held each check as a whole: a check citing two requirements whose
tests only ever saw it credit one passed, and the other was cited on evidence the suite had never seen. `--credits`
now also fails on a requirement a crediting check cites and was never seen crediting, naming the check and the
requirement; the fix is a test that reaches that credit, or no longer citing it. Measured on the day it was added,
no check failed it. A log of the findings the suite saw, the review's other ask here, is the census of what checks
withhold that this record already describes. Held by `crates/sv-check/tests/census_per_requirement.rs`. The
decision stands.

## Later, 9 October 2026: the mirror of the checks stays, held to the census

The architecture assessment of 8 October 2026 (backlog 0187, item 12, its third part) proposed shrinking the
mirror in `tools/coverage.py` (`RUST_CHECKS`, about 180 entries, each check's requirements and tier written again in
Python) to the findings-only list, by having `Verified::new` log the kind of run. That would make
`docs/COVERAGE.md`, `docs/REQUIREMENTS.md`, and `data/reach.json` something only a full test run can write. Asked to
choose between the two, **the owner chose on 9 October 2026 to keep the mirror, held to the census** ("agree, keep
the coverage mirror list held to the full test count"), as recommended: the generated files stay writable by
`python3 tools/coverage.py` alone, in seconds and without a build, and the mirror cannot quietly go wrong, because
`--check` fails on a check it names that the code lacks or a requirement it cites that the code does not, and
`--credits` fails on a check whose credits in the test run disagree with its lists. The cost, accepted: a new check is
written in two places, and the second is held to the first. Item 12's third part is closed as not to be built.

## Later, 14 October 2026: the census carries the in-part mark, and holds the list of checks only ever in part

`docs/COVERAGE.md` and `docs/REQUIREMENTS.md` print a check as able to mark a requirement *checked* unless
`tools/coverage.py` lists it as only ever in part, and nothing held that list to the code: it named 11 checks, and
the suite saw 89 more credit only ever in part (backlog 0430). The line `Verified::new` writes is made before
`.in_part()` is chained on, so it cannot carry the mark. Now `Verified::in_part` writes a line of four (the check, its
requirements, `in part`, the place) when it marks a credit, and the new `Verified::whole_after_all` writes `whole` when
a credit is made whole again (`sv-cli`'s V7.5.1 credits, on the owner's word through `sv review`). `--credits` counts,
for each check, the credits made, marked in part, and made whole again, and fails when a check whose every credit the
suite saw was in part is not on the list, or one on it was seen credit whole. A check in part only on a single sample
(`in_part_if`) is whole when a test gives it more; two had no such test (`probe.cookie-attributes`,
`probe.admin-action-ordinary-user`) and now do.

Found building it: the census read each file up to its first `#[cfg(test)]`, and a `#[cfg(test)] mod name;` that only
declares a file of tests kept elsewhere was taken for that place. About 11,700 lines of 13 files that ship were read as
test code, `assemble.rs` after its line 53 among them. The census now reads up to the first `#[cfg(test)]` that is not
such a declaration; with that, the three generated files were otherwise unchanged and no other fault appeared.

## Later, 14 October 2026: a credit that names no requirement is left out of the in-part count (backlog 0469)

`config.workflow-checkout-keeps-token` credits AC.12.2 only in part now, since AC.12.2 also asks that runners be scrubbed
of cached credentials before AI tooling runs, which no workflow file shows. It also gives a credit naming no requirement
when a workflow checks nothing out, and that credit, being whole, made `--credits` read the check as able to be whole.
A credit that names no requirement can make none *checked*, so `--credits` now leaves it out when it counts a check's
credits made, marked in part, and made whole again. The check joins `RUST_IN_PART`.
