# ADR-151: An authorization server is asked, through a test client the owner declares, whether it holds to what OAuth asks of it

**Status:** accepted, 25 October 2026, in the last of the five pull requests that build it. Proposed 24 October 2026
with the claim for backlog 0625's seventh part.

**Governs:** the test-client entry in stackvet.toml (`crates/sv-manifest/src/lib.rs`), the probes that use it
(`crates/sv-check/src/signed_in/oauth_client.rs`, `crates/sv-check/src/signed_in/oauth_client/pkce.rs`,
`crates/sv-check/src/signed_in/oauth_client/refresh.rs`, `crates/sv-check/src/signed_in/oauth_client/client_auth.rs`,
`crates/sv-check/src/signed_in/oauth_client/response_mode.rs`, `crates/sv-check/src/signed_in/oauth_client/par.rs`,
`crates/sv-check/src/signed_in/oauth_client/logout.rs`), the blanking of what the server issues
(`crates/sv-check/src/script.rs`), and their tests. A pull request that changes what the entry holds, what is sent
with it, or what a refusal credits, changes this record too, or says in its description why it does not
(`docs/adr/README.md`).

## Context

An app that is itself an authorization server (`authorization-server = true` under `[capabilities]`: other apps send
their users to it to sign in) is held to ASVS V10.4 and V10.6. Part 6 (ADR-147) reads what the server publishes about
itself. What it publishes is not what it does when asked, and eight requirements are about what it does:

- V10.4.1 (L1): redirect addresses checked against the client's registered ones by exact string comparison.
- V10.4.2 (L1): a sign-in code used only once.
- V10.4.5 (L1): a refresh token, once used, not taken again, and its sign-in's other refresh tokens revoked.
- V10.4.6 (L2): PKCE required, `plain` refused, and the `code_verifier` checked.
- V10.4.10 (L2): a confidential client authenticated on its token requests.
- V10.4.12 (L3): only the `response_mode` the client needs.
- V10.4.13 (L3): the code grant only through pushed authorization requests (PAR).
- V10.6.2 (L2): a sign-out started by another app confirmed by the person, or checked against its `id_token_hint`.

To ask any of these, `sv` has to act as an app registered with the server, and a server talks only to apps registered
with it, each with an id, its redirect addresses, and usually a secret. The owner, told this on 24 October 2026, said
of the approach below: "Yes, build it".

## Decision

- **A test-client entry,** `[stack.run.oauth-client]`, with `id`, `redirect` (one registered redirect address), and
  `secret` for a confidential client, which is always written as a seed value, `{seed:NAME}` (ADR-124), never in the
  file. `sv` never shows the secret, only its first four characters and its length. The seed script registers the
  client in the copy of the app `sv` starts, set to skip the consent page, since a consent page asks a person to click.
- **The server's addresses** come from its published details (ADR-147): `authorization_endpoint`, `token_endpoint`,
  "pushed_authorization_request_endpoint", and `end_session_endpoint`. Where it publishes none, the entry's own
  `authorize` and `token` paths say where they are.
- **The person signing in** is the first test account of `[stack.run.users]`, signed in as the other signed-in probes
  sign in. Without that section, only what needs no person is asked (V10.4.1's refusal before signing in, and
  V10.4.10).
- **Everything goes to the copy of the app `sv` started,** inside the fence; no new connection.
- **Each probe is gated on the normal case working first:** the registered redirect address answered with a code, a
  code exchanged for a token, a refresh token taken once. When the normal case does not work, nothing is concluded,
  and the report says which step failed. A consent page where a code was expected is said to be one, with how to make
  the seed skip it.
- **What credits, and how far:** a server that takes what it should refuse is a finding against the requirement. A
  refusal, with the normal case working before and after, is credited in part: one client, one person, and a sample
  of each kind of wrong request are asked, not every client the server holds. V10.4.2's and V10.4.5's revocation of
  tokens already issued is asked where the server publishes an introspection address, and otherwise left not assessed.
- **Left out, the entry costs nothing:** each of the eight reads not assessed, and the report says how to add it. A
  server that is not asked is never a pass.
- **Dynamic registration:** where the server publishes a `registration_endpoint`, `sv` registers its own test client
  in the copy it started, and the owner writes nothing. A client registered this way usually meets the consent page,
  so with it only what needs no code is asked, and the report says so.
- **Built in five pull requests:** redirect matching and code reuse (V10.4.1, V10.4.2), with the entry; PKCE and
  refresh reuse (V10.4.6, V10.4.5); client authentication and response mode (V10.4.10, V10.4.12); PAR and sign-out
  without a hint (V10.4.13, V10.6.2); then dynamic registration. The plan in 0625 said four. Registration comes last so
  that every probe is first built and tested on a client the owner registered, where a code can be had.

## Alternatives considered

- **Dynamic registration only, with no entry.** Rejected: many servers do not publish a registration address, and
  those that do usually put a consent page before a client registered that way, so most probes would get no code.
- **Clicking through the consent page.** Rejected: `sv` would be agreeing, on a person's behalf, to a page it cannot
  read reliably, and a page that is not a consent page could be agreed to by mistake.
- **A secret written in stackvet.toml.** Rejected: the file is committed, and a key is never written down (CLAUDE.md).

## Consequences

- An owner whose app is an authorization server, and whose seed registers one test client, has eight requirements
  asked of the running server instead of none.
- The starter shows the entry as commented lines under the authorization-server question, with the seed lines for
  django-oauth-toolkit and node-oidc-provider, the two libraries part 6 reads.
- Each probe sends a few requests at most; none of them is a flood, and none signs the person anywhere but the copy
  `sv` started.

## Where the build differs

V10.4.1 and V10.4.2, built 24 October 2026 (the first pull request). The checks are "probe.oauth-redirect-not-exact"
and "probe.oauth-code-reused", run in the signed-in suite after the redirect checks and before the password changes,
since an app may lock the account after the wrong passwords at the end. Five things the decision did not say:

- **Without `[stack.run.users]`, nothing is asked.** The checks run in the signed-in suite, which needs the test
  accounts, and a refusal before anyone signs in shows nothing either: a server sends the browser to its sign-in page
  for a good address and a bad one alike.
- **Left out, the entry is mentioned only to an app that answers as an authorization server:** one of the two
  published details documents, read as part 6 reads them. Every other app with signed-in pages is told nothing, since
  a test client means nothing to it.
- **The changed addresses are three:** letters added to the registered address's path, a query added to it, and its
  host made the start of a host under `.invalid`. A server that matches by prefix takes the first two, and one that
  matches a host by its start takes the third.
- **The codes and tokens the server issues are blanked** from everything the run writes down, as the seed's values are,
  shown as "[a code or token the app issued]". The record keeps the app's answers, and the token address's answers are
  tokens.
- **Revocation is asked only of a confidential client,** since an introspection address takes the client's secret. A
  code refused the second time, with its first token still active, is a finding; with no introspection address, or a
  public client, the credit says revocation was not asked.

A crash, no answer, or a limiter's answer (a 429, or a 503 with Retry-After) to a changed address or to the code sent a
second time is not read as a refusal (ADR-021), and concludes nothing. The client's secret is sent in HTTP Basic, as
RFC 6749 asks a server to take it; the record never keeps a request's
headers. The scope asked for is `openid` unless the entry names another.

V10.4.6 and V10.4.5, built 25 October 2026 (the second pull request). The checks are "probe.oauth-pkce-not-required"
and "probe.oauth-refresh-token-replayed", run after the first pull request's, each with sign-in codes of its own, since
a server that refuses a reused code may rightly revoke what that code gave. For V10.4.6, a code is asked for with no
challenge and with the `plain` method, and a code is exchanged with a verifier one letter off; a code or token given
for any of them is a finding, and refusals are credited in part only when a fresh code, exchanged with the right
verifier after them, still gives a token. A refusal sent back to the client's address with `error=invalid_request`,
as RFC 7636 says, counts as a refusal. For V10.4.5, which is written for public clients, the check runs only when the
test client has no `secret`; with one, it is not assessed and the report says to declare a public client. A used
refresh token taken again is a finding, and so is a newer one its first use gave still working after the used one came
back. A server that gives no new refresh token with each use, and refuses the used one, is credited in part with the
revocation said to be unasked.

V10.4.10 and V10.4.12, built 25 October 2026 (the third pull request). The checks are
"probe.oauth-client-not-authenticated" and "probe.oauth-response-mode-not-held". V10.4.10 is about confidential
clients, so it runs only when the test client has a `secret`; with none, it is not assessed and the report says to
declare a confidential client. A fresh code is exchanged with no client authentication, and another with a secret one
character off; a token for either is a finding, and refusals are credited in part only when a third code, exchanged
with the right secret, still gives a token. The credit names what was not asked: V10.4.10 also covers pushed
authorization and revocation requests, and only token requests were sent. For V10.4.12, the test client is taken to
use the code flow's own mode, its code in the query of its redirect address; the record leaves no entry for another
mode, since every client `sv` asks takes its code that way. A code asked for with `response_mode=fragment` and with
`response_mode=form_post` is read for a code sent back in the address's fragment, or in a form the page posts to the
address; either is a finding. Refused, or answered in the query as usual, with the usual request answered after, is
credited in part. A code that comes back another way is blanked like the rest.

V10.4.13 and V10.6.2, built 25 October 2026 (the fourth pull request). The checks are "probe.oauth-code-without-par"
and "probe.oidc-logout-without-hint". For V10.4.13, the first, ordinary authorization request, sent straight to the
authorization address, answered with a code is a finding. When it is refused, and the server publishes a pushed
authorization request address, `sv` asks again straight, then pushes the same request there and sends its
`request_uri` to the authorization address; refused straight and answered with a code when pushed is credited in part.
The other checks send their requests straight, so with such a server they are not asked, and the report says why: the
probes do not yet go through PAR. For V10.6.2, run last since it may end the person's session at the server, the
first test user's browser is sent to the published `end_session_endpoint` with no `id_token_hint`, then with a
token-shaped hint `sv` makes up at run time, and after each the test client's next authorization request shows
whether the person is still signed in. Signed out by either is a finding; still signed in after both is credited in
part. A server that publishes no sign-out address is not asked. One fault in the first three pull requests came to
light here: when the first request gave no code, the note said so only for V10.4.1 and V10.4.2, and every other
requirement the test client is asked about read not verified with no reason. The note now names all eight.

Dynamic registration, built 25 October 2026 (the fifth pull request), which makes this record accepted. With no
`[stack.run.oauth-client]`, and the server's published details naming a `registration_endpoint`, `sv` sends it an RFC
7591 registration for a confidential client, its redirect address one that is never followed, and runs every check
above with the client that comes back. Its `client_secret` and `registration_access_token` are blanked with what the
server issues. A registration refused, or answered with no client id, is said, with how to declare a client; the
server may take registrations only with an initial access token, which `sv` does not have. A client registered this
way that meets the consent page is said to have, ahead of the reason the first request gave no code. The client stays
in the copy of the app the run started, and goes with it.
