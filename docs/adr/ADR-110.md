# ADR-110: The reports lead with the things to fix, and say what was not examined right after

**Status:** accepted, 12 October 2026, in the pull request that builds it (backlog 0371). The decision is the owner's,
made that day from the website's words (backlog 0224, `docs/website/home-page.md`): the report "starts with the most
important things to fix, then what was checked, and what nobody has looked at yet." Asked the order section by
section, the owner chose: the short version, the things to fix worst first, how the report was made, what was not
examined, then the rest; "most important" means severity, with the app's own code ahead of test code.

**Governs:** `crates/sv-report/src/html.rs`, `crates/sv-report/src/markdown.rs` and `crates/sv-report/src/dashboard.rs`
(the order of their sections), `crates/sv-cli/src/report_prompt.rs` and `docs/prompts/report.md` (the order the
reading prompt gives). A pull request that changes these changes this record too, or says in its description why it
does not (`docs/adr/README.md`).

## Context

From the first report (`docs/design/0010-the-reports.md`, 27 September 2026) the rule was that **what was not
examined comes first**, before anything found, because a list of findings read on its own reads as the whole truth
about the app. Four tests held it. The short version at the top of `report.html` and `compliance.md` already named
the worst findings, but the sections below it opened with "Read this first" (how the run went, and the key to the
status words), then the gaps, then the things to fix; `compliance.md` had no list of things to fix at all, only the
worst five; `security.md` and the dashboard put the gaps before the findings; and the reading prompt had the AI tool
start with what was not checked. For a person new to all this, the first full section they met said what StackVet had
not done, and the things they could act on came third.

## Decision

- **The same order in every report:** the short version (unchanged); **the things to fix**, the app's own first,
  worst first; what was set aside in `stackvet.toml`; **how this report was made** (renamed from "Read this first",
  which cannot be first in third place); **what was not examined**; then everything else as before. `compliance.md`
  gains a short list of the things to fix, a line each, pointing to `security.md` for each in full.
- **What was not examined stays directly after**, ahead of every table, so the findings are never read as the whole
  truth: the reason for the old rule holds, and only the order of the first two changes.
- **The reading prompt follows it:** at most three things to fix first, then what was not checked ("do not skip this,
  and do not make it sound minor" kept), then the person's questions.
- **The dashboard** shows each app's findings before what was not examined.

## Alternatives considered

- **Keep the gaps first** (the old rule): it puts the least actionable section ahead of the most, for exactly the
  readers StackVet is for.
- **Fold the gaps into the short version only**: the short version is one screen; the gaps need their own section,
  and the owner chose it directly after the things to fix.

## Consequences

- `crates/sv-report/tests/report.rs` holds the new order in all three files, in place of the test that held the old.
- The finer points of what counts as a thing to fix (an information note, a finding that found nothing wrong) are
  backlog 0371's next step and this record's Later entries.

## Later, 12 October 2026: notes worth knowing, and one count for the things to fix

At the owner's word the same day, after a real report on an example app said "4 things were found", "Fix the 3 things
that need attention", and "4 things to fix" about the same run, with a piece of good news among the four:

- **A note worth knowing is never a thing to fix.** An `Info` finding in the app's own code (`is_note`) is shown under
  its own heading, "Worth knowing", after the things to fix in `report.html` and `security.md`, and is said in a
  sentence in `compliance.md`'s list. It is not among the worst findings at the top, not counted in the headline's
  "found", and given no "Fix it in the code" (ADR-098, Later). A finding listed apart, in test code or a bundled
  library, keeps its place in that section.
- **One count:** the headline's "found", "What to do next"'s "Fix the N things that were found", and the "N things to
  fix" heading all count the same set, the app's own findings that are not notes. "What to do next" used to count the
  requirements that need attention, a different number.
- **Good news is not a finding:** the check of AI-made commits records none outside a merge as a check that found
  nothing (ADR-092, Later).

## Later, 13 October 2026 (backlog 0408: the SARIF file's notes are notes)

The owner's decision, from the Antigravity trial's `findings.sarif`, which held no findings and nine notifications at
level `warning`, one for each thing not examined; to the owner they read as nine problems with the app. They are now at
level `note`: still in the file, so an empty `results` never reads as a clean bill of health, but no longer shown as
problems in an editor or on GitHub. What was not examined stays as prominent in the reports as this record says.
`report.html` and `compliance.md` say, near the top, what the file is and holds, counted from the file itself: for code
editors and GitHub's code scanning, not for reading; how many findings; and how many notes on what was not examined.
