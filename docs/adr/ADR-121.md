# ADR-121: The checklist before going live, a report file of its own that credits nothing

**Status:** accepted, 15 October 2026. The owner asked for it after running prompt 7 in the follow-up model trial
(backlog 0577), and answered the item's two questions the same day: "as recommended: a tick counts as a hand check only
when the line names a requirement and the person confirms it through sv review, otherwise it is a note; both forms,
written with the report and reprinted by `sv before-live` from the last report. Build it; a new ADR in the building pull
request." Backlog 0589.

**Governs:** `crates/sv-report/src/checklist.rs`, which draws the checklist from a report, and
`crates/sv-cli/src/before_live.rs`, which prints it again. A pull request that changes what the checklist holds, what
it credits, or what a tick records changes this record too, or says in its description why it does not
(`docs/adr/README.md`).

## Context

What a person must do or confirm before an app is on the internet was already in the report, in four places and in
the order the requirements come: the "Before going live" list (`sv probe`'s questions, `crates/sv-report/src/live.rs`),
the decisions nobody has made, the findings left, and the gaps, among them a credit withheld because the copy `sv` ran
was started with a setting that loosens it (backlog 0564). Nothing put them in the order a person deploys, and the
person deploying is not a programmer.

## Decision

1. **A file of its own.** Every report folder holds `before-going-live.md` beside the others, and `report.html` has a
   section with the same checklist. It is written with the report, from the report and nothing else, in four parts in
   the order of a deployment:
   - **at the host, before the first deploy:** HTTPS and old TLS versions (for an app on the internet), each setting
     the run's copy was loosened with, a key found in the code, debug mode, the lockfile, and a real security contact;
   - **at the live address, after the first deploy:** each line of the "Before going live" list with its `sv probe`
     command, and trying the account pages on the live site;
   - **the decisions still open,** each with its question and the requirement it decides;
   - **what is still there:** each thing left to fix or accepted as a risk, so the person goes live knowing it; the
     low-severity ones counted and left to `low-findings.md`.

   A fifth part, with no boxes, says what the report could not verify at all: how many requirements nothing verified,
   the kinds of run that did not happen, and how many limits "What was not examined" names. A finished checklist is
   not to be read as a pass.
2. **It credits nothing.** A line is a thing to do, not a check, and the file says so at its top. Nothing in it
   changes a requirement's status or a count. `report.html` counts the things found in its last part rather than
   repeating each finding the page already shows.
3. **It is sealed with the rest, and `sv before-live [PATH]` prints it again** from the app's last report, only when
   the folder's seal holds and the bytes are the ones sealed (`report_seal::proven`, as `sv explain --app` asks of
   `report.json`). It checks nothing and writes nothing. A report folder written before this change has no checklist,
   so its seal no longer covers every file `sv` writes: `sv` says so (`report_seal::missing`) and asks for the report
   to be written again, as it did when `seen.json` joined the report files (ADR-082).
4. **What a tick records** (the owner's answer; built after this, backlog 0604). A line is ticked in `sv review`,
   never by editing the file, which is written again with each report. A tick on a line that names a requirement,
   confirmed by the person there, is recorded as a hand check of that requirement (`[checked-by-hand]`, sealed, as
   `sv review` records one now), but only for a requirement `sv` already accepts a hand check for
   (`data/human-checks.json`): a tick widens nothing. Any other tick is a sealed note that the next checklist shows as
   done, with when, and that credits nothing.

## Alternatives considered

- **Printed by a command only, never written.** Never stale, but a person reading the report folder would not find it.
  The owner chose both.
- **Made afresh by `sv before-live` from `report.json`.** `report.json` is a program's reading of the report, and the
  checklist would have to be rebuilt from it by a second reader that could drift from the first; printing the sealed
  file shows exactly the checklist that came with the report.
- **Every tick a hand check.** The live-site requirements (HTTPS, HSTS, old TLS) are not in `data/human-checks.json`,
  because `sv probe` settles them; letting a tick credit them would add a way to evidence the owner has not chosen.

## Consequences

- A report folder holds ten files. The README, the guide, the website's reports page, `docs/ARCHITECTURE.md`, the
  MCP server's resources, and `sv report --help` say so.
- A report folder from an older `sv` must be written again before `sv` can show it wrote it (the MCP server's
  resources, `sv review`'s writing the report again, `sv explain --app`, `sv compare`, `sv before-live`).
