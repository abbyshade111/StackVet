# ADR-091: Four Bandit rules in test code are information, not findings, and a person reviews them

**Status:** accepted, 11 October 2026, at the owner's word ("yes, I approve"), in the pull request that builds it. Proposed the
same day in backlog 0248, from a real report on an app built with `sv` in Cursor: 89 findings, 79 of them in one test file,
62 of them Bandit's "use of assert" and 14 its "hardcoded password string".

**Governs:** `crates/sv-check/src/finding.rs` (the list of rules that are information in test code, and which findings
are), `crates/sv-report/src/bluf.rs` (the headline names what is information and does not count it), `crates/sv-report/src/markdown.rs` and `crates/sv-report/src/pages.rs` (the section and its copy into information.md), and
`crates/sv-cli/src/assemble.rs` (the split, which keeps those findings out of the report's findings). A pull request that
changes these changes this record too, or says in its description why it does not (`docs/adr/README.md`).

## Context

`sv` already listed findings in test code apart from the app's own code, and still counted them: "this changes where a
finding is listed, never whether it counts", as the report's own words had it. Test code can hold a real key, and sample
code gets copied, so counting them was deliberate. For four Bandit rules it is noise: an assert is how a test is
written, and a password-looking string in a test file is usually a fixture. The owner asked for these to be information,
reviewable, not counted; and for any real-looking key in a test file to still count.

## Decision

- **Which findings:** Bandit's B101 (assert), and B105, B106, and B107 (password-looking strings), when the finding is in
  test code and no other tool also reported it. The secrets rules are not on the list: a real-looking key in a test file
  still counts.
- **What it does:** such a finding is not a finding. It is kept in the report's own list (`test_information` in the
  report file, left out when empty), not in the findings, so it does not move any count, any headline, or any requirement's
  credit. The headline says how many there are, which rules, and that they can be reviewed with `sv review`.
- **Review:** the owner reviews them with `sv review`. A review can change nothing about the count on its own; turning one
  into a finding needs a later decision, recorded in its own pull request (see below).

## Alternatives considered

- **Leave them counted:** the report stays noisy; a person reads 79 lines to find the few that matter.
- **Count them as findings at info:** they would stay in the findings list and move the counts.
- **Exclude test folders altogether:** would hide a real key in a test file, which the decision keeps visible.

## Consequences

- Reports for apps with test files show fewer findings. Their headline says what was left out and why.
- The report file gains a list (`test_information`) that older readers do not know about; it is left out when empty, so a
  report with none is the same as before.
- Not built yet: the `sv review` step for these findings, so a reviewer can say a finding is real and have it count; and
  the listing of them in the markdown and html reports beyond the headline. Until those are built, the headline and the
  report file are the only places they appear. Both are to be filed as backlog items, numbered after checking the open
  pull requests.

## Tests

`crates/sv-check/src/finding/test_information_tests.rs`: the four rules in a tests folder are information; the same rules
in app code still count; a file the report marks as test code is information; a secrets rule in a test file still counts;
a finding another tool also reported still counts. Break test: B101 removed from the list, and two tests fail.

## Later, 11 October 2026: the review step is built, as ADR-093

The `sv review` step this record left not built is built by ADR-093: a reviewer can record a sealed `counts` entry for a
test-file information finding that is real, and it then counts as a finding. The information list and the headline keep
the rest. The listing of these findings in the markdown and html reports is backlog 0260, still open.

## Later, 11 October 2026: the markdown report lists them in full

`security.md` now lists every test-file information finding in its own section after the findings, with its rule,
file, line, title and fingerprint, and says how to make a real one count (ADR-093). The section is left out when there
are none. The html report still shows the headline only.

## Later, 15 October 2026: a test password made of words is information too (backlog 0529)

In the three-tool trial of 14 October 2026, `tests/conftest.py`'s `PASSWORD = "violet-canoe-marble-ledger"` was a
high finding from `secrets.credential-assignment`, while Bandit's B105 on lines of the same test files was test
information: one check treated `tests/` as the app and another did not. Asked how far to go, the owner answered (b):
only a value that reads as words or a passphrase becomes test information; a random-looking value in a test file still
counts, as this record ruled on 11 October.

So `Finding::is_test_information` also holds a `secrets.credential-assignment` finding in test code whose value is made
of words (`secrets::reads_as_words`: two words or more, each three letters or more with a vowel, split at `-`, `_`,
`.`, a space, or a capital; no digits or other characters), when no other rule but this record's four Bandit rules
reported the same line. The redacted value carries whether it was made of words (`Secret::reads_as_words`, never
written to a report). The finding's description says "in a test file and made of words … a test password reused
elsewhere is still a risk"; its title, and so its fingerprint, are unchanged. A provider's key is caught by the
pattern rules, which are not on the list, and a random-looking value is not made of words: both still count. The same
words in the app's own code count as before. The tests are in `crates/sv-check/src/secrets/test_passphrase_tests.rs`;
with the new clause taken out of `is_test_information`, two of them fail, and with one word counted as enough, one does.

## Later, 26 October 2026 (the fifth weekly review)

The headline no longer names the rules. Since backlog 0635 (22 October) it says "N things in test code are information, not findings: information.md lists them. Review them with `sv review`" (`crates/sv-report/src/bluf.rs`), and a test asserts the rule ids are absent from it; the rules are named in `information.md`. The section is still written into `security.md` (`markdown.rs`) and copied to `information.md` (`pages.rs`; both files are added to Governs). The decision, that these four rules are information and a person reviews them, is unchanged.
