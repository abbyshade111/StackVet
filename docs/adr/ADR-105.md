# ADR-105: The phone, two-factor, and recovery changes are tried as the email change is, and V7.5.1 is whole only when each is refused or confirmed not offered

**Status:** accepted, 12 October 2026, in the pull request that builds it. The owner's word on backlog 0232 group G,
passed on by the session organizing the backlog the same day: `change-phone`, `change-two-factor`, and
`change-recovery` beside `change-email`, each judged like the email change and used only on an account made through
`signup`; a `not-offered` list, which the owner asked to confirm in `sv review`, sealed as `[scope-review]` is; and
V7.5.1 whole only when the email change was tried and refused and each of the other three was tried and refused or is
confirmed not offered, an unconfirmed list staying the AI tool's word, in part. The password-change sample and TOTP
beside an emailed code stay out (ADR-090).

**Governs:** `crates/sv-check/src/signed_in/account_changes.rs` (how each change is tried and judged),
`crates/sv-manifest/src/lib.rs::AccountChange` and `crates/sv-manifest/src/lib.rs::AccountChangesReview` (what
stackvet.toml says), `crates/sv-cli/src/review.rs::record_not_offered` (the owner's confirmation),
`crates/sv-check/src/seal.rs::account_changes_review_fields` (what the confirmation is sealed over), and
`crates/sv-cli/src/assemble.rs::account_changes_whole` (when V7.5.1 is met whole). A pull request that changes these
changes this record too, or says in its description why it does not (`docs/adr/README.md`).

## Context

V7.5.1 asks for full re-authentication before changes to the details that affect authentication: the email address,
the phone number, the two-factor settings, and what is used to recover the account. Since backlog 0244 `sv` tried the
email change alone, signing up an account, asking for the change with a wrong password and then the right one, and
signing in with the new address to see whether it took. ADR-053's "Later" entry marked that credit in part, because
the other three were never tried. Few apps have all four, so a requirement that could only ever be met in part was
also unfair to an app that offers no phone number at all.

## Decision

**Three keys beside `change-email`.** Each of `change-phone`, `change-two-factor`, and `change-recovery` under
`[stack.run.users]` is the request that makes the change, with `{password}` for the current password and
`{new_value}` for the new value, and `shows`, a private page that lists the value once the change takes. None of the
three is something to sign in with, so where the email check signs in with the new address, these look for the new
value on that page. The value is a phone number for `phone` and `two-factor` (the number the codes go to), and an
email address for `recovery`. Each kind, and the wrong and the right attempt, take values from different parts of the
run's random string, so no value can be mistaken for another on the page. A phone number is found by its digits alone,
since apps write numbers in their own formats.

**Judged as the email change is.** All three share one account made through `signup` and one signed-in session, so a
run stays inside the sign-ins the spec states (`SIGN_INS_IN_A_RUN`). For each: the change with a wrong password, then
the page; the value there is a finding, High, under a rule of its own (`probe.phone-change-without-password`,
`probe.two-factor-change-without-password`, `probe.recovery-change-without-password`). Otherwise the change with the
right password, then the page: the value there credits the rule, in part; no value is not assessed, because a refused
change means nothing beside a change that never takes. A page that cannot be opened is not assessed, and says so. A
crash at the wrong-password change or its page is withheld from the credit (`RESTS_ON_A_REFUSAL`).

**`not-offered`, confirmed by the owner.** `[stack.run.users] not-offered` lists any of `phone`, `two-factor`, and
`recovery` the app has none of, in place of its key. Nothing listed is tried. It counts only once the owner confirms it
in `sv review`, which writes `[account-changes-review]` with the list as it stood, who, when, and a seal over them, as
`[scope-review]` is written (ADR-024, Later). A list changed after it was confirmed is unconfirmed again. An
unconfirmed list, written by the AI coding tool or by hand, counts for nothing, and the report says so as a gap.

**Whole only when every part is covered.** Where the report is put together, V7.5.1 is met whole when the email
change is credited and each of the other three is credited or confirmed not offered. Then every V7.5.1 credit loses
its "in part", and when any part rests on the owner's confirmation the credit says which, so a reader can tell what
`sv` tried from what the owner said. Otherwise each credit stays in part.

## Alternatives considered

- **Sign in with the new value**, as the email check does: none of the three is a sign-in name.
- **A change of the two-factor settings that sets nothing**, such as turning two-factor off: there is no value to look
  for on a page, so it cannot be judged this way. It is written as the number the codes go to; an app whose only
  two-factor change is something else is not assessed for it, and the report says why.
- **Trusting `not-offered` as written**: it would let the tool that wrote the app say a requirement is met by leaving
  things out. The owner asked for it to be confirmed.
- **A sign-in for each attempt**, as the email check does: nine more sign-ins, which went past the spec's sixty in the
  scripted runs. One session serves all three, since none changes how the account signs in.

## Consequences

- A builder who names the three changes, or confirms what the app does not offer, can have V7.5.1 checked whole. Until
  then the report shows it checked in part, as before.
- Each new check needs a page that lists the value within the first 4,000 characters `sv` keeps of an answer; a value
  further down, or one the page writes differently, reads as a change that did not take.
- The owner is asked one more question in `sv review` when `not-offered` lists anything.
- **Broken on purpose, each put back:** the wrong attempt's value not looked for (each flaw went unfound), the right
  attempt's control skipped (a change that never takes was credited), the owner's confirmation not required (an
  unconfirmed list made V7.5.1 whole), the list compared without `still_holds_for` (a changed list kept counting), and
  the seal not checked (a review written by hand counted).

## Later, 15 October 2026: the password left out (backlog 0561, ADR-119)

Each of the three changes is now also sent with the password field left out, between the wrong password and the right
one, and read on its `shows` page as the others are. A change taken that way is a finding ("... with the password left
out"), since an app that checks the password only when it is sent refuses a wrong one and takes this. A credit now
says the change was refused both ways. What makes V7.5.1 whole is unchanged. The fake app's flaw
`account_change_password_only_if_given` is the witness (`crates/sv-check/src/signed_in/account_changes_left_out_tests.rs`).
