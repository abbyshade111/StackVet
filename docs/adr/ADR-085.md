# ADR-085: A stand-in name server on the fenced network records the names an app asks for

**Status:** accepted, 10 October 2026, in the pull request that builds it (0240, option 1). Proposed the same day with the
backlog claim. The owner's choice, the same day: option 1 of the three set out in the claim; the owner moved 0240 ahead
of the dashboard (0227). Where the build differs from the plan below, see "Where the build differs" at the end.

**Governs:** `crates/sv-run/src/docker.rs`, `crates/sv-run/tests/fence.rs`, `crates/sv-run/assets/*.mjs`. The name server
is one more script in that folder, run in the Node image the fence already uses. A pull request that changes how the
fenced network is made, or what runs on it, changes this record too, or says in its description why it does not.

## Context

ADR-019 makes the app run on a network with no way out: the network is `--internal`, with no gateway (`NO_GATEWAY`), and
a check that the gateway is really absent. The fence keeps the app from reaching anything. It does not record what the
app tried to reach. Backlog 0240 asks for that record, because the names an app looks up are the only way to see an app
calling home.

Today an app that looks up a name gets no answer, because the fenced network has no DNS. The name lookup fails, and
nothing is written down.

## Decision

On the fenced network, a stand-in name server runs for the length of the run. It answers each name the app asks for with
SERVFAIL, the answer a name gets today, so the app sees the same result as now. (Corrected 10 October 2026, before the
build: the first draft said NXDOMAIN. Measured on Docker 29.5.2, an internal network answers an outside name with
SERVFAIL, with or without the stand-in as the DNS server, so NXDOMAIN would have changed the app's result.) It writes down, for the report,
each name and query type it was asked, and when. Nothing else changes: no address is reached, and no outside name is
resolved.

- **The server is a script in the Node image the fence already uses**, pinned by digest (`PROVIDER_IMAGE`), using only
  built-in modules, as the test provider does. No new helper image.
- **The record is kept beside the report, as the other kept output is** (`seen.json`, ADR-082): the name, the query
  type, and the time, each name redacted by the secret rules before it is kept, the way every other kept string is.
- **No TCP listener.** Connections made by address, rather than by name, are not seen. That is the limit of this option,
  and the report says so where it applies.

## Considered

- **Option 2, a name server plus a catch-all TCP listener.** It would also see connections by address. It needs routing
  rules in the fence and extra container privileges: a larger change to the boundary. Declined for now; it can be a later
  record.
- **Option 3, do not build it, and say in the documentation that attempts are not recorded.** Smallest, but leaves the
  question unanswered.

## Consequences

- An app's result should not change: it fails to resolve names as it does today. The build measures this by running the
  example apps with and without the server, and the two runs must agree on each requirement, or the difference is written
  down and decided.
- A name can carry a secret in a subdomain. Redaction applies before anything is kept, and a test plants one and checks
  that it does not reach the record.
- A new file appears in the report folder. It is named in the report, and it is left out when the server did not run.
- The fence's own check (that the network has no route out) is unchanged, and stays the first thing a run proves.

## Where the build differs

Built in the pull request that accepts this record (backlog 0240), 10 October 2026:

- **The names go into `seen.json`, not a new file.** The report already keeps `seen.json` for what the app answered
  (ADR-082), so the names sit under its `stand_ins` as `names`. When the name server did not run, the key is absent, so
  a reader cannot take it for "asked nothing". An empty list means it ran and the app asked for no name.
- **Each name appears once.** The same name is asked for twice per run as an IPv4 address and an IPv6 one, and again on
  each retry, so each name and address type is one entry with a count (`asked`) and the time the first question came.
- **The script is passed on the command line**, as the test provider's is; no file is written to the owner's disk.
- **The report says how many lookups were made, not which names.** The run's paragraph gives the count, that each was
  answered SERVFAIL, and where the names are kept. The names are not repeated in the report, so the report never shows a
  name that the redaction has not passed.
- **Measured against the plan.** Each of the three example apps (`flask-booking`, `notes-with-users`, `oidc-notes`) was
  run twice with `sv report --run`: once with this build, and once with `main`, which has no name server. Every
  requirement's verdict matched in all three pairs. The differences were the run's own timings and random ids, and, on
  the side with the name server, the sentence saying the app looked up no names. A separate check, on a copy whose start
  asks for one name, showed the lookups kept as two entries with four questions each. This is the test the plan asked
  for. The apps asked no names, so the name server changed no result they could show.
