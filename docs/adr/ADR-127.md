# ADR-127: The test sign-in provider mints access tokens and logout tokens, so the app's own checks of them are seen

**Status:** accepted, 16 October 2026, in the pull request that builds it (backlog 0500, second part). The owner's
choice of 14 October 2026, written on the item: build it after the three probe sweeps, "a record of its own, since it
changes what sv runs inside the fence". Written by the orchestrating session.

**Governs:** `crates/sv-run/assets/oidc-provider.mjs` (its access-token, ID-token, logout-token, and introspection endpoints),
`crates/sv-check/src/oidc/tokens.rs`, the back-channel logout field of `crates/sv-manifest/src/lib.rs::OidcSection`
and its line in `crates/sv-manifest/src/spec.rs`, and the V7.6.2 citation on `crates/sv-check/src/oidc.rs::CROSS_SESSION`.
A pull request that changes what the provider mints, what the checks send, or what they credit or cite changes this
record too, or says in its description why it does not (`docs/adr/README.md`).

## Context

The test provider inside the fence signs anybody in and can be told to get the next ID token wrong in one way. Backlog
0500 found three more things it could show, with no new machinery outside the fence:

- **V10.3.1:** a resource server accepts only access tokens meant for it. An app that takes the provider's access
  tokens as bearer tokens should refuse one the provider issued for another service.
- **V10.5.5:** with OIDC back-channel logout, the app checks a logout token's type (`logout+jwt`), that it carries the
  logout `events` claim, and that it carries no `nonce`, before it ends anybody's session.
- **V7.6.2:** a session is created only with the person's consent or an explicit action. The existing cross-session
  probe already shows a sign-in finished in a browser that never started it.

Two other proposals on the item are not taken here. V10.3.3 is about a resource server identifying a user from an
access token; the existing same-email probe reads ID tokens, so citing it there would claim what it does not show.
V10.5.3 needs the provider's published details to be wrong from the moment the app first reads them, which means a
second start of the app; the run starts it once.

## Decision

- **The provider mints two kinds of token on request, inside the fence only.** `POST /_sv/access-token` with
  `aud=self` or `aud=other` returns a signed access token (`typ: at+jwt`) for this app's client, or for a client that
  does not exist. Its `/userinfo` answers for either, as a real provider's does, and a new `/introspect` (listed in
  its discovery document) says which client each was issued to. `POST /_sv/logout-token` with `variant=good`,
  `wrong-typ`, `no-events`, or `with-nonce` returns a signed logout token for the test person, correct or wrong in that
  one way.
- **V10.3.1, asked only when the app takes the provider's tokens.** The control first: a token issued to this app,
  sent as `Authorization: Bearer` with no cookie, must open the private page. If it does not, the app is not a
  resource server for these tokens there, and V10.3.1 is not assessed, with that reason. If it does, a token issued for
  another service is sent the same way. Opened is a finding, `probe.oidc-access-token-audience-not-checked`, high.
  Refused, with the app's own token opening the page again afterwards, is *checked in part*: one page, one other
  audience.
- **V10.5.5, asked only when stackvet.toml names the address.** `backchannel-logout = "/backchannel-logout"` under
  `[stack.run.oidc]`. Left out, nothing is sent and V10.5.5 says why. For each of the three wrong tokens, a fresh
  sign-in is made, the token is posted to that address as `logout_token`, and the session is looked at. A session
  ended by any of them is a finding, `probe.oidc-logout-token-not-checked`, medium. The control comes last: a correct
  token must end a fresh session, or nothing is credited. All three refused, with the control working, is *checked in
  part*: the three checks the requirement says the client must make, each once, and nothing of the short expiry it
  recommends.
- **V7.6.2 is cited beside V10.1.2 and V10.2.1** on `probe.oidc-sign-in-from-another-session`. A return from the
  provider taken in a session that did not begin it is a session made without that person's action.
- Every check here runs after the ordinary sign-in has been shown working again, as the module's other checks do.

## Consequences

- An app that takes only cookies says nothing about V10.3.1, and the report says why, rather than crediting it.
- The provider's new endpoints are reachable only on the fenced network, like its mode endpoint; the fence is
  unchanged.
- Held by `crates/sv-check/src/oidc/tokens_tests.rs`, red with each check's judgement turned around and with the control
  removed; the provider's endpoints by the started-app OIDC test, which needs Docker.

## Later, 16 October 2026: an ID token sent where an access token goes (V9.2.2, backlog 0500)

V9.2.2 asks that a service check a token is the right kind before believing it: only access tokens for decisions about
what may be done, only ID tokens as proof of who signed in. The test provider now mints an ID token on request (`POST
/_sv/id-token`), the same kind a sign-in hands the app, for the test person and this app's client, which its
`/userinfo` and `/introspect` do not know as an access token. `probe.oidc-id-token-taken-as-access-token` asks it only
where V10.3.1 is asked: when an access token issued to this app opens the private page as a bearer token. Then the ID
token is sent the same way. Opened is a finding against V9.2.2 (CWE-287): its signature, issuer, and audience were all
good, and only its kind was wrong. Refused, with the access token opening the page before and after, is V9.2.2 checked
*in part*: one page, and one wrong kind of token. Refused, with the access token then refused too, is not assessed. The
fence is unchanged: the endpoint is on the provider's fenced network, like the others. Held by
`crates/sv-check/src/oidc/tokens_tests.rs`, red with the ID token never taken, with the credit given without the
access token's second try, and with the bearer-token gate removed.
