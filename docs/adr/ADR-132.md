# ADR-132: stackvet.dev is built from the repository first, and where it is hosted is chosen after

**Status:** accepted, 22 October 2026, in the pull request that builds the site; proposed the same day with the
claim for backlog 0376, at the owner's answer of that day, asked in a session where stackvet.dev should be hosted:
"Build first then do some research and provide up to 5 options, a mix of free and low cost, with the pros and cons
and your recommendation".

**Governs:** `tools/website.py`, `crates/sv-cli/tests/website.rs`, `.github/workflows/site.yml`,
`deploy/stackvet.dev/wrangler.jsonc`, `crates/sv-cli/tests/site_workflow.rs`, `docs/website/how-it-works-page.md`,
`docs/website/build-walkthrough-page.md` (with the screens in the folder beside it),
`docs/website/self-assessment/README.md`, and the repository's own `stackvet.toml` (what StackVet's report on itself is held to). A pull request that changes what the
site is built from, where it is written, or that nothing of it is published without the owner's word, changes this
record too, or says in its description why it does not (`docs/adr/README.md`).

## Context

The home page's words and look were settled on 12 October 2026 (`docs/website/home-page.md`, backlog 0224), and the
framework pages are written by `tools/framework_pages.py` into `exports/site/` (ADR-129). Every condition 0376 set for
building is met; going live still waits for the walk-through (backlog 0373) and the owner's word. Where the site is
hosted, and how stackvet.dev and stackvet.app point at it, are the owner's: hosting may cost money.

## Decision

- **Built first, by a script in the repository,** with no dependency beyond Python's own library: the home page, the
  credits page, How StackVet works, StackVet checks itself, and the reports page, beside the framework pages, into
  `exports/site/`, which git ignores, as `tools/framework_pages.py` writes.
- **Read, never copied,** as ADR-129 holds the framework pages: the words from `docs/website/home-page.md` and
  `docs/website/reports-page.md`, the coverage numbers from `docs/COVERAGE.md`, the credits from the licenses the
  repository records, and the self-assessment and its bill of materials from where they are kept.
- **Self-contained:** no script, style sheet, font, or image is fetched from anywhere; the type falls back to the
  system's when Atkinson Hyperlegible is not installed.
- **Hosted on Cloudflare,** the owner's choice of 22 October 2026 from the five options brought after the build
  (Cloudflare, GitHub Pages, Netlify, Codeberg Pages, and Bunny.net): "Let's go with Cloudflare, the domains are
  registered via Cloudflare already". It serves static files free and without limit, and it is the one free choice
  of the five that sends response headers a site sets, which a security tool's own site should; both addresses' DNS
  is already there, so stackvet.app can redirect to stackvet.dev by a rule on its zone. The build writes `_headers`:
  a content security policy that allows only the scripts the build wrote, by their hashes, and loads nothing from
  elsewhere, with the headers against framing, type guessing, and the referrer.
- **Nothing is published** by building it. Hosting is chosen by the owner from up to five options, free and low cost,
  each with its pros and cons and a recommendation, researched after the site is built and recorded here when chosen.

## Where the build differs

- **The self-assessment is a new one, made for the site,** at the owner's word on 22 October 2026 ("the self
  assessment should probably be updated", and "We could test level 3 that way, too"). The paper's, of 4 October 2026
  (`docs/paper/self-assessment-v2`), stays as it was, since the paper cites it. The new one is `sv report .` on this
  repository with `[app] level = 3` added to its `stackvet.toml` (ADR-130), and is kept in
  `docs/website/self-assessment/`, which says how it was made.
- **Only its small files are kept,** the owner's choice of the same day, since nothing committed is ever removed:
  the folder `sv` wrote was 41 MB, most of it the findings in test and sample code, and the eight files kept are
  about 1.1 MB. The page links them, and says the rest was left out.
- **It is shown as it came out:** 312 things to fix, most of them, by the look of them, StackVet's rules firing on its
  own detection code. The owner chose to build the page now and go through them in an item of their own (backlog
  0633), with nothing set aside until the owner confirms it with `sv review`.
- **The words are read, and the notes on them left out:** a home page section's last list is its notes, and a section
  holding only a line in italics is a placeholder; neither is shown. The coverage numbers the words were written with
  are replaced by `docs/COVERAGE.md`'s, and the build stops if the sentence a number sits in has changed. The AI
  tools named in "Get started" are read from `docs/prompts/setup.md`'s "Tried so far". A button for something not yet
  made (the walk-through, backlog 0373) is shown as coming.
- **How StackVet works** is the paper's description of 4 October 2026, said to be that, with the current drawing of
  the five steps (`docs/website/diagrams/how-it-works.svg`). The inventory of what a run gathers, which the owner
  named for it on 12 October 2026, was a page in a session and is not in the repository.
- **The framework pages** are written into `standards/` (ADR-129, Later).
- **The words of How StackVet works** are kept in `docs/website/how-it-works-page.md`, as the home page's are, with a
  real line from the VS Code build of the setup prompt trial; the home page's opening conversation is the Cursor
  build's, in its own words, at the owner's word of 22 October 2026. Inline styles are allowed by the policy, since
  the pages and the example report `sv` wrote set them in `style` attributes; scripts are not.
- **Held by** `crates/sv-cli/tests/website.rs`, which also hashes every inline script on every page and finds it in
  the policy. With the notes kept, the placeholder shown, the report files not
  copied, or any folder written over, it fails. With the numbers not filled in, only the script's self-test fails,
  since the figures written in the words are today's.

## Later, 22 October 2026: How a build goes, from the owner's screenshots

The home page's *See how a build goes* now leads to a click-through of one real build (backlog 0373): the owner built
a small app for their family in Cursor that evening, with StackVet connected, and took 28 screenshots. The owner
chose to make this one from the build now and the walk-through of a setup later, since the setup (5:51 to 6:03) has
no screenshots; *Watch the walk-through* stays shown as coming.

- **Seventeen screens, in the order taken,** each with a caption that says only what its screen shows, in
  `docs/website/build-walkthrough-page.md`, read by `tools/website.py` as the other pages' words are. One step to a
  section, each with a link to the next, so the page needs no script.
- **Read for anything personal before any was kept,** at the owner's choice of covering over cropping: the owner's
  username and computer name, in the terminal's prompt, are covered by a plain box in two (four places in one), found
  by eye and by `tesseract`; a second search of every kept screen found the name in none. Nothing else personal is
  in any. The originals stay on the owner's drive; what is committed is the covered screens, made smaller (1,400
  pixels wide at most, 96 colors, 2.4 MB in all) in `docs/website/walkthrough/`.
- **Held by** `crates/sv-cli/tests/website.rs`: the button leads to the page, every kept screen is shown once, every
  step but the last leads on, and the notes on the words are left out. With the screens not copied, the button not
  linked, or the notes kept, it fails.

**Later, the same day:** the owner chose to start with the walk-through of the build and leave one of a setup for
later ("I want to just start with the walkthrough for now"). Both of the home page's walk-through buttons lead to *How
a build goes*, nothing is shown as coming, and going live no longer waits on a walk-through of a setup (backlog 0373,
done).

## Later, 22 October 2026: the deploy, which only the owner starts

The owner added the Cloudflare token and account to the repository's secrets and stackvet.app's placeholder record,
and asked for the deploy job ("go ahead and write the deploy job"). Proposed with the claim for it (backlog 0376),
accepted here.

- **`.github/workflows/site.yml` publishes only when the owner starts it** (`workflow_dispatch`): nothing on a push, a
  schedule, or a pull request publishes, so the first run is the site going live, at the owner's word. Its deploy job
  builds the site with `tools/website.py` at the commit it is started from and publishes `exports/site/` with
  `cloudflare/wrangler-action`, a new dependency, pinned to its v4.1.3 commit, with wrangler at 4.148.0 (the newest
  release at least two weeks old that day). Then it asks stackvet.dev for its first page and fails unless the answer
  carries the content security policy, waiting up to ten minutes for the first certificate.
- **A check job, with no secret,** runs on any pull request that changes the site or its deploy: it builds the site
  and has wrangler read the deploy without publishing (`--dry-run`).
- **`deploy/stackvet.dev/wrangler.jsonc`:** a Worker of static files only, no script, at stackvet.dev as a custom
  domain, with no workers.dev or preview addresses. `tools/website.py` writes `.assetsignore` so the folders' own
  markers are not uploaded.
- **The token reaches the deploy step alone,** through the action's inputs; the workflow can only read the
  repository. The redirect from stackvet.app is a rule on that zone, the owner's to add.
- **Held by** `crates/sv-cli/tests/site_workflow.rs`. With the workflow publishing on a push, its deploy running on any
  event, or the token handed to the check job, it fails.
