# ADR-147: An authorization server's own published details, and its lifetime settings, are read

**Status:** accepted for the published details, 24 October 2026, in the pull request that builds them; the settings
check is still proposed, and becomes accepted in the pull request that builds it. Proposed the same day with the claim
for backlog 0625's sixth part.

**Governs:** the authorization-server metadata read (which addresses are asked, and what each answer concludes) and the
authorization-server settings check (which libraries' settings are read, with which defaults): the two requests
are added to `crates/sv-check/src/probes.rs`, and the read is `crates/sv-check/src/as_metadata.rs`, with its tests
(`crates/sv-check/src/as_metadata/tests.rs`); the settings check's module is named by its path in the pull request that
builds it. A pull request that changes what is
asked, what an answer concludes, or which defaults are assumed, changes this record too, or says in its description
why it does not (`docs/adr/README.md`).

## Context

V10.4 and V10.6 apply to an app that is an authorization server, one that other applications send their users to so
they can sign in (the `authorization-server` condition). Nothing in `sv` spoke to them. Such a server publishes what
it accepts in its metadata: RFC 8414's `/.well-known/oauth-authorization-server`, and OpenID Connect's
`/.well-known/openid-configuration`. Two libraries most such Python and Node apps use set the lifetimes V10.4.3 and
V10.4.8 ask about. Their documentation, read 24 October 2026: django-oauth-toolkit's `OAUTH2_PROVIDER` settings,
`AUTHORIZATION_CODE_EXPIRE_SECONDS` defaulting to 60 and `REFRESH_TOKEN_EXPIRE_SECONDS` defaulting to `None`, "which
means refresh tokens never expire"; node-oidc-provider's `ttl`, `AuthorizationCode` defaulting to 60 seconds and
`RefreshToken` to 14 days, with `rotateRefreshToken`'s default refusing to rotate once a token has lived a year.

## Decision

- **Two more read-only requests in every run that starts the app:** `GET /.well-known/oauth-authorization-server` and
  `GET /.well-known/openid-configuration`, sent through the probe sidecar to the copy of the app `sv` started, as its
  other requests are. Not a new connection: the app is the only thing asked. An answer that is not a JSON object with
  an `issuer` concludes nothing.
- **What an answer concludes:**
  - V10.4.16 (level 3): "token_endpoint_auth_methods_supported" listing "client_secret_basic", "client_secret_post",
    "client_secret_jwt", or `none`, or left out (RFC 8414 then means "client_secret_basic"), is a finding; listing only
    "private_key_jwt", "tls_client_auth", or "self_signed_tls_client_auth" is credited in part: what the server says it
    accepts, not what each client is set to.
  - V10.6.1 (level 2): "response_types_supported" with any value holding `token` is a finding (an implicit flow); only
    `code`, "id_token", and `code id_token` is credited in part.
  - V10.4.6 (level 2): "code_challenge_methods_supported" listing `plain` is a finding; it never credits, since what the
    server says it supports is not that it requires PKCE.
- **The settings, read from the code:** django-oauth-toolkit's `OAUTH2_PROVIDER` and node-oidc-provider's `ttl` and
  `rotateRefreshToken`, with the defaults above for a setting left out, in an app that has the library.
  - V10.4.3 (level 1): an authorization code living longer than 10 minutes (1 at level 3) is a finding; within it is
    credited in part (a setting, not the server's behavior).
  - V10.4.8 (level 2): django-oauth-toolkit with `REFRESH_TOKEN_EXPIRE_SECONDS` unset or `None`, and node-oidc-provider
    with `rotateRefreshToken: true` (rotation with no cap), are findings; a set limit is credited in part. A setting
    given by a function or read from the environment is not judged, and says so.

## Alternatives considered

- **Probe the server's behavior.** That is backlog 0625's seventh part, which needs a test client; the published
  details and settings are the cheap first step, and say which servers offer dynamic registration.
- **Ask the two addresses only when stackvet.toml says the app is an authorization server.** Rejected: two read-only
  requests to the app's own copy cost nothing, and an app that is one without saying so is still read.

## Consequences

- An authorization server that offers weak client authentication, an implicit flow, or `plain` PKCE is told so from its
  own words; one whose refresh tokens never expire is told which setting to add.
- A run that starts the app sends two more requests to it.

## Where the build differs

The published details, built 24 October 2026 (the first pull request). The three checks are
"probe.authorization-server-weak-client-auth" (V10.4.16), "probe.authorization-server-implicit-flow" (V10.6.1), and
"probe.authorization-server-plain-pkce" (V10.4.6). V10.6.1 is read from the OpenID document alone, since it is about an
OpenID provider; client authentication and PKCE from either. A run keeps the first 4,000 characters of each answer
(`sv_check::probes::KEPT_CHARS`, so a run never copies a page out of an app); a document longer than that does not
parse, and concludes nothing, which leaves its requirements not verified rather than read from half a document. The
suite's own count of what it asks (`probes::tests`) names the two requests.
