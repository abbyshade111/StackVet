# ADR-019: `sv` runs the app in a container on a network with no way out

**Status:** accepted. Decided with `sv run`'s design (DESIGN, "Running the code" and "`sv run`", from 22 to
24 September 2026) and written down here on 27 September 2026, because the ADR analysis found that no record
named it (BACKLOG, "Records that disagree with what was built", item 8).

**Governs:** `crates/sv-run/src/docker.rs`, `crates/sv-run/src/docker/fence.rs`, `crates/sv-run/src/docker/probes.rs`, `crates/sv-run/src/docker/containers.rs`, `crates/sv-run/src/docker/helpers.rs`, `crates/sv-run/tests/fence.rs`, `crates/sv-run/assets/*.mjs`, `crates/sv-run/src/image_reference.rs`, `crates/sv-run/src/install.rs`, `crates/sv-run/src/name_server.rs`, `crates/sv-run/src/exec_session.rs`, `crates/sv-run/images/Dockerfile`. A pull request
that changes any of these changes this record too, or says in its description why it does not (`docs/adr/README.md`).

**Replaces, for `sv`:** v1's ADR-010 (on the `v1` branch), which ran generated code as a Node process under
Node's permission model and rejected containers because "Docker is not available on the target machine". That
record describes v1 and stays as it was.

## Context

The strongest evidence about an app comes from running it: signing in as a test user and asking what that user
can reach. v1 could run the apps it wrote because it knew they were Node: it started them under Node's
permission model, which limits the file system, and two days later fenced their network with `sandbox-exec` on
macOS and a network namespace on Linux (`pipeline/net-fence.ts`). ADR-010 was not updated for the second step.

`sv` checks apps it did not write, in any language, so it can neither assume Node nor rely on Node's
permission model. It also runs somebody else's code, which may be careless or hostile, on the owner's own
computer. A container backend became available on the owner's machine on 22 September 2026 (Colima 0.10.3 with
Docker 29.8.1), which removed ADR-010's reason for rejecting one.

## Decision

`sv run`, and `sv report --run`, start the app in a container, fenced as follows:

- **The network is created with `--internal`**, so nothing on it can reach anything outside it. The runner
  then asks Docker whether the network really is internal, and refuses to start the app if the answer is
  anything but yes. Passing the flag and checking it are different claims, and only the second survives an
  edit that drops the flag.
- **Nothing is published to the owner's computer.** The probes run from a small helper container on the same
  internal network, not from the host.
- **The app's folder is mounted read-only**, the only writable place is a small in-memory folder for a test
  report, and the app is given none of the owner's environment: no keys and no home folder.
- **The helper containers get less still.** The helper that sends the probes, and the stand-in mail server,
  sign-in provider, AI model, and browser, have a read-only file system, no capabilities, and no way to gain
  privileges.
- **No container backend means "not assessed".** Everything that needs the app running is reported as not
  assessed, never as passed or failed, and the reports say which applied.

## Alternatives considered

- **Keep v1's approach**, a process under a language's own permission model with an OS network fence. It
  works only for languages that have such a model, and `sv` checks apps in any language.
- **A container on Docker's default network, probed through a published port.** This was measured, not
  assumed: on the default network the app reached `1.1.1.1:53`, so the fence was gone. On an `--internal`
  network it did not, and the host could not reach a published port either, which is why the probes moved
  into a helper container.
- **Run nothing, and check only files.** This loses every requirement that only a running app can answer:
  sign-in, sessions, access control, and uploads.

## Consequences

- The owner needs Docker, or a compatible backend such as Colima, for anything that runs the app. Without it,
  those requirements say *not assessed*, and the report says why.
- Docker downloads the images `sv run` starts the first time each is needed: the image the manifest names for
  the app (`image` under `[stack.run]`), and `busybox`, `axllent/mailpit`, `node:22-alpine`, and
  `chromedp/headless-shell` for the helpers. That is Docker's connection, not `sv`'s, and the README says so.
- The `sv` container image cannot run apps itself, because starting containers from inside a container means
  handing it the Docker socket, which is control of the owner's computer (DESIGN, "`sv` in a container").
- An app that needs to reach an outside service to start or work cannot be fully checked this way. The fence
  is the point, so `sv` supplies stand-ins on the fenced network instead: a mail server, a sign-in provider,
  and an AI model.

## Later, 30 September 2026

The weekly review of the records found one sentence above that is not true of the code. "The only writable place
is a small in-memory folder for a test report" holds for the app's folder, which is mounted read-only, and for every
helper container, which runs with `--read-only`. It does not hold for the app's own container: `sv-run` starts it
without `--read-only` (`crates/sv-run/src/docker.rs`, the `run` arguments for the app), so the app can write
anywhere in its container's own file system outside `/app`, such as `/tmp`. That space is Docker's storage, not the
owner's folder, and it is removed with the container. The in-memory folder for the test report is given no size
limit either, so "small" is not enforced. The comment beside that code said the same as this record and is
corrected. Whether the app should run read-only too, with an in-memory `/tmp`, is a choice with a cost (an app or a
build step that writes elsewhere would fail) and is in the backlog.

## Later, 3 October 2026

The owner chose read-only. The app's container now runs like every helper: `--read-only`, `--cap-drop ALL` and
`no-new-privileges`, with two in-memory folders as its only writable places, `/tmp` (256 MB) and the test-report
folder (16 MB). The arguments are built by `app_args` in `crates/sv-run/src/docker/containers.rs`, so a test reads them, and
`the_app_is_hardened_like_every_helper` turned red when each flag or size was removed in turn.

Measured before and after, with `sv run` on every example app and on a small app that refuses to start unless it is
contained:

- That app, under the old arguments, could write to `/etc` and held Docker's default capabilities
  (`CapEff 00000000a80425fb`). Under the new ones it could write only to `/tmp`, held none, and started.
- The four example apps that start gave the same results before and after, check for check, including the
  signed-in checks, the headless browser, and the app's own test suite writing to the report folder.
- `examples/flask-booking` did not start before or after: its build step, `pip install`, cannot download anything
  behind the fence. What it last printed changed, from the network refusal to "site-packages is not writeable",
  and neither line names the cause, so the report now says that a build step runs inside the fence, where nothing
  can be downloaded and nothing outside `/tmp` written, and that packages belong in the image.

The cost is the one recorded above: an app that writes outside `/tmp` while it runs now fails to start, and the
report says where it may write.


## Later, 4 October 2026: the network's gateway

The deep review of `sv` at `eff3f17` found a way out that this record's title denies (S2, high): `docker network create
--internal` stops traffic to the internet but still gives the network a gateway address, and that address is the host
(this computer on Linux, or the virtual machine Docker runs in on Docker Desktop and Colima). The review's fenced
container reached the Colima machine's SSH server. Fixed the same day (#558): the network is made with no gateway
address where Docker allows it, and before the app starts a throwaway container knocks on every address a gateway could
have; an answer, or a refusal, stops the run. The fence test now needs a plain `--internal` network to be refused, so a
pass proves something. DESIGN, "The fence's gateway".

## Later, 4 October 2026: the release build must keep unwinding

The containers and network a run starts are removed by `Teardown`'s `Drop` (`crates/sv-run/src/docker.rs`), and a
`Drop` runs when a check panics only because the release build unwinds. Switching `[profile.release]` to `panic =
"abort"` to make the binary smaller would leave a run's fenced containers running whenever a check panicked. The reason
was until now only a comment in `Cargo.toml` and a sentence in DESIGN, "A release profile" (#330); nothing tests it,
so it is said here. Ctrl-C and a run killed outright are ADR-025's.

## Later, 4 October 2026: limits on what the app may use

The deep review found that the app ran with no limit on memory, processes, or processors, and that `sv` kept
everything a command printed (S9, medium). An app that leaks memory, starts processes without end, or answers with
gigabytes could take the owner's computer down with it, and the app is code `sv` was asked to check, not code it
trusts. Every container a run starts now gets the same limits, added in the one place every `docker run` passes
through (`DockerBackend::prepared`), so a helper written later cannot be missed: 2 GB of memory and no swap beyond
it, 512 processes, and two processors, or all of them when Docker has fewer. The browser's and the mail server's
in-memory folders now have a size, as the app's already did. `sv` keeps at most 32 MB of what any command prints on
each stream; the rest is read and thrown away, so the command never waits on a full pipe. A Docker call whose output
was cut is never handed to a check as an answer, and a test suite's output says where it was cut. DESIGN, "Limits on
what the app may use".

The review also asked for `--user`, so the app does not run as root inside its container. That was weighed and left
out. Every capability is already dropped, so root inside the container cannot read another user's files, change
ownership, or bind a privileged port, and `no-new-privileges` stops it gaining any. Many images install their
packages under root's home folder or with root-only permissions, so a fixed other user would make apps fail to start
for a reason that has nothing to do with their security. If that changes, it is a record of its own.

## Later, 4 October 2026: each run removes only its own

The deep review found that a run was named from the process id alone and torn down by name (S10, medium). Two copies
of `sv` in two containers sharing one Docker daemon, as on a CI runner, are often the same process number in their
own containers, so they gave their runs the same names and each run's teardown could remove the other's containers.
A run's name now ends in four random bytes, and everything it creates, containers and its network alike, carries
the label `org.securevibe.run` with that name. Its teardown removes what Docker lists under that label, by id, and
falls back to the run's own names only if Docker will not list them. The owner label that the next run's cleanup
reads after a crash is unchanged. DESIGN, "Each run removes only its own".

## Later, 5 October 2026: the browser's DevTools on loopback, and the driver in a world of its own

The deep review's S11. The browser image's own start script forwards port 9222 on every address to Chromium's
DevTools, so the app, on the same fenced network, could reach the browser by its address and drive it: read what
it reads, and change what it sees. Reproduced with `chromedp/headless-shell:151.0.7922.109` on an internal network:
another container got DevTools' version answer from the browser's address. Built by session securevibe-e9 at the
owner's asking, in branch `claude/securevibe-e9-s11`.

- **Chromium is started directly** (`--entrypoint /headless-shell/headless-shell`), with DevTools on 127.0.0.1
  alone. The driver shares the browser's network, so it still reaches DevTools there, and nothing else does. The
  image's forwarder is not started.
- **The driver runs every expression in a world of its own** in the page (`Page.createIsolatedWorld`), the same
  page and storage with none of the page's scripts, so the app cannot redefine what the sign-out check reads
  with. When that world cannot be made, the action fails rather than reading through the page's world.
- Storage is still read with the page's interfaces in that world, not through DevTools' storage domains, which the
  review also named; the world of its own already keeps the page's scripts out of the reading.

Held by `the_app_cannot_reach_the_browser_s_devtools_or_hide_its_storage_from_the_driver`, against a real browser
and an app that redefines `Storage.prototype.getItem` and `Object.keys`, and by
`the_browser_and_its_driver_are_fenced_and_hardened_like_the_sidecar`, which needs no container backend.

## Later, 5 October 2026: the driver watches the page's workers and WebSockets

The deep review's improvement 5, last part. The browser driver recorded what the tab itself tried to send to other
sites, which the V14.2.3 check reads, and nothing a worker sent or a WebSocket opened. It now asks the browser to
report and hold each worker, shared worker, and service worker the page starts, watches its requests, and then lets
it go, and it records each WebSocket the page opens to another site. What the app may do is unchanged; the browser
sees more of what it tries, so the check can find more and claims nothing new as passed. Built by session
securevibe-e9 at the owner's asking, in branch `claude/securevibe-e9-ws-workers`.

Held by `what_a_page_sends_elsewhere_from_a_worker_or_over_a_websocket_is_recorded`, against a real browser.

## Later, 7 October 2026: packages installed before the run (ADR-052)

The app still runs on a network with no way out, its folder read-only. When the owner sets `install = true`, one
container more runs before it: given only the app's dependency files, on Docker's ordinary network, it downloads the
packages without running any of their code, into a volume the app is then given read-only. That container is the
only part of a run that can reach the internet, and the report says when it ran. Everything else in this record stands.

## Later, 8 October 2026: the hardening in one place, as the limits are

The architecture assessment of 8 October 2026 (BACKLOG, "From the architecture assessment of 8 October 2026", item
2) counted the hardening arguments every container carries, `--read-only --cap-drop ALL --security-opt
no-new-privileges`, written out at eleven places in `docker.rs` and one in `install.rs`; the 4 October entry above
had already put the *limits* in the one place every `docker run` passes through, `prepared`, and the fallback for a
run without a sidecar had once been started with no hardening at all for exactly this reason. The five arguments
now go on in `prepared` too (`docker::HARDENING`, `hardened`), for every `run` and `create` and never for an `exec`,
and no builder carries a copy. The fallback path (`inside_fence_with_input`) now goes through `prepared` as well, so
it gets the limits and the run label it lacked. Nothing a container is started with changes; where it is said does.

Held by `every_container_started_is_hardened_in_one_place_and_a_plain_exec_is_not` (`crates/sv-run/src/docker/probe_tests.rs`)
and by each container kind's own test asserting through `prepared` that the flags arrive once and that the builder
wrote none of them. The one place removed on purpose: seven tests failed, one per container kind and the chokepoint.

## Later, 8 October 2026: `image` is held to Docker's grammar before it reaches a command line

The review of `sv` that day (BACKLOG, "From the review of 8 October 2026", item 6) said `image` under `[stack.run]`
was not checked against Docker's reference grammar. `sv run` passed it to `docker run` and `docker create` as the
one argument where the image goes, and an argument beginning with a dash is an option there: an `image` of
`--privileged`, written into a manifest by whoever wrote the app, would have reached Docker as a flag, and the fence
this record describes is made of such flags. **`image` is now held to Docker's own grammar** (`distribution/reference`:
an optional registry with a port or a bracketed IPv6 address, lower-case path components joined by `.`, `_`, `__`, or
dashes, a tag of up to 128 characters, a digest of an algorithm and at least 32 hexadecimal digits, 255 characters in
all) before the plan is made (`sv_run::image_reference`, `CannotRun::BadImage`), and a value that is not a name is
refused with its reason in plain words, the run reported as not assessed. The check lives in `lib.rs`, where the plan
is read from the manifest, so no path to Docker misses it. Held by `image_reference`'s own tests and
`crates/sv-run/src/image_tests.rs`.

## Later, 9 October 2026: the app is told where Google's Gemini test model is

The gap analysis of 7 October 2026, finding 13(g). The app inside the fence was given the test model's address and a
placeholder key in the variables the OpenAI and Anthropic libraries read, and nothing for Google's, so an app that
called Gemini reached no model and every AI check was not assessed for it. It is now also given
`GOOGLE_GEMINI_BASE_URL`, set to the test model's address, and `GEMINI_API_KEY` and `GOOGLE_API_KEY`, set to the same
placeholder key as the others (`model_env` in `crates/sv-run/src/docker/containers.rs`). Google's own libraries read these:
`google-genai` for Python (2.29.0, `google/genai/_base_url.py`) and `@google/genai` for JavaScript (2.28.0, its Node
build) take the address from `GOOGLE_GEMINI_BASE_URL` and the key from either name; read in their source on this day,
since Google's documentation names only the key. With both key names set, the Python library logs one line saying it
uses `GOOGLE_API_KEY`; both are given because code written against older libraries reads one or the other.

Nothing here opens the fence: the address is the test model's on the fenced network, and the key works nowhere. An
app that writes Google's address into its own code still reaches nothing, and the AI checks say so as before.

## Later, 9 October 2026: a backend runs Linux containers, and is given folders in the short form

Docker counts as a backend only when it runs Linux containers. Until now `docker info` answering was enough; on
Windows, Docker can be set to Windows containers, and then it answers and refuses every container `sv` starts (the
app's image, the probe sidecar, the install step are all Linux ones) in words that read like a fault of the app's.
`sv` now asks `docker info --format {{.OSType}}`: `linux` is a backend; `windows` is no backend, said with what to
change (in Docker Desktop, "Switch to Linux containers"); anything else is no backend with what Docker said. No
backend means what it always has: everything that needs the app running is not assessed, never passed or failed.
Found by the Windows workflow, whose runner is set that way (backlog 0120, sixth Windows finding).

On Windows the folders handed to Docker (`-v`) come from `sv_frameworks::paths::canonical`, in the short form
`C:\...`, which Docker reads, rather than the standard library's long form `\\?\C:\...`, which it refuses. On macOS
and Linux nothing changes. Neither has been tried yet with Linux containers on a Windows computer.

## Later, 10 October 2026: the app's name lookups go to a stand-in name server on the same fenced network (ADR-085, backlog 0240)

The fence is unchanged: the network is still `--internal`, with no gateway, and the check that it is closed still runs
first. What is new is one more helper on that network: a name server, run from the pinned Node image (`PROVIDER_IMAGE`,
the same image the test sign-in provider uses) with its script, `crates/sv-run/assets/name-server.mjs`, passed on the
command line, so nothing is written to disk. The app is started with `--dns` pointing at it. It answers every name with
SERVFAIL, the answer a name gets on the fenced network today, and it resolves no outside name. Its one job beyond that
is to write each question it is asked into its own log, which `sv` reads before the container is removed.

The list above names the helper images by tag. Each is now run by its digest as well as its tag: `busybox:1.36`,
`axllent/mailpit:v1.31`, `node:22-alpine`, and `chromedp/headless-shell:151.0.7922.109`, with the digest the registry
gives for that tag. A moved tag cannot change what runs. The run record lists the helper images by name and digest, and
the app's own image digest when the app was run, read from the local Docker. The decision stands: the same images, no
network of their own; this only pins which bytes of each. The digests were read from the registry's manifest headers
on 10 October 2026, and are to be checked by a `docker pull` on a computer that runs Docker.

## Later, 13 October 2026: the helper images are named in one file, and Dependabot moves them (backlog 0317)

The deep review of 12 October 2026 (backlog 0277) found the pins above held in the code alone. CI fetched the helper
images by tag before the tests, so it fetched what the tag pointed to that day, not what `sv` would run. Nothing
proposed a new fingerprint when an image had a security fix.

- **One file names them.** `crates/sv-run/images/Dockerfile` holds one line per helper image, `FROM <name>:<tag>@sha256:<digest>
  AS <stage>`, for the stages probe, mail, provider, and browser. The file is never built. `docker.rs` reads each
  image from it when `sv` is compiled, so a missing line stops the build rather than leaving a helper unnamed. The
  suite's two fetch steps read it with `awk`, as the image job reads the root Dockerfile. A test holds the three
  readers to the same four images, and fails if the workflow names mailpit or the headless browser itself.
- **Dependabot moves it.** Its `docker` entry for that folder proposes a new fingerprint, and sometimes a new tag, each
  week after a seven-day wait. CI then runs the whole suite against it before it can merge. A new tag is a change to
  what every `sv run` starts. A new browser version can change how pages are drawn, and a new Node major version the
  helpers' scripts run on. Each arrives as a pull request to review, never on its own.
- **What stays by tag.** The tests name the app's own image by tag, as an owner's manifest would (`busybox:1.36`,
  `node:22-alpine`, `python:3.12-slim`). CI fetches those three by tag. `sv` records the digest an app's image was
  run by (above); it does not choose that image.

## Later, 13 October 2026: the gateway fence holds over IPv6 too (backlog 0300)

A daemon set to give new networks IPv6 (`daemon.json`, `default-network-opts` with `com.docker.network.enable_ipv6=true`,
Docker 27 and later) gives the internal network an IPv6 subnet whose gateway is the bridge: the host, or the virtual
machine Docker runs in, just as the IPv4 gateway is. The network was made isolating the IPv4 gateway alone, and the
gateway check read IPv4 addresses alone, so such a network passed while the app could reach the host over IPv6 (the deep
review's S2 again). Now:

- The network is asked for first with both `com.docker.network.bridge.gateway_mode_ipv4=isolated` and
  `com.docker.network.bridge.gateway_mode_ipv6=isolated`; a daemon that refuses that pair gets the IPv4 options as
  before, in the same order.
- The gateway check reads every gateway and subnet of either family and knocks on each, from a container on the network,
  skipping only an address that is the knocking container's own. An IPv6 gateway that answers stops the run as an IPv4
  one does; a netcat that cannot say either way about an IPv6 address stops it too, rather than passing.
- `crates/sv-run/tests/fence_ipv6.rs` makes an internal IPv6 network with only the IPv4 gateway isolated, asks a
  container directly whether the IPv6 gateway answers, and holds the check to that only where it answers: an answering
  gateway must stop the run (corrected 13 October 2026, backlog 0410: where it did not answer, the test only printed).
  It also made a network with the options the runner asks for first and held the check to passing it, without calling
  the runner's own code. Each says which branch it took on a daemon that cannot make such networks.

On Docker Desktop and Colima as installed, IPv6 is off, so nothing changes there. The decision, an internal network
whose gateway the app cannot reach, checked before the app starts, is unchanged; it now covers the gateways of both
address families, though not the bridge's IPv6 link-local address, which no gateway list names (corrected 13 October
2026; closed by the entry below).

## Later, 13 October 2026: on a plain internal network, an unanswered knock is not a fence

Backlog 0301, from the deep review of 12 October 2026. When Docker refuses every way of making the network without a
gateway address (a daemon older than the `gateway_mode` and `inhibit_ipv4` options), the run fell back to `--internal`
alone, whose bridge keeps its address on this computer, and the gateway check decided. A knock on port 9 that timed out
read as the fence holding. Behind a host firewall that drops what it does not allow instead of refusing it (ufw or
nftables letting only SSH in from the bridge), the knock times out while SSH stays open to the app. On that branch a
knock that goes unanswered is now not taken for a fence: the check cannot tell it from such a firewall, so the run is
refused, saying that the network was made with `--internal` alone and that Docker 28 or later makes it with no gateway
address, which the check can trust. A network made without a gateway address is judged as before, and an answer of any
kind still stops the run on either. Held by `on_a_plain_internal_network_an_unanswered_knock_is_not_a_fence` in
`crates/sv-run/src/docker.rs`, and by `crates/sv-run/tests/fence.rs` where Docker is there.

(Corrected 13 October 2026, backlog 0414. "Plain" was decided by whether Docker refused every way, not by what it
built, so a daemon that took an option without honoring it was judged as not plain; `tests/fence.rs` no longer told a
gateway that answered from one that was silent; and Docker 27 with `inhibit_ipv4` also avoids the plain branch. The
entry below says what holds now.)

## Later, 13 October 2026: no IPv6 on the fenced network at all (backlog 0410)

The separate security review of 0300 (#1725) found the IPv6 fence sound, with gaps. The bridge's IPv6 link-local
address (`fe80::`) is on no gateway list, so it was never knocked on, and an app on a network with IPv6 could find the
host there. On Docker 27, which can give new networks IPv6 by default but has no gateway modes, every run with that
default on was refused without saying how to fix it. `sv` needs no IPv6, so now:

- **None is asked for.** The network is made with `--ipv6=false` beside `--internal`, by one function,
  `sv_run::docker::network_create_args`, which the runner and a Docker test both use.
- **None is allowed.** The knocking container lists its own addresses of every family (`ip -o addr`). Any IPv6
  address but loopback, link-local included, stops the run, since a daemon whose default gives networks IPv6 may not
  honor the request. The refusal names the address and says how to turn that default off: remove
  `com.docker.network.enable_ipv6` from `default-network-opts` in Docker's daemon.json, and restart Docker. A list
  that cannot be read stops the run too.
- **Every knock reports.** The verdict counts one report for each address knocked on (a knock, or the container's
  own address), so output cut short cannot read a missing knock as the fence holding.
- **The options are held.** A unit test holds the first entry of the option list to both isolated gateway modes, and
  every network command to `--internal --ipv6=false`. Each guard above was broken by hand and its test went red.
- **The Docker tests say more.** Where the IPv6 gateway does not answer, the test now requires the run to be refused
  for having IPv6, and the direct knock uses the pinned probe image. A network with IPv6 and both gateways isolated is
  now refused, and a new test makes the runner's own first network and requires the check to pass it.

What is still not checked: whether a given daemon honors `--ipv6=false` (the check refuses the run where it does not),
and which branch CI's Docker takes, which each Docker test prints. The decision, an internal network whose gateway
the app cannot reach, checked before the app starts, is unchanged; it now holds by leaving IPv6 out.

## Later, 13 October 2026: plain is read from what Docker built, and a plain network never passes (backlog 0414)

The separate security review of 0301 (#1739) found the rule sound where it applied, with gaps. **The owner's word,
13 October 2026:** keep the refusal on old Docker: a plain `--internal` network whose knock gets no answer refuses the
run. Now:

- **Plain is what Docker built.** A network is plain when Docker took none of the ways of leaving out a gateway, and also
  when, asked for one, it still names a gateway address for the network, of either family: a daemon that accepts an
  option it does not know and ignores it builds a plain network all the same (`plain_reason` in
  `crates/sv-run/src/docker.rs`, tested on its own). The refusal says which.
- **A plain network never passes.** An answer stops the run as reached; silence, or every address being the knocking
  container's own, stops it as plain. The refusal names both ways a Docker can make the network the check trusts:
  `gateway_mode_ipv4=isolated` (Docker 28 and later) or `inhibit_ipv4` before it.
- **The positive control tells reached from silent again.** `tests/fence.rs` judges the `--internal`-alone network as
  if it had been asked for without a gateway, and requires the refusal to be that the gateway answered; it then judges
  it as plain and requires a refusal, printing which.
- **The runner's own way is tested.** Making the network is one method, `make_fenced_network`, which the run and a
  Docker test both call; the test says which branch it took and requires a network made without a gateway to pass and
  a plain one never to.

What is still not checked: a daemon that ignores the option and names no gateway either (the check then judges by the
knock alone, as for a network made without one), and which branch a given daemon takes beyond the one CI's Docker
prints.

## Later, 14 October 2026: link-local IPv6 alone on a Docker before 26.0.2 (backlog 0450)

The refusal for any IPv6 on the fenced network stands. Its advice, to remove `com.docker.network.enable_ipv6` from
daemon.json, cannot be followed on a Docker before 26.0.2. That Docker leaves IPv6 on in containers of networks made
without it (CVE-2024-32473; Docker's advisory and the 26.0 release notes say 26.0.2 switched it off), so every
container shows a link-local `fe80::` address whatever daemon.json says. When every IPv6 address the knocking container
lists is link-local, `sv` now asks Docker its server version (`docker version --format '{{.Server.Version}}'`, the
local daemon only), and below 26.0.2 the refusal names that version and says to update to 26.0.2 or later. A version
that cannot be read, a newer Docker, or any address that is not link-local keeps the daemon.json advice. Only the words
change, and only on that path: nothing more is run unless link-local addresses alone are seen. What Docker did before
26.0.0 is not settled by those pages; moving to 26.0.2 or later is right either way.

## Later, 14 October 2026: one `docker exec` carries a run's single requests (backlog 0341)

Every request still goes in from inside the fence, from the sidecar, through the same `nc -e` exchange. What changed is
how many processes carry them. Each single request used to start a `docker exec` of its own, which the review of 12
October 2026 estimated at 100 to 300 milliseconds before the app is asked anything, and a signed-in run sends a few
hundred. One `docker exec -i
<sidecar> sh` is now kept open for the run (`crates/sv-run/src/exec_session.rs`). Its shell reads each request as two
lines, the host and port, then the request in base64. It writes the request to a file in the sidecar's memory, as
before, and after each answer prints a line with a marker made fresh for the session, which the app cannot know, and
the exchange's exit code.

Before any real request, a check exchange hands bytes of every value through the framing and must get them back
unchanged. If that check fails, or the session cannot start, a request goes one exec each, as before. The same
happens to every request after the session breaks down, so a sidecar that has gone is still told from a silent app
(ADR-025). A request already sent when its session broke down is not sent again, since it may have changed something,
and it reads as unanswered. The session ends before the sidecar is removed. Requests sent together or in turn
(`probe_together`, `probe_in_turn`) were already one exec per batch and are unchanged. Not yet measured against a real
report's `request_timings`. The test with real Docker holds the count: twelve requests, one session, twelve answers,
each its own.

## Later, 16 October 2026: `docker.rs` split along its seams (backlog 0324)

Nothing this record decides changed; where its code lives did. The fenced network, the knock on its gateway, and
what the knock's answers mean are now `crates/sv-run/src/docker/fence.rs`, and the scripts the sidecar runs to send
requests and read answers are `crates/sv-run/src/docker/probes.rs`; both are named in the Governs list above.
`docker.rs` keeps the run itself, the containers' arguments, and the teardown, and its tests are in files of their
own under `crates/sv-run/src/docker/`. `network_create_args` is still public at `sv_run::docker::network_create_args`.

The rest followed in the next part of the split: what every container is given, its hardening and limits and each
one's arguments, is `crates/sv-run/src/docker/containers.rs`; starting the helpers beside the app is
`crates/sv-run/src/docker/helpers.rs`; and the methods that make the fenced network and check its gateway joined the
rest of the fence in `crates/sv-run/src/docker/fence.rs`. `read_only_bind` is still public at
`sv_run::docker::read_only_bind`. `docker.rs` keeps the run itself, waiting for the app, the teardown, and the seed.
