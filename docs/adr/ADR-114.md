# ADR-114: The copy `sv` runs keeps the app's limit on wrong passwords; only a limit on every sign-in is raised for it

**Status:** accepted, 14 October 2026, in the pull request that builds it (backlog 0383). The decision is the owner's,
asked through the coordination board's waiting line while the owner was away and answered that day as the session
recommended: options A and C together.

**Governs:** `crates/sv-manifest/src/spec.rs::STARTER_MANIFEST`, whose notes on the test users say what to do about
a limit on sign-in attempts, and `crates/sv-check/src/signed_in/mod.rs`, whose note when a limit refused the run's
own sign-in says it again, `crates/sv-run/src/start_settings.rs`. A pull request that changes what either tells the AI coding tool about a sign-in limit
changes this record too, or says in its description why it does not (`docs/adr/README.md`).

## Context

`sv` signs in up to 60 times in one run, all from one address (`SIGN_INS_IN_A_RUN`). ADR-028 had the spec say so,
and ask that the copy `sv` runs allow that many, "for example, through a setting only the test copy is started with",
keeping the real limit everywhere else. In the second loop trial (backlog 0257), twelve of the 90 builds scored did
that by raising the limit on wrong passwords itself, to 60, 100, or 1,000, in their `start` command. The guessing check
then sends `failed-sign-ins` plus two wrong passwords and finds nothing stopping them, so it reports "Wrong passwords
can be tried without limit". Seven of the nine such findings in the trial came from this, each about a limit the
shipped app keeps.

Three ways to settle it were put to the owner: (A) change the advice, so that the copy keeps stopping wrong passwords
at the declared number and only a limit that counts every sign-in is raised; (B) have `sv` spread its sign-ins across
its accounts; (C) have the wrong-password finding say when the start command sets something that looks like a sign-in
limit.

## Decision

A and C together. The spec now says that the copy `sv` runs must keep stopping wrong passwords at the number
`failed-sign-ins` declares, as the real app does, and must never have that limit raised. Only if the app also has a
limit that counts every sign-in, right passwords too (for example, by address), may the copy allow 60 of those,
through a setting only the test copy is started with, with the real limit kept everywhere else. The report's note when
a limit refused `sv`'s own sign-in says the same.

C was already built by backlog 0386 (`crates/sv-run/src/start_settings.rs`, `sign_in_limit_note`, and its use in
`crates/sv-cli/src/assemble.rs`). The wrong-password finding names any setting in the start command whose name looks
like a sign-in limit, so a finding about a loosened copy says so.

## Alternatives considered

- **B, spreading `sv`'s sign-ins across accounts.** Not chosen by the owner. The session's own reasons for not
  recommending it: it changes what the run does, needs more test accounts from every seed, and a per-address limit on
  every sign-in would still be in the way.
- **Saying nothing about limits.** Not taken: an app with a per-address limit on every sign-in locks `sv` out, and the
  checks that needed a session go unassessed. The spec should say how to avoid that without weakening the check.

## Consequences

- A builder following the spec no longer raises the wrong-password limit for the test copy, so the guessing check
  reads the limit the app ships with.
- An app whose only limit is on wrong passwords needs nothing raised. `sv`'s right-password sign-ins do not count
  against it, unless the app counts every attempt.
- Not measured yet: whether builds that follow the new advice stop raising the limit. The next loop trial should
  count them.

## Later, 15 October 2026: a setting loosened for the run earns no credit (backlog 0564)

The owner's go of 14 October on backlog 0564. When the start command in stackvet.toml sets something that loosens the
copy `sv` runs (what `sv_run::weakening_named_in` already warns of: `insecure`, a security word with `disable`,
`skip`, `bypass`, or `no`, or one set to `0`, `false`, `no`, or `off`), the run's credits for the rules that setting
bears on are taken out, and each is said as a gap naming the setting: "the copy `sv` ran had X set in its start
command, so what the run saw here is not what the app does as it is shipped". A finding under those rules says it is
about that copy. Which rules a setting bears on is read from the words of its name (`sv_run::start_settings::loosened`):
cookies, CSRF, HSTS and HTTPS, CSP, two-factor codes, rate limits, and authentication. A setting that names none of
them is warned about as before. A value is shown only when it is a short word such as `0` or `false`, never one that
could be a key.

A setting that only looks like a sign-in limit (`CLUB_LOGIN_ATTEMPTS=100`) withholds nothing: raising a limit on every
sign-in for the run, with wrong passwords still stopped at the stated number, is what this record asks of the copy, and
a V6.3.1 credit then shows the copy stopping them. Its findings keep the note of 0386.

Read only from the start command, as the warning is: the environment and settings files 0564 also names are not read
yet. And a note for the owner: a loosened copy mostly makes a run look worse, not better, so a credit it earns is
usually true of the stricter app too; the credit is withheld anyway, as decided, because a copy that differs on the
very thing a rule asks about is not the app the report is about.

## Later, 15 October 2026: the environment file the start command reads is judged too (backlog 0605)

**Status:** accepted, 15 October 2026, in the pull request that builds it. The owner chose option (b) on 15 October:
read only what the start command itself names, with that file's format read first, say in the report that other
settings files are not read, and add no manifest key. Option (a), new keys under `[stack.run]`, waits until a real
app's loosening hides in a file the start command does not name.

- **Which files.** The file after `--env-file` (`node --env-file=.env`, `uvicorn --env-file .env`), and the file a
  shell `source`s or `.`s where a command starts (`sv_run::start_settings::env_files_named_in`). Each is read from the
  app's folder, which is where the start command runs (`/app`). A path under `/app/` is that folder. A path outside
  it, a link out of it, a missing file, or a file over 1 MB is not read.
- **Its format first.** Each line must be blank, a `#` comment, or `NAME=value`, with an optional `export`
  (`env_file_settings`). That is the form a shell, Docker, and Node all read. A file with any other line is not judged
  at all, and the report names the line by number, never its text.
- **Judged as the start command is.** Each setting goes through `start_settings::loosened`. A credit it bears on is
  taken out, and the gap names the setting and the file. Unlike the start command, the file may be the one the app
  ships with, so the gap says that if it is, the setting is loosened there too. A value is shown only when it is a
  short word (`0`, `false`); a value with a space in it is read as the name alone. No other text of the file is ever
  shown, since an environment file is where keys live.
- **What the report says.** The run note always says which settings were read for this: the start command's, and
  the environment files it reads, by name. It also says that any other settings file the app reads is not read, so a
  setting loosened there is not seen. Each file named and not read is listed, with why.
- **How it is held:** `crates/sv-run/src/env_file_tests.rs` and `crates/sv-cli/src/assemble_env_file_tests.rs`.
  `loosened_for_the_copy` is the one function the run calls for both sources. No test runs the app end to end for
  this, as none did for the start command's half.
