# ADR-084: More in the build-loop record: each call's outcome, what was handed over, and what changed between checks

**Status:** accepted, 10 October 2026: every decision is built (see the three "Later, 10 October 2026" entries below,
which say where each build differs from the plan). Proposed 9 October 2026, with the backlog claim (0226, part 3, item D). The owner's decision, the same
day: "yes to A, C, and D". It extends ADR-076, whose lines held the time, the tool's name, and a check's counts. Each
part is accepted in the pull request that builds it. Written by session paper-facts.

**Governs:** `crates/sv-cli/src/build_loop.rs`, which writes the record and reads it back. A pull request that changes
what it says about the record changes this record too, or says in its description why it does not
(`docs/adr/README.md`).

## Context

The observability review of 9 October 2026 (backlog 0226) found that the build-loop record cannot tell a check that
failed or timed out from a call that only asked for text, writes nothing for a call refused before it ran or when the
record could not be written, leaves no trace when the AI coding tool turns it off in `stackvet.toml`, does not say
which AI tool or which `sv` was used, does not record the prompts and report files handed over, and keeps only the
first and last checks' counts, so a total that drops may be a fix or a finding set aside.

## Decision

Each line of the record may also carry, and the report's paragraph says what they show:

1. **The call's outcome**: ok, timed out, crashed, or refused; never the error's text, which can quote the app.
2. **A line when the record is turned off**, so a gap is seen as one, and the report saying so when the record could
   not be written.
3. **Names `sv` itself defines** that the call asked for: a section, a feature, a question id. Never an argument the
   AI tool wrote, a path, or finding text.
4. **Which tools were used**: the AI tool's name and version from `initialize`, cut short, and `sv`'s version.
5. **What was handed over**: each prompt fetched, each report file read, and that the instructions were given at
   `initialize`.
6. **At each check, the findings' fingerprints** (hashes, not text), so the report can say how many were fixed, set
   aside, and new between the first check and the last.

The record stays in the report folder, capped, written link-safely, and credits nothing (ADR-076). A forged or edited
line is still possible for anything that can write the folder, and the report still says so; a copy outside the folder
that cannot be quietly rewritten is a separate decision (review part 3, item J).

## Alternatives considered

- **Arguments in full**: says the most, and carries the AI tool's words, paths, and the app's text into the record.
- **Counts only** (ADR-076 as built): the loop's struggle and its fixes stay invisible.

## Consequences

Lines grow from tens of bytes to a few hundred at a check (the fingerprints); the 4 MB cap still holds tens of
thousands of calls. The report can say which AI tool built the app, whether it read the report and rules it was given,
and how many findings it fixed rather than set aside.

## Later, 10 October 2026: decisions 1, 2, and 4 built

Built by session securevibe-e2 (backlog 0231). Each line of the record now carries:

- **`outcome`**: `ok`, `failed`, `timed-out` (the check ran past its time limit), `crashed` (the check stopped on a
  fault in `sv`), or `refused` (a tool `sv` does not have, written down as `unknown`, never by the name the AI tool
  sent). Never the error's words. A line naming any other outcome is one `sv` did not write, and is counted as
  unreadable.
- **`client`**: the AI coding tool as it named itself in `initialize` (`clientInfo`), kept to letters, digits,
  spaces, and `.-_+/()`, 40 characters a part (`build_loop::client_name`).
- **`sv`**: the version that answered.

When `stackvet.toml` turns the record off, the server writes one line holding only the time and `"off": true`, once
until a call is written down again, so a gap is seen as one; no call is written while it is off. A call that cannot
be written into the record is counted by the process that tried, and the next report that process writes says how
many (`unwritten`); a report written by another process, `sv report` at a terminal, cannot know of them and says
nothing of them. The report's paragraph says how many calls failed, ran out of time, stopped on a fault, or were
refused; which AI tool named itself and which `sv` answered; how many times the record was turned off; and how many
calls could not be written. Each new field of the report's `build_loop` is left out when it is empty, so a report
written before reads and seals the same.

Where the build differs from the plan: decision 1's "refused" covers only a tool `sv` does not have. A call whose
arguments are not an object names no app (its folder is in the arguments), so there is no record to write it in; it
is answered as before and not written down.

## Later, 10 October 2026: decision 6 built

Built by session securevibe-e2 (backlog 0231). A line written for a call that checked the app now keeps that check's
findings' fingerprints (`fingerprints`: sorted, each once, at most 1,000, with `fingerprints_cut` when there were
more), never a finding's words; a list holding anything but letters, digits, and hyphens, or longer than the limit, is a
line `sv` did not write, and is counted as unreadable. When a report is written, the first check's fingerprints are set
against the last's: those gone, those of them the report about to be written holds as a person's false alarms (set
aside in `[[finding-review]]`, sealed), and those new. The report's `build_loop.findings_moved` keeps the three counts
and the paragraph says them. Nothing is said with one check, or when either check's line did not keep every
fingerprint, or was written before this.

Where the build differs from the plan: the plan said "fixed". A finding no longer found may have been fixed, or the
check may no longer reach it (a file moved out of the scan, a rule changed), and the record cannot tell which, so the
report says "no longer found (fixed, or no longer reached by the check: the record cannot tell which)". Accepted risks
stay among the findings, so they are neither gone nor set aside.

## Later, 10 October 2026: decisions 3 and 5 built

Built by session securevibe-e2 (backlog 0231). A line now also keeps:

- **`asked`**: the names `sv` itself defines that the call asked about. A value is kept only when the tool's own
  published schema lists it as allowed for that property (a feature for `stackvet_before`, a topic for
  `stackvet_guidance`), or when it is an `id` or `requirement` that names a requirement in the loaded frameworks. Any
  other value the AI tool sent is left out, so its own words never reach the record.
- **`handed`**: what `sv` handed over: `instructions` (given at `initialize`), `prompt:<id>` (a prompt fetched with
  `prompts/get`), and `report:<file>` (a report file read with `resources/read`, by the report's own file names).

A line holding anything else in either list, or more than 20 in one, is one `sv` did not write. The report's paragraph
says what the AI tool asked about (the first twelve by name, the rest counted) and what `sv` gave it.

Where the build differs from the plan: `initialize` and `prompts/get` name no app, so what they hand over is kept by
the server and carried on the next line written for an app; a session that connects, fetches a prompt, and never calls
a tool for an app leaves no trace of it. A report file read is written down at once, on a line of its own (tool
`resources/read`), for the app the report folder sits in, when that folder holds a `stackvet.toml`; a report written
with `--out` elsewhere is carried on the next line instead. Only what happened is said: a record from before this
cannot show what was not handed over, so the report never says the instructions were not given.

## Later, 11 October 2026: the record holds the size of each prompt and report file (backlog 0227)

The owner said yes to sizes for the observability dashboard's build-loop section (ADR-086). Each line the build loop
records for a prompt or a report file now also says that file's size in bytes, as `size` next to its name. The name is
still the only thing the dashboard shows of the contents, and nothing else is read or kept. Lines written before this
have no size and are shown as names only; the dashboard says so, rather than showing a size of zero. The chain of
hashes (above) covers a line as written, so older lines are unchanged and the chain still checks.

## Later, 12 October 2026 (the third weekly review)

The 11 October entry says each line carries `size` beside its name; the code writes `sizes`, a map (`handed_sizes`, `crates/sv-cli/src/build_loop.rs`). The index said "(proposed)" for this accepted record and is corrected.

## Later, 14 October 2026: where each finding was, so a report can name the ones that went on an unchanged line (backlog 0401)

The owner's instruction of 14 October 2026: "StackVet comparing two checks and naming the findings that went while
their lines did the same thing, from the build-loop record's fingerprints." Decision 6 counts the findings that went
between the first check and the last; a count cannot say which, since the record keeps fingerprints and a fingerprint
cannot be turned back into a line. So each check line now also holds `placed`: for each v2 fingerprint it lists, the
finding's rule (`ast.open-redirect`, `bandit.B104`: `sv`'s own names, never the app's words) and a hash of its file's
path (`file_key`, sixteen hex characters of SHA-256; the file's name is not kept). A line holding anything else there,
or a fingerprint it does not list, is not a line `sv` writes and is counted as unreadable.

When the report is written, each finding in the first check, gone by the last, and not set aside as a false alarm is
looked for again, at most 50 (`look_again`, `crates/sv-cli/src/build_loop.rs`): the file is found by its hash among the
app's files, and its fingerprint recomputed over each of today's lines, as written and with a comment that tells a
scanner to look away taken off (`still_reads`, `crates/sv-check/src/review.rs`). One whose line still reads as it did
went some other way than a fix, and the report names it at the top with its rule, file, and line, and tells the person
to ask whoever changed it (`went_same_line`). One that `sv` still finds on that line, under the new fingerprint a
comment there gives it, did not go, and is not named or counted as looked for. A line rewritten to do the same thing
(`"0.0.0.0"` to `""`) is not caught, and the sentence says so. It is a line in the report: it credits nothing, fails
nothing, and moves no count. Records written before this have no `placed`, and nothing is looked for.

Held by `crates/sv-cli/src/build_loop/placed_tests.rs`, `crates/sv-check/src/review_still_reads_tests.rs`,
`crates/sv-report/src/went_same_tests.rs`, and, through the server, `crates/sv-cli/src/mcp/build_loop_went_same_tests.rs`.
Each guard was taken out in turn and at least one of them went red: the comment not taken off, the line above not
read, nothing looked for, a false alarm looked for, an unkept fingerprint placed, the line left out of either report,
and a finding found again on its line named as gone.
