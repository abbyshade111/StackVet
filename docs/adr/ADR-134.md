# ADR-134: A seed may print numbered values, and each sign-up takes the next one unused

**Status:** accepted, 23 October 2026, in the pull request that builds it; proposed the same day with the claim for
backlog 0637, at the owner's answer of that day, asked in a session how StackVet should handle an invite-only app whose
codes work once: "Numbered values".

**Governs:** `crates/sv-check/src/signed_in/requests.rs::fill_seed`, `crates/sv-check/src/signed_in/requests.rs::next_sign_up`,
`crates/sv-check/src/signed_in/requests.rs::sign_up_value_note`, `crates/sv-check/src/signed_in/passwords.rs::sign_up_only`,
and their tests (`crates/sv-check/src/signed_in/seed_numbered_tests.rs`). A pull request that changes what a seed may
print or how `{seed:NAME}` is filled changes this record too, or says in its description why it does not
(`docs/adr/README.md`).

## Context

ADR-124 lets a manifest cite a value the seed printed as `{seed:NAME}`, one value per name. `sv report --run` makes
several accounts through the sign-up form, each with that one value. In the owner's Cursor build of 22 October 2026 the
app's invites worked once, so the first sign-up used the seed's invite up and the rest were refused, and six checks did
not run; the report guessed the sign-up needed "a value stackvet.toml does not carry".

## Decision

- **A seed may print numbered values,** `INVITE_1=…`, `INVITE_2=…`, and so on, beside or instead of `INVITE=…`.
- **`{seed:INVITE}` takes the next numbered value not yet used** for each sign-up, in order, and `INVITE` itself when
  there are no numbered ones, as now. A value is used once.
- **When the seed printed too few,** the sign-ups past them go without, and the report says which checks did not run
  for want of a value, and that the seed can print more.
- **When sign-ups after the first are refused with the same value,** the report says the value likely works once, and
  how to print numbered ones, rather than guessing at a missing field.
- The manifest still never holds the values (ADR-124), and nothing is run that was not run before.

## Where the build differs

- **One count for the run:** every sign-up goes through `sign_up_only`, which moves the numbered values on by one
  before it sends; `fill_seed` gives `{seed:NAME}` the value numbered for that sign-up, `NAME` when the seed printed no
  numbered ones, and leaves it as written past the last, so the app refuses it and the refusal is quoted. Anything filled
  before the first sign-up takes the first.
- **The report's words:** where a check could not make its account (the guessing limit's, and the emailed code's), it
  gives only the reason the run's own count shows. When the form cites a value the seed did not print: that it was sent
  as written. With one value and no numbered ones: from the second sign-up on, that it may work once and how to print
  one per account; on the first, that it was sent unused, so working once is not the reason. With numbered values: when
  the run made more sign-ups than there were values, how many of each; when this sign-up had its own, that it did, so
  running out is not the reason. When the form cites none, what it said before. The value itself is never said.
- **The starter manifest** (`sv init`) says how to print numbered values.
- **Held by** `seed_numbered_tests.rs`, which sends three sign-ups through `sign_up_only` and finds each value in
  its own: with the move to the next value taken out, it fails. Each of the report's reasons is held by its own assertion there: with the sentence
  for a first sign-up, a value never printed, or a sign-up that had its own value taken out, the test fails at that
  case's line.
