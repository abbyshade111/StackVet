# ADR-098: `sv review` says which findings it never offers, and each finding in the report names its next step

**Status:** accepted, 11 October 2026, at the owner's word ("1. yes 2. yes as you recommend for both"), in the pull
request that builds it. Proposed the same day in backlog 0253, from the Cursor build, where `sv review` said nothing was
waiting while the report still listed a finding needing attention, and the AI coding tool first advised the owner wrongly.

**Governs:** `crates/sv-cli/src/review.rs` (what sv review says when nothing is waiting), and `crates/sv-report/src/lib.rs`
with `crates/sv-report/src/markdown.rs` and `crates/sv-report/src/html.rs` (the next step beside each finding). A pull
request that changes these changes this record too, or says in its description why it does not (`docs/adr/README.md`).

## Context

`sv review` goes through the entries in `stackvet.toml` that are not yet sealed. A finding with no entry is never offered,
so "nothing is waiting" can stand beside a report that lists findings needing attention. Nothing in either said what to
do with such a finding, and the tool's first advice was to record a real finding as a false alarm.

## Decision

- **When nothing is waiting, `sv review` says what it does not offer.** One sentence: a finding with no entry is never
  offered there; a real one is fixed in the code and checked again, and a false alarm needs a `[[finding-review]]` entry
  first, which the person then confirms there. It then says how many findings that count the last report in the default
  report folder lists, read from its `report.json`, or that no report was read. It reads the file only to count.
- **Each finding in `security.md` and the report page names its next step:** fix it and check again, or, if it is a false
  alarm, give it an entry naming its rule, file and fingerprint and confirm it with `sv review`; until then it counts. An
  accepted risk, which a person has answered already, has no such line.
- **Neither offers a way to set a finding aside.** Only an entry a person confirms with `sv review` does that, as before
  (ADR-022 and the seal).

## Alternatives considered

- **Let `sv review` offer every finding in the last report.** It would let a person set aside a finding without the entry
  that names it, and a report folder is not where decisions are kept.
- **Say nothing, and rely on the guide.** The guide says it (section 5), and the owner and the tool still read the two
  outputs as contradicting each other.

## Consequences

- Every finding in the reports carries one more line; the reports are a little longer.
- `sv review` reads `report.json` from the default report folder when nothing is waiting. A report written elsewhere with
  `--out` is not counted, and the message says which folder it read.

## Later, 12 October 2026 (the third weekly review)

Low-severity findings are shown as one grouped line per rule in `security.md` and the report page (ADR-095), and that line names no next step; the full entries in `low-findings.md` do. "Each finding names its next step" above holds for findings that are not grouped.

## Later, 12 October 2026: a note worth knowing has no next step

An `Info` finding in the app's own code is a note worth knowing, shown apart from the things to fix (ADR-110, Later),
and asks for nothing, so `next_step` gives it none: it is no longer told "Fix it in the code". Every other finding
names its next step as before.
