# ADR-148: The test provider mints access tokens for another person and with less scope, and the app's API is asked about both

**Status:** accepted, 24 October 2026, in the two pull requests that build it: V10.3.3 first, then V10.3.2. Proposed
the same day with the claim for backlog 0625's fifth part.

**Governs:** the test sign-in provider's access-token address (`crates/sv-run/assets/oidc-provider.mjs`, and its
protocol in `crates/sv-check/src/stand_in.rs`), the access-token probes beside V10.3.1's
(`crates/sv-check/src/oidc/tokens.rs`), and their tests (`crates/sv-check/src/oidc/subject_tests.rs`, and the
provider's own in `crates/sv-run/tests/oidc_provider.rs`), `crates/sv-check/src/oidc/scope_tests.rs` for V10.3.2, and the
entry that names the route (`crates/sv-manifest/src/lib.rs::ScopedRoute`, with its line in the starter,
`crates/sv-manifest/src/spec.rs`). A pull request that changes what the provider mints, what is
sent to the app, or what an answer concludes, changes this record too, or says in its description why it does not
(`docs/adr/README.md`).

## Context

V10.3.2 (level 2) asks that an API deciding on an OAuth access token decides on what the token grants: its subject and
its scope. V10.3.3 (level 2) asks that it knows the person by claims that cannot be reassigned, the issuer and subject,
not by an email address another person can hold. `sv` already asks the app, through its own test provider, whether an
access token for another service opens a private page (V10.3.1, ADR-127), and asks that only once one issued to this
app does: an app that takes only cookies is not a resource server for these tokens and is not judged. The provider's
access-token address mints a token for this app or for another service, always for the one test person, with the full
scope.

## Decision

- **The provider mints two more kinds of access token**, both for this app, each wrong in one way: `who=other-person`,
  a different subject who has the first person's email address (as the `other-person` mode does for ID tokens), and
  `scope=…`, a narrower scope than the full one. The provider runs inside the fence, as now; nothing new connects out.
- **V10.3.3, asked when V10.3.1's own token opens the private page and stackvet.toml says how to save something
  (`create`) and where it shows (`shows`), as V10.5.2's question already uses:** the first person saves a marker; a
  bearer token for the other person who shares the email is sent to `shows`. The marker coming back is a finding: the
  API decided whose data it was by email. The first person's own token showing it, and the other's not, is credited in
  part (one page, one other person).
- **V10.3.2, asked only where stackvet.toml names a route and the scope it needs** (a new entry under
  `[stack.run.oidc]`, built in the second pull request): a token without that scope is sent to the route. Taken is a
  finding; refused, with the full-scope token taken just before and after, is credited in part. With no such entry,
  V10.3.2 is not asked, and the report says how to name one.
- **The `resource-server` condition the design proposed is not part of this:** whether V10.3 applies to an app that
  only signs people in is an applicability change of its own, with a record of its own when it is built. These probes
  keep V10.3.1's gate, so a cookie-only app is still not judged.

## Alternatives considered

- **Judge V10.3.3 from the code** (an account looked up by the token's `email`). The code rule for V10.5.2 does this for
  sign-ins; an API can decide in more places than one file shows, and the answer from the running app is direct.
- **Ask V10.3.2 with a guessed route.** Rejected: which route needs which scope is the app's own, and a guess that is
  wrong would show nothing either way.

## Consequences

- An API that knows people by their email address, or ignores a token's scope, is told so from what it did.
- A run with `[stack.run.oidc]` and `create` sends a few more requests to the app.

## Where the build differs

V10.3.3, built 24 October 2026 (the first pull request). The check is "probe.oidc-access-token-user-keyed-on-email",
run right after V10.3.1's. One thing the decision did not say: every access token the provider mints now carries the
test person's `email` claim, as many providers' do. Without it, an API that knows people by email would find no
address in the token, and the other person's token would be refused for a reason that shows nothing about V10.3.3. The
V10.3.1 tokens carry it too, which changes nothing they are asked. The provider's contract test runs the script for
real and checks each token's subject, audience, and email.

V10.3.2, built 24 October 2026 (the second pull request). The check is "probe.oidc-access-token-scope-not-checked",
run after V10.3.3's. The entry is `scoped = { path = "…", scope = "…" }` under `[stack.run.oidc]`, read with `GET`, and
the starter shows it as a commented line. The provider's access-token address takes `scope=…` and grants that scope in
place of the full one. Two tokens are minted for this app, one with the full scope and the named one, one with the full
scope alone; the credit is in part, since one route and one scope are asked, and `sub` and `authorization_details`,
which V10.3.2 also names, are not (the subject is V10.3.3's question).
