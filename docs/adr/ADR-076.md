# ADR-076: The build loop written down as it happens, and the report saying what it shows

**Status:** accepted, 9 October 2026, in the pull request that builds it; proposed the same day with the backlog claim
(0006, finding 22(d)). Where the build differs from the plan is at the end. The owner's decision, the same day: "observability
is really important, so let's go with the first option". Written by session securevibe-e9.

**Governs:** `crates/sv-cli/src/build_loop.rs`, which writes the record and reads it back, and its tests
(`crates/sv-cli/src/build_loop/tests.rs`, `crates/sv-cli/src/mcp/build_loop_tests.rs`). The server writes each call
down in `crates/sv-cli/src/mcp/mod.rs` (ADR-066's), and a report folder's report reads the record in
`crates/sv-cli/src/report_folder.rs`; neither is listed, since each is changed often for other reasons, `crates/sv-cli/src/build_loop/*_tests.rs`. A pull request that changes what these say about the record changes this record too, or says in its
description why it does not (`docs/adr/README.md`).

## Context

`sv`'s claim to a person who is not technical is the build loop: the AI coding tool checks the app through `sv` while
it builds, fixes what is found, and checks again. Nothing records that this happened. A report written once, at the
end, reads the same whether the tool checked forty times along the way or never (`docs/GAP-ANALYSIS.md`, 4.6). The
gap analysis offered two answers: record the MCP calls made while building, or have the report say that nothing
shows the loop happened. The owner chose the first.

## Decision

- **What is written.** The MCP server appends one line for each call to a tool that looks at the app
  (`stackvet_check`, `stackvet_write_report`, `stackvet_preflight`, and the others that read the folder), with the
  time, the tool's name, and what came back in counts only: findings, requirements credited, and not assessed. No
  argument, no code, no finding's text, no path outside the app. The tools that only hand back text (`stackvet_spec`,
  `stackvet_prompts`, `stackvet_guidance`, `stackvet_explain`) are written down too, by name and time, since asking
  for the rules before writing code is part of the loop.
- **Where.** Beside the reports, in the app's report folder (`stackvet-report/` by default), in a file of its own
  that writing a report keeps rather than replaces. The person's folder already holds what `sv` writes about the
  app; nothing is kept elsewhere, and nothing leaves the computer.
- **On by default.** The record is the point of the loop's evidence, and it holds no more than the reports already
  do. It can be turned off in `stackvet.toml`, and the report then says it was off.
- **What the report says.** A section, "How this app was built with `sv`": how many checks ran through the AI tool,
  over what span of time, and how the counts moved from the first to the last, or, plainly, that nothing shows `sv`
  was used while the app was built. It is evidence about the process, not about the app: nothing in it credits a
  requirement or changes a grade.
- **What it cannot show, said where it is shown.** The AI coding tool can write to the same folder, so the record is
  what `sv` wrote unless something changed it since. The report's seal covers the record as it stood when the report
  was written, so a later change is caught; an earlier one is not, and the section says so.

## Alternatives considered

- **The report saying only that nothing shows the loop happened.** Cheaper, and honest, but it leaves the person
  with nothing to look at; the owner chose the record.
- **Keeping the record outside the app's folder** (as the dashboard's history is, ADR-057). Out of the AI tool's
  plain reach, but not out of its reach on the same computer, and a record kept apart from the app is lost when the
  folder moves to another computer or is checked out in CI. Kept beside the reports, it travels with them and is
  sealed with them.
- **Recording each call's arguments.** More to see, but the arguments carry paths and code; counts are enough to
  show the loop and keep nothing new about the app.

## Consequences

- One more file in the report folder, growing by a line a call; a long build adds a few hundred lines.
- The weekly review and the dashboard can read the same record later; neither is built by this.

## Where the build differs from the plan

- **The record is not sealed as a file.** Every call adds a line, so a sealed record would break the report folder's
  seal between reports, and the folder would stop being offered as `sv`'s. Instead the report carries what it read
  from the record (`build_loop` in `report.json`: the calls, the checks, the first and last time, and the counts at
  each end), and that is sealed with the report. A change to those numbers after the report is caught; a change to
  the record before the report is written is not, and the report says so.
- **Where, exactly:** `build-loop.jsonl` in the app's default report folder (`stackvet-report/`), whichever folder a
  report is written to, so one app keeps one record. It is one of the names a report folder may hold, so a report is
  still written beside it and the folder is still offered as `sv`'s. The folder is made one level at a time, never
  through a link, and the record is opened without following one.
- **Which calls:** every tool call naming a folder that holds a `stackvet.toml`; a call at a folder with none (the
  spec asked for at the root, say) is not this app's and is not written down. A call that ran a check carries its
  counts. A call to write a report is written down after the report has read the record, so a report counts the calls
  before it.
- **The report's words** are one paragraph at the top of each report, beside the baseline's line, rather than a
  section of its own: how many calls and checks, over what span, the counts at the first and the last check, what it
  is not, and what the seal covers. With no record, it says nothing shows `sv` was used and that this is not a
  finding; turned off (`build-loop-record = false` under `[app]`), it says the report cannot tell.
- **Only the server a person starts writes it.** `sv mcp` writes the record; a server made in the tests does not
  unless the test asks, and `SV_BUILD_LOOP_RECORD=off` stops `sv mcp` writing it, for the one test that serves the
  repository's own example apps.
- **A record grows to 4 MB at most** (tens of thousands of calls); past that nothing more is written, and a line that
  cannot be read is counted and said rather than skipped quietly.

**Later, 9 October 2026** (backlog 226, part 1, items 3 and 7): the last point above was not what the build did. A
record holding one byte that is not UTF-8 read as empty, so the report said nothing showed `sv` was used; it is now
read as bytes and decoded a line at a time, and such a line is counted as unreadable like any other. And a record at
its limit said nothing of it, so "the last check" could name one long before the last; the report's `build_loop` now
carries `full`, left out when false so an older report reads the same, and the paragraph says the last check named is
the last one written. The decision stands; this makes the build hold to it.

**Later, 10 October 2026** (ADR-084, backlog 0231): turned off, the record now holds one line saying so, with the time
and nothing else, so a gap in it is seen as one; no call is written while it is off, as before. Each line also says how
the call ended, which AI tool named itself, and which `sv` answered. ADR-084 holds the detail.

## Later, 10 October 2026: the record is chained, so an edit to a line shows (backlog 0239, option 3)

The owner chose option 3 of backlog 0239 on 10 October 2026: rather than a second copy of the record outside the app
folder, each line of the record is chained to the one before it. A line's `chain` is a SHA-256 over the previous line's
chain and this line's own text without its chain. A report says whether the chain holds, the line where it first breaks
if not, and the head: the last chain that checked out, which a report keeps so that two reports can be compared.

What this record does not give: a rewrite of the whole record can recompute every hash and keep a valid chain. The
head is what makes such a rewrite visible across reports, and a report says so. The record stays one file in the app's
report folder, and it still holds only what it held: the chain is integrity metadata, and off lines carry it too.
Tests: `crates/sv-cli/src/build_loop/chain_tests.rs`, and `crates/sv-cli/src/mcp/build_loop_tests.rs` now leaves the chain
out of the keys an off line holds.

## Later, 12 October 2026 (the third weekly review)

What a line holds is more than "counts only": ADR-084 added each call's outcome, the client, the `sv` version, fingerprints, the names asked and handed over, and sizes (10 and 11 October). Read this record's "What is written" with ADR-084. The test files under `build_loop/` and `mcp/` are in the Governs list now.

## Later, 12 October 2026: written only to a plain file (backlog 0282)

The record already refused a link; it now refuses anything else that is not an ordinary file, a named pipe above all.
Opening a pipe to write waits for a reader, and the record is written after every tool call on the server's one thread
for answering, so a pipe made where the record goes stopped the server for good. The call is answered as before; the
line is not written, and the pipe is left as it was. `stackvet_prompts` with a path reads the report under the same
rule, and no more than the 16 MB the server reads of any file.

## Later, 13 October 2026: a chain that holds says nothing of lines cut from the end (backlog 0310)

Each line is chained only to the one before it, so lines cut from the end of the record leave a chain that checks out,
as a rewrite of the whole record does; the report's sentence said a chain that holds vouched for every line, and named
only the rewrite. It now names both, and says how to tell: an earlier report shows the hash its record ended at, and a
record that has only grown since still passes through it. Nothing new is kept to catch it on its own; carrying the last
hash into the sealed report, so the next report could compare without a person, is the stronger fix the item names and
is not built here. Held by `crates/sv-cli/src/build_loop/chain_tail_tests.rs` (the behavior) and
`crates/sv-report/src/build_loop_tail_tests.rs` (the wording).

## Later, 14 October 2026: the record is kept out of the report folder (backlog 0404)

In the owner's trial in Antigravity, the AI coding tool cleared `stackvet-report` before a report ("Clear report
directory"), the record went with it, and the report said nothing showed `sv` was used, after dozens of calls. The
owner's answer of 14 October 2026 (asked through the board's waiting line, answered as the session recommended):

- **Where it is kept.** The record is kept in a hidden folder of its own in the app, `.stackvet/build-loop.jsonl`
  (`sv_scan::ecosystems::build_loop_record_in`). Deleting or replacing the report folder leaves it, and it still
  travels with the app's folder. Each report still carries what it read from it under the report's own seal.
- **A record in the old place.** A record kept in the report folder before then is read where it is, and moved whole
  to the new place when the next line is written, so its chain carries on.
- **Not read as the app's code.** `.stackvet` is one of the folders every walk of the app leaves out (`SKIP_DIRS`).
- **When there is no record but other signs that `sv` was used,** the report says "No record of the build was found;
  it may have been deleted", and names the signs, rather than "Nothing shows that sv was used". The signs are things
  only `sv`'s instructions or tools write: answers in `stackvet.toml` marked `by = "ai-tool"`, `security-notes.md`
  sections with a `Written by:` line, and an earlier report `sv` sealed in the report folder (`build_loop::signs_of_use`,
  carried as `signs_of_use`). None of them is a call to the MCP server, so the report says only that the record may
  have been deleted, and that this is not a finding.
- **Held by `crates/sv-cli/src/build_loop/kept_apart_tests.rs`.** With each of these guards taken out, one of its four
  tests went red, and only that one of the four:
  - `.stackvet` out of `SKIP_DIRS`;
  - the signs not read;
  - the old record not moved.

## Later, 14 October 2026: the record also keeps each finding's rule and a hash of its file (backlog 0401)

Beside its fingerprints, each check line now keeps, for each, the finding's rule and a hash of its file's path, so a
report can name the findings that went while their line still reads as it did. A rule's id is `sv`'s name for a
check, not the app's text, and the file's name is not kept. What and why: ADR-084, "Later, 14 October 2026".

## Later, 15 October 2026: the build prompt keeps `.stackvet/` in git and the report folder out (backlog 0557)

In the three-tool prompt trial of 14 October 2026, Antigravity committed `stackvet-report/` three times and added
`.stackvet/` to `.gitignore` on its own, which keeps this record out of a fresh clone and out of CI, the case this
record keeps the record in the app's folder for (Alternatives considered, above). Asked whether the build prompt should
have the AI tool ignore both, **the owner chose on 15 October 2026 to ignore only the report folder** (option A): prompt
5 now says "Before the first commit, add `stackvet-report/` to `.gitignore`: the report is for me to read, not for the
repository. Keep `.stackvet/` in the repository: it is StackVet's record of the build, which the report reads." `sv`
itself still writes no `.gitignore`; the sentence is the AI tool's instruction. Held by `build_prompt_rules.rs`.
