# ADR-123: A way into the app the code shows that stackvet.toml's list of sign-in pathways does not name is a finding

**Status:** accepted, 15 October 2026, in the pull request that builds it (backlog 0491, its second half). The decision
is the owner's, asked through the coordination board's waiting line and answered the same day: "yes, go with your
recommendation for 0491's second half". Written by session documentation.

**Governs:** `crates/sv-check/src/sign_in_paths.rs::not_listed_findings` and `crates/sv-check/src/sign_in_paths.rs::named_by`,
the stack.auth table in `crates/sv-manifest/src/lib.rs::AuthSection` and its lines in
`crates/sv-manifest/src/spec.rs::STARTER_MANIFEST`, and the call in `crates/sv-cli/src/assemble.rs` that adds the
findings. A pull request that changes what counts as a way in, what an entry names, or what the finding cites, changes
this record too, or says in its description why it does not (`docs/adr/README.md`).

## Context

V6.3.4 (level 2) asks that, "if the application includes multiple authentication pathways, there are no undocumented
pathways and that security controls and authentication strength are enforced consistently". Backlog 0491's first half
(ADR-022, Later, 15 October 2026) lists the ways in the code shows beside the question, as where to look. Nothing compared
that list with what the owner says the ways in are, so a forgotten route, a test login, or an API key check stayed a
line among others for the owner to notice.

## Decision

- **A list, asked and not assumed.** `[stack.auth] pathways` in stackvet.toml names every way to sign in, by the path
  or the name the code uses (`/login`, `/auth/google`, `x-api-key`). It starts commented out in the starter file.
  Left out, nothing is compared, and nothing is said about V6.3.4 that was not said before.
- **What an entry names** (`named_by`): case and spaces aside, a way in whose key it is; for a path, also the paths
  below it (`/auth/google` names `/auth/google/callback`, not `/auth/google-legacy`); for a Passport strategy, also its
  name without `Strategy` (`google` names `GoogleStrategy`). An empty list names nothing: it says there is no way in.
- **A way in the list does not name is a finding,** `config.sign-in-pathway-not-listed`, against V6.3.4, CWE-288,
  medium, low confidence, at the line the way in is on, one per way in. The ways in are the ones the reader of 0491's
  first half finds: routes whose path says sign-in, a token, or a session; a sign-in path compared with the request's
  path; Passport strategies; and API keys read by their header name. Test code is left out.
- **Finding-only.** A list that names every way in found credits nothing: a way in may be one the reader does not find
  (a middleware, a framework it does not read), so a full match is not evidence that none is undocumented. Low
  confidence, because a path named for sign-in may not sign anybody in; the fix says such a one can be set aside in
  `sv review`.

## Alternatives considered

- **Leave it at the list beside the question** (the other choice put to the owner): nothing would ever say a way in
  is missing from the owner's own list, which is what V6.3.4 asks.
- **Credit V6.3.4 when every way in is listed:** the reader finds only the ways in it knows, so a match would claim
  more than was seen.
- **Compare with the security notes' answer to V6.1.3 instead of a list in stackvet.toml:** prose cannot be matched
  against a path without guessing.

## Consequences

- `docs/COVERAGE.md` counts V6.3.4 as supporting only: a check reads the code, and can only ever find it failing.
- `sv check`, which the AI coding tool calls while building, does not compare yet; the reports do.
- Held by `crates/sv-check/src/sign_in_paths/not_listed_tests.rs` (what an entry names and what is left over) and
  `crates/sv-cli/tests/sign_in_paths_listed.rs` (a way in the list does not name makes V6.3.4 need attention; a full
  list, or none, leaves it not verified). Each went red with its part undone.
