# ADR-144: `sv rules` adds a one-line import of `AGENTS.md` to the app's own `CLAUDE.md`, and says which tools still will not see the rules

**Status:** accepted, 24 October 2026, in the pull request that builds backlog 0665. Proposed that day with the claim,
at the owner's word: "please continue with 0665". Where the build differs from the plan is under "As built", below.

**Governs:** which tool files are read and what is planned for each (`crates/sv-check/src/tool_files.rs`), where
sv rules writes and says it (`crates/sv-cli/src/main.rs::cmd_rules`), and the tests that hold both
(`crates/sv-cli/tests/rules_tool_files.rs`). A pull request that changes which of a tool's files sv rules writes
into, what it writes there, or what it tells the person about a tool that will not read the rules, changes this record
too, or says in its description why it does not (`docs/adr/README.md`).

## Context

`sv rules` writes the rules for the AI coding tool into `AGENTS.md`, between `sv`'s markers, and nowhere else. A tool
that does not read `AGENTS.md` never sees them, and nothing tells the person. Each tool's own documentation was read
on 24 October 2026:

| Tool | Reads `AGENTS.md` | Source |
| --- | --- | --- |
| Codex | Yes, one file a folder from the project's root down; an `AGENTS.override.md` in a folder is read instead; 32 KiB in all by default | learn.chatgpt.com, "AGENTS.md" |
| Cursor | Yes, in the project's root and its folders | cursor.com/docs, "Rules" |
| GitHub Copilot | Yes: the cloud agent and code review; in VS Code, `chat.useAgentsMdFile`, on by default | docs.github.com, "Adding repository custom instructions"; code.visualstudio.com, "Custom instructions" |
| Windsurf (Devin Desktop) | Yes; the root file in every message | docs.devin.ai, "AGENTS.md" |
| Claude Code | Only when there is no `CLAUDE.md`, `.claude/CLAUDE.md`, or `CLAUDE.local.md` in the folder or above it (v2.1.277 and later); a `CLAUDE.md` holding `@AGENTS.md` reads it in every version | code.claude.com, "How Claude remembers your project" |
| Aider | No: only with `--read AGENTS.md`, `/read`, or `read:` in `.aider.conf.yml` | aider.chat, "Specifying coding conventions" |
| Cline | Listed as read, but its documentation does not say whether a `.clinerules` file or folder hides it | docs.cline.bot, "Cline Rules" |

The gap that matters most is Claude Code's. An app built with it nearly always has a `CLAUDE.md` (its `/init` writes
one), and then `AGENTS.md` is not read at all.

## Decision

- **Claude Code: a one-line import in the `CLAUDE.md` the app already has.** When the app's folder holds `CLAUDE.md`
  or `.claude/CLAUDE.md`, `sv rules` puts `@AGENTS.md` (`@../AGENTS.md` from `.claude/`) between `sv`'s markers in
  it, the same markers and the same rules as in `AGENTS.md`: everything outside them is the owner's and kept as it
  was, a later run replaces only what is between them, and one marker without the other is refused. Never a second
  copy of the rules (ADR-017, Later, 24 October 2026). A file that already imports `AGENTS.md` outside the markers is
  left alone.
- **No new file for a tool.** `sv rules` never creates a `CLAUDE.md`: with none, Claude Code reads `AGENTS.md` itself.
  It never writes `CLAUDE.local.md` (the person's own, kept out of the repository) or any tool's settings file
  (`.aider.conf.yml`, Cline's, Codex's).
- **Never through a link.** A `CLAUDE.md` that is a link (a documented way to share `AGENTS.md` with Claude Code) is
  not written; `sv rules` says so, and goes on.
- **It says which tools still will not see the rules,** from what is in the folder: Claude Code with only a
  `CLAUDE.local.md`; Codex with an `AGENTS.override.md` beside `AGENTS.md`; Aider whenever an `.aider.conf.yml` is
  there without `AGENTS.md` among its files to read, with the line to add; and Cline, whose documentation does not
  settle it, when a `.clinerules` is there. A note is advice; it writes nothing.
- **What it is worth:** nothing, as evidence, like the rules themselves.

## Consequences

- `sv rules` may change one more file in the app's folder, `CLAUDE.md`, and only one that is already there, by a
  marked block of three lines. The person is told which file, and the block is removed by deleting it.
- Cline's behavior is not verified; it is named as unknown, never as covered.

## As built, 24 October 2026

- **As planned**, with one addition: a `.claude` folder that is itself a link is not written into either, and `sv
  rules` says so, since writing `.claude/CLAUDE.md` through it would change a file somewhere else.
- **A `CLAUDE.md` with broken markers** is left as it was, with the reason printed, and the command still succeeds:
  `AGENTS.md` has been written by then, and failing the whole run would hide that.
- **Size:** the section `sv rules` writes into `AGENTS.md` is about 8 KB, and about 12 KB with the lines for five
  frameworks, well inside Codex's 32 KiB.
- **Broken on purpose,** each red and then green once put back: the link check on `CLAUDE.md` off
  (`a_claude_md_that_is_a_link_is_not_written_through`), the link check on `.claude` off
  (`a_claude_folder_that_is_a_link_is_not_written_into`), the check for an import already there off
  (`no_claude_md_is_created_and_one_that_imports_already_is_left_alone`), and the import line taken out of the section
  (both import tests).

## Later, 24 October 2026: the notes serve `sv doctor` and `stackvet_status` too (backlog 0667)

`tool_files::plan` is also read by `sv doctor`, and so by `stackvet_status` (ADR-066, Later, 24 October 2026), to
say whether the rules are where each tool reads them. Two notes were worded for after a write ("`sv` did not write
into it"); they now say "`sv rules` does not write into it", true from either place. What `sv rules` writes is
unchanged.
