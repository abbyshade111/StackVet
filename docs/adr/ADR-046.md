# ADR-046: Compressed archives sent to the upload, to the limits the owner states

**Status:** accepted, 7 October 2026, in the pull request that builds it; proposed the same day with the backlog
claim. The decisions are the owner's, of 3 October 2026 (the backlog, "Upload names with `../` and compressed bombs",
item 15), recorded here because they had no record.

**Governs:** `crates/sv-check/src/signed_in/archives.rs` (the archives sv makes and the check that sends them), and
`crates/sv-manifest/src/lib.rs` (the upload entry's settings for the limits and the formats). A pull
request that changes what they say about this changes this record too, or says in its description why it does not
(`docs/adr/README.md`).

## Context

V5.2.3 (ASVS, level 2) asks that an app which takes compressed files checks them against a most the files inside may
add up to and a most number of files, before it unpacks them. A small archive can unpack to a great deal: a zip of a
megabyte can hold a gigabyte of zeros. An app that unpacks such a file without counting fills its disk or memory.

Nothing in `securevibe.toml` said whether an app unpacks archives or what its limits are, and `sv` cannot tell either
from outside. The upload probes sent text only, so an archive could not be sent until request bodies became bytes
(DESIGN, "Requests reach the app as input", 3 October 2026).

## Decision

- **The owner states the limits and the formats**, beside `max-bytes` on the `upload` entry: `max-unpacked-bytes`
  (the most an archive may unpack to), `max-files` (the most files one may hold), and `unpacks-archives`, the formats
  the app unpacks (`"zip"`, `"gzip"`). A list rather than a yes or no, so an app that unpacks zip and not gzip is
  never judged on gzip. `sv` sets no limits of its own. Nothing is sent while the formats are not stated, and nothing
  of a format not listed.
- **An ordinary small archive of the same format goes first.** Refused, the app does not take that format at this
  upload, and the format's question is not assessed.
- **Then one archive just over each stated limit:** one that unpacks to a mebibyte more than `max-unpacked-bytes`, for each
  format listed, and for zip one holding one file more than `max-files`. Each unpacks to at most 1 GiB and is itself
  at most 8 MiB (the upload check's own cap) and under `max-bytes`, so a refusal cannot be a size refusal; a limit
  that cannot be tested inside those is not assessed, and the report says why.
- **Refused (a 4xx answer) is credited** when an ordinary GIF sent straight after is accepted, and only when
  `max-bytes` is stated: without it a refusal could be of the archive's own size. Accepted is found either way. **Accepted is a
  finding**, since the owner says the app unpacks the format. **A crash, a 5xx, or no answer is held back** as not
  assessed: a refusal was not seen.
- **Sent after every other upload check**, so an app that unpacks one and falls over takes no other check with it:
  with a sign-in of its own, after the other checks that use A's session and before the password changes.
- **`sv` writes the archives itself**, with no new dependency: a run of zeros compressed by a few lines of code, and
  the zip and gzip wrappers around it, checked in the tests against Python's own `zipfile`, `gzip`, and `zlib`.

## Alternatives considered

- **A yes or no for "unpacks archives".** An app that unpacks zip and not gzip would be found for accepting a gzip it
  never opens.
- **Limits of `sv`'s own** when the owner states none. A figure the owner never chose would make a finding of an app
  whose limit is merely higher.
- **A compression library** (`flate2`, `zip`). A new dependency for one check, where a stream of zeros is a few lines.

## Later, 9 October 2026: a zip whose stated sizes are false

**Status:** accepted, 9 October 2026, in the pull request that builds it; proposed the same day with the backlog
claim (0029, part 15). As built: `docs/design/0316-a-zip-whose-stated-sizes-are-false-9-october.md`.
Every archive above says truly what it unpacks to, so an app that checks only the sizes a zip states, and then
unpacks without counting, is credited. One more zip closes that: headers that state an ordinary small size, data
that unpacks to a mebibyte past `max-unpacked-bytes`, inside the same caps. It is judged as the others are, and
V5.2.3's credit needs it refused too. Readers that stop at the stated size and fail the checksum unpack nothing from
it; their apps answer with an error, which is a refusal or held back, never a finding.

## Later, 11 October 2026: a plain tar is an archive the check sends (backlog 0241)

Built by session tar-archives. `unpacks-archives` now takes `"tar"`, for an app that unpacks a plain, uncompressed `.tar`.
For it the check sends an ordinary small tar first, then one that unpacks just over the stated `max-unpacked-bytes`, as it does
for zip and gzip. The tar writer is `tar` in `archives.rs`: a 512-byte `ustar` header with its checksum, the data padded to whole
blocks, and the two empty blocks that end an archive.

Judged as zip is, with two differences that are said in the report rather than hidden:
- **No stated size to falsify.** A tar's header states one size, and Python's `tarfile` reads exactly that many bytes before it
  reads the next header. A tar whose stated size is smaller than its data is therefore refused as a broken archive, not
  unpacked short, so the "stating less" check is not built for tar.
- **Not compressed, so its size is its unpacked size.** One just over the most is sent only while it fits the upload's own
  cap (8 MiB, `MOST_UPLOAD_BYTES`); above that the report says it is not tested, rather than building it. A stated
  `max-files` for a tar is said not to be tested, as this check sends one-file tars only.

Tests: `each_plain_tar_unpacks_to_exactly_what_it_says_in_pythons_tarfile` reads sizes around a 512-byte block and the cap with
Python's `tarfile`. Break: the writer's padding or end blocks wrong, the test fails at its Python read. ADR-046's other
formats are unchanged.

Governs: unchanged in list; this entry adds the tar format to what the record covers.

## Later, 11 October 2026: a stored 7z, the owner's choice (backlog 0242)

The upload check now sends a 7z (`unpacks-archives = ["7z"]`), written by hand stored and not compressed, as the tar is,
so it is capped the same way: one just over `max-unpacked-bytes` is sent only when it fits the upload's own cap, and a
7z holding more than one file is not tested for `max-files`, which the report says. The reader that checks it is
`py7zr`, a test-only package pinned to one version (ADR-089). rar is not sent: the owner chose to keep it a known limit,
and a rar named in `unpacks-archives` is refused with its reason, as before.

Tests: `each_stored_7z_unpacks_to_exactly_what_it_says_in_py7zr` reads 7z files at the sizes the tar test uses, and the
most the check sends, back with `py7zr`. `a_7z_whose_data_is_altered_is_refused_by_py7zr` shows that reader checks the
data, not only the header. Break: the writer's CRC or data layout wrong, the round-trip test fails at its `py7zr` read.

Governs: the list is unchanged; this entry adds the 7z format to what the record covers.

## Later, 12 October 2026 (the third weekly review)

A refused archive is credited in part, not in full (`crates/sv-check/src/signed_in/archives.rs`, #1410, 10 October, ADR-053's "Later"). So "is credited" in the Decision reads "is credited in part". The formats and limits are as written.

**15 October 2026: accepted means answered as the ordinary archive was (backlog 0560, ADR-119).** An archive past the
limits is found only when it was answered as the ordinary small archive of its format was: an archive refused on the
upload form shown again with 200 is under 400 too. An answer unlike the ordinary archive's is not assessed and says
what was compared. The ordinary GIF sent straight after a refusal must be answered as the ordinary archive was before
the refusal is credited. The archive is never fetched back, since an app may unpack it rather than keep it as sent.

**15 October 2026: the ordinary archive answered with the upload form (backlog 0560, ADR-119).** An ordinary small
archive answered with a 2xx carrying a file field (the upload form shown again) is not taken as accepted, since an
archive is never fetched back: V5.2.3 is not assessed for that format, and says so.

## Later, 15 October 2026: the kind of file the upload checks send (backlog 0584)

An app that takes only some kinds of file refused the ordinary GIF every upload check is read beside, and every upload
requirement stopped there, with no way for the owner to say what it takes (the game site in the Opus run, backlog 0577,
took single-file HTML pages only). The upload entry gains `accepts`, a list of extensions or media types in the owner's
order (`crates/sv-manifest/src/lib.rs`, named in the spec `sv init` prints). The ordinary file is then the first kind on
the list `sv` can make (GIF, PNG, JPEG, HTML, PDF, plain text, CSV, or JSON:
`crates/sv-check/src/signed_in/uploads/kind.rs`), and so is every file built to be refused beside it: too large, with
contents that are not that kind, named to climb out of the folder, named to break the download's header, and the
ordinary file sent after a refusal. A refusal is still credited only beside an ordinary file of the same kind that was
taken. Without `accepts`, a GIF, as before. When `accepts` names nothing `sv` can make, or nothing at all, nothing is
sent and the upload requirements are not assessed, saying so. Each file is the kind's opening bytes, a marker, and its
closing bytes, as the GIF was: enough for a check of what a file starts with, not a picture or a page a viewer opens.

What this does not change: the archives this record governs are sent as before (a refusal of one is read beside an
ordinary file of the kind sent, as every refusal is), and the SVG, the antivirus test file,
and the pages and code sent to see how an upload is served keep their own kinds, as each of those checks is about its
kind. Governs: unchanged in list; this entry adds `accepts` to the upload entry's settings it covers.
