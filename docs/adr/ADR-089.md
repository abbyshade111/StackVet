# ADR-089: The part 4 audit's one-sample credits are checked in part, as the owner approved on 11 October 2026

**Status:** accepted, 11 October 2026, at the owner's word ("I agree and approve all your recommendations"), in the pull
request that makes the marks (backlog 0006, part 4).

**Governs:** `crates/sv-check/src/oidc.rs`, `crates/sv-check/src/signed_in/sessions.rs`, `crates/sv-check/src/signed_in/signin.rs`,
`crates/sv-check/src/signed_in/tokens.rs`, `crates/sv-check/src/probes.rs`, `crates/sv-check/src/production.rs`,
`crates/sv-check/src/running.rs`, `crates/sv-check/src/signed_in/passwords.rs`, `crates/sv-check/src/signed_in/codes.rs`,
`crates/sv-check/src/browser.rs`, `crates/sv-check/src/signed_in/admin.rs`: the credits marked in part here. A pull request that
changes which credit is in part, or the reason for it, changes this record too, or says in its description why it does not.

## Context

Backlog 0006, part 4 asked for every running check that credits a requirement from one sample to be read against the
groups A to H of ADR-053, and marked "checked in part" where one sample cannot speak for the rest. The audit read the plain
credit sites across the check code. Its recommendations, approved on 11 October 2026, are applied here.

## Decision

1. **Group B** (one page, one sign-in, one session): the same email on two accounts (`oidc.rs`), the idle timeout and the
   lifetime of a session (`sessions.rs`), and the brute-force limit on one account (`signin.rs`).
2. **Group C** (one request or flow): the issuer, nonce, audience, signature and cross-session checks of the OIDC sign-in
   (`oidc.rs`); the expiry of the app's own token (`tokens.rs`); TRACE (`probes.rs`); the three GraphQL checks
   (`probes.rs`); the one request to the root answered 301 (`production.rs`); and the app stopping during the questions
   (`running.rs`).
3. **Group G** (one of several named operations): the context-word password (`passwords.rs`), and the email code used in
   another session and the guessing of email codes (`codes.rs`).
4. **Group H** (listed pages or forms): the password fields not masked (`passwords.rs`), and the sign-out control on each
   listed private page (`browser.rs`).
5. **Decisions approved as recommended:**
   - Password rule probes (length, composition, altered comparison, the current password on a change) are in part: one
     password is one sample of every password the rule governs.
   - A fixed list of names (`/.git` in `probes.rs`, the 16 private file names in `running.rs`) is in part, as a fixed list
     is not every file.
   - Per-client grants (V10.4.4, `running.rs`) are in part: a published server-wide list does not show per-client grants.
   - Other users' data on one record (`admin.rs`) is in part: one record of one owner is one sample.
6. **Kept whole, as recommended:** the long password (V6.2.9 says the length is "permitted", a capability), the
   port-level answer on port 80 (`production.rs`), the certificate and stapling checks (one certificate and one handshake
   per service, normally a server setting), and the answers a person or the AI records (`confirm.rs`, `notes.rs`,
   `design.rs`, `hand.rs`), whose tier already says whose answer it is.

## Not decided here

- The `running.rs` check of the admin page found by its address (`ADMIN_BY_ADDRESS`) was not in the approved
  recommendations. Decided 11 October 2026: left as it is. It credits no requirement (its requirement list is empty), so
  a mark would change no count; its own text already says what it shows (the headers opened none, and what else guards the
  pages is not something a request shows), and V8.4.2 (level 3, several layers of protection) is not claimed by it.
- `suite.rs` and the `.gitignore` check in `config.rs` have not been read test by test, so they are unchanged.

## Consequences

- The reports of apps with a single listed item, page or action now say "checked in part" for those checks, as a single listed
  admin page already did. Nothing a correct app earned is taken away: an in-part credit still counts as evidence, and is
  shown as such.
- Each marked check's own test now asserts "in part", and a test fails when its mark is removed.
# ADR-089: A test-only 7z reader, `py7zr` pinned to one version, to check the 7z archives the upload check sends

**Status:** accepted, 11 October 2026, at the owner's choice ("A for rar and B for 7z", then "py7zr, a Python package" as
the reader), in the pull request that builds it (backlog 0242).

**Governs:** `crates/sv-check/src/signed_in/archives.rs` (the 7z writer and the test that reads its files back), and
`.github/workflows/rust.yml` (the step that installs the reader before the tests run). A pull request that changes
either changes this record too, or says in its description why it does not (`docs/adr/README.md`).

## Context

The archive check (ADR-046) writes its own zip, gzip, and tar files, by hand, and checks each one with a reader that is
not `sv`'s own: Python's standard `zipfile`, `gzip`, and `tarfile`. A 7z archive needs the same check. Python's standard
library has no 7z reader. Writing 7z by hand is possible for a stored (uncompressed) file, which is how the tar is
written, and the owner chose to build 7z on those terms; rar has no open writer, so it stays a known limit that the
check does not send.

## Decision

- **The 7z files are written by hand, stored, not compressed**, so a 7z is as big as what it unpacks to. It is capped
  as a tar is (ADR-046): one just over the stated most is sent only when it fits the upload's own cap, and a 7z holding
  more than one file is not tested for `max-files`, which the report says.
- **`py7zr` reads them back in the tests**, a Python package outside `sv`, pinned to `1.1.3` (uploaded 19 June 2026,
  more than two weeks before this change). It is installed only in the CI step that runs the tests. `sv` does not
  ship with it, does not import it, and runs nothing from it.
- **The tests fail without it**: the archive test reports that Python refused the archive, so a machine without
  `py7zr` cannot pass the test without reading the 7z files.
- **rar stays refused by name** in `stackvet.toml`, as it was: a `unpacks-archives` entry of `rar` is refused with the
  reason, and no rar is ever sent.

## Alternatives considered

- **The `7z` program (p7zip)**: an independent reader, but a system install on the owner's Mac and in CI, not a Python
  package, and no pin the tests can check.
- **No reader, the layout checked by hand**: no new tool, but the test would check the writer against its own reading
  of the format. Declined, since the check's job is to say the file is read by something else.

## Consequences

- The tests now need `py7zr` installed. Installing it is a CI step; a developer running the tests on a Mac installs it
  into their own Python first (`python3 -m pip install py7zr==1.1.3`), as CI does.
- The pin is moved by a pull request that changes this record, after the new version is checked against the 7z files
  the tests write.
- `sv` at run time is unchanged: no new code path reads a 7z file, and the upload check gains only the 7z entries.
