# ADR-089: A test-only 7z reader, `py7zr` pinned to one version, to check the 7z archives the upload check sends

**Status:** accepted, 11 October 2026, at the owner's choice ("A for rar and B for 7z", then "py7zr, a Python package" as
the reader), in the pull request that builds it (backlog 0242).

**Governs:** `crates/sv-check/src/signed_in/archives.rs` (the 7z writer and the test that reads its files back), and
`.github/workflows/rust.yml` and `.github/workflows/windows.yml` (the steps that install the reader before the tests run;
the Windows one was missed in the first pull request and added after the main branch went red on Windows, 11 October 2026). A pull request that changes
either changes this record too, or says in its description why it does not (`docs/adr/README.md`).

## Context

The archive check (ADR-046) writes its own zip, gzip, and tar files, by hand, and checks each one with a reader that is
not `sv`'s own: Python's standard `zipfile`, `gzip`, and `tarfile`. A 7z archive needs the same check. Python's standard
library has no 7z reader. Writing 7z by hand is possible for a stored (uncompressed) file, which is how the tar is
written, and the owner chose to build 7z on those terms; rar has no open writer, so it stays a known limit that the
check does not send.

## Decision

- **The 7z files are written by hand, stored, not compressed**, so a 7z is as big as what it unpacks to. It is capped
  as a tar is (ADR-046): one just over the stated most is sent only when it fits the upload's own cap, and a 7z holding
  more than one file is not tested for `max-files`, which the report says.
- **`py7zr` reads them back in the tests**, a Python package outside `sv`, pinned to `1.1.3` (uploaded 19 June 2026,
  more than two weeks before this change). It is installed only in the CI step that runs the tests. `sv` does not
  ship with it, does not import it, and runs nothing from it.
- **The tests fail without it**: the archive test reports that Python refused the archive, so a machine without
  `py7zr` cannot pass the test without reading the 7z files.
- **rar stays refused by name** in `stackvet.toml`, as it was: a `unpacks-archives` entry of `rar` is refused with the
  reason, and no rar is ever sent.

## Alternatives considered

- **The `7z` program (p7zip)**: an independent reader, but a system install on the owner's Mac and in CI, not a Python
  package, and no pin the tests can check.
- **No reader, the layout checked by hand**: no new tool, but the test would check the writer against its own reading
  of the format. Declined, since the check's job is to say the file is read by something else.

## Consequences

- The tests now need `py7zr` installed. Installing it is a CI step; a developer running the tests on a Mac installs it
  into their own Python first (`python3 -m pip install py7zr==1.1.3`), as CI does.
- The pin is moved by a pull request that changes this record, after the new version is checked against the 7z files
  the tests write.
- `sv` at run time is unchanged: no new code path reads a 7z file, and the upload check gains only the 7z entries.
